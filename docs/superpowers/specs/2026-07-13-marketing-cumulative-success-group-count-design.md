# 营销任务累计成功群组数量 - 规格

## 背景

营销任务列表当前展示 `targetGroupCount`，数据库字段为
`marketing_task.target_group_count`。现有逻辑在创建任务时只统计明确选择的固定群组；账号动态目标在发送轮次中才解析真实群组，因此列表可能在已经成功发送消息后仍显示 0 个群。

最新业务口径不再是“创建时选择的目标群数”，而是“该任务历史上成功触达过的唯一 WhatsApp 群数量”。这个数量只在收到协议发送成功结果后增长，同一群跨轮次、跨账号或重试成功都只能累计一次，并且后续不因群组状态变化而减少。

## 统计口径

- 统计范围是单个租户下的单个营销任务。
- 群组唯一标识使用去除首尾空白后的 WhatsApp `group_jid`，不使用内部 `group_link_id`。
- 只有 `marketing_task_send_attempt.status = 1` 的成功尝试可以产生累计群组。
- 已进入队列、发送中、失败、跳过和等待重试的尝试均不计入。
- 同一任务下相同 `group_jid` 无论成功多少轮、发送多少条、使用多少账号，都只计数一次。
- 计数单调递增；群组被封禁、失效、解散或账号退出后不扣减。
- 本功能不维护“当前可用群组数量”。后续若需要，应使用独立字段和独立统计口径。

## 数据模型

新增不可变去重事实表 `marketing_task_success_group`：

- `id`: 主键。
- `tenant_id`: 租户 ID。
- `marketing_task_id`: 营销任务 ID。
- `group_jid`: 去除首尾空白后的 WhatsApp 群 JID；空字符串不允许入表。
- `first_success_attempt_id`: 首次成功对应的发送尝试 ID，便于审计。
- `first_success_at`: 首次成功时间，epoch 毫秒。
- `created_at`: 记录创建时间，epoch 毫秒。

唯一约束为：

```text
(tenant_id, marketing_task_id, group_jid)
```

唯一约束是跨轮次、跨账号并发成功时的最终幂等边界。表不设置软删除字段；成功触达事实一旦产生就不能因后续业务状态变化而删除。项目现有业务表未使用数据库外键，本表保持相同约定。

继续复用 `marketing_task.target_group_count` 保存累计成功群组数量，避免破坏现有接口字段 `targetGroupCount`。通过新迁移修改该列注释为“任务累计成功触达去重群数”，新建任务一律初始化为 0。前端列表列名改为“累计有效群组数量”。

## 成功结果处理

修改正常群组营销的成功结果回写链路，不修改定时轮次生成逻辑。

1. `MarketingSendResultServiceImpl` 收到普通营销成功事件。
2. `markAttemptSuccess` 只允许把 `SUBMITTED` 尝试首次更新为 `SUCCESS`。同一 attempt 的重复事件继续按现有逻辑直接跳过。
3. 从已成功的 attempt 取得持久化后的 `marketing_task_id` 和 `group_jid`。优先使用 attempt 在生成发送命令时保存的实际群快照；仅当原值为空时，现有成功回写 SQL 才使用事件中的 `groupJid` 补齐。
4. 尝试向 `marketing_task_success_group` 插入一条事实记录。
5. 插入影响 1 行时，执行 `target_group_count = target_group_count + 1`；唯一键已存在时影响 0 行，不更新计数。
6. 继续执行现有 target 成功汇总、任务成功消息条数累计和关联结果回写。

步骤 2 至步骤 6 均处于现有 `@Transactional(rollbackFor = Exception.class)` 事务中。若成功 attempt 已落地但群组事实或任务计数更新失败，整个事务回滚，避免事实表与主表计数不一致。

成功 attempt 最终仍没有有效 `group_jid` 时：

- 正常维护消息成功条数；
- 不写成功群组事实，不增加累计群组数量；
- 输出包含 tenantId、taskId、targetId、attemptId 的告警日志，便于修复协议或历史数据。

## 并发与幂等

- 同一成功事件重复消费：`markAttemptSuccess` 第二次影响 0 行，不再进入群组累计逻辑。
- 不同 attempt 同时成功且群相同：数据库唯一约束只允许一个事务插入成功，只有该事务执行 `+1`。
- 同一群先失败后由新 attempt 重试成功：失败不写事实；首次成功写入事实并 `+1`。
- 同一群已经成功后再次失败或再次成功：事实记录保留，计数不变。
- 同一个群在不同营销任务中成功：按任务分别累计一次。

不得使用内存集合、本地缓存或先查后插的非原子流程作为去重依据。

## 历史数据迁移

新增 Flyway 迁移，顺序执行：

1. 创建 `marketing_task_success_group` 及唯一约束。
2. 从历史 `marketing_task_send_attempt` 中筛选 `status = 1` 且 `group_jid` 非空的数据。
3. 按 `(tenant_id, marketing_task_id, TRIM(group_jid))` 去重，选择最早成功记录写入事实表。
4. 按事实表记录数一次性回填全部 `marketing_task.target_group_count`；没有成功事实的任务回填为 0。
5. 修改 `target_group_count` 的数据库字段注释。

这次迁移回填是新旧口径切换所需的一次性校准，不属于运行期每轮重算。迁移前应统计成功 attempt 中 `group_jid` 为空的数量；这部分因为缺少群唯一 ID，不能猜测或计入。

## 接口与前端

- 后端继续返回 `targetGroupCount`，数值语义改为累计成功触达去重群数。
- 任务列表和详情继续读取同一字段。
- 列表列名从“营销群组数量”改为“累计有效群组数量”。
- 本次不新增“当前可用群组数量”字段，也不在页面端重新聚合发送记录。

## 日志

成功结果回写日志增加本次是否新增累计群组事实，例如 `newSuccessfulGroup=true/false`。缺少有效 `group_jid` 时使用 warn 级别日志。日志不得输出消息正文或凭据。

## 测试

后端单元测试：

- 第一个群首次成功时插入事实并增加群组计数。
- 同一 attempt 的重复成功事件不插入事实、不增加消息计数和群组计数。
- 不同 attempt、不同轮次对同一群成功时，消息成功条数分别增加，群组数量只增加一次。
- 同一任务第二个不同群成功时，群组数量增加到 2。
- 失败、跳过或待重试尝试不写成功群组事实。
- 成功 attempt 缺少 `group_jid` 时不增加群组数量并记录告警。

后端数据库测试：

- 验证 `(tenant_id, marketing_task_id, group_jid)` 唯一约束。
- 验证固定群与账号动态目标命中同一 `group_jid` 时只累计一次。
- 验证两个账号成功触达同一群时只累计一次。
- 验证事务异常时 attempt、事实表和任务计数一起回滚。
- 验证历史回填后 `target_group_count` 等于历史成功 attempt 的去重群数，而不是创建时选择群数。

前端测试：

- 列表列名展示“累计有效群组数量”。
- 字段仍读取后端 `targetGroupCount`，不在前端自行计算。

## 非目标

- 不调整定时轮次解析群组、积压保护和 outbox 生成逻辑。
- 不改变成功消息条数和失败消息条数的现有累计口径。
- 不实现当前可用群组数量、群组流失数量或运营趋势分析。
- 不把普通群组营销的累计逻辑扩展到建群营销任务。

## 自检

- 无待定项或占位符。
- 统计发生在成功结果回写阶段，与“实际成功后才计入”一致。
- 唯一约束覆盖重复事件以外的跨轮次、跨账号并发场景。
- 新建任务初始化、历史数据回填、接口语义和页面文案保持一致。
- 当前可用群组数量明确排除在本次范围外，未与累计成功群数混用。
