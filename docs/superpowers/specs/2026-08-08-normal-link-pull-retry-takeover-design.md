# 普通群链接模式随机静默、失败重试与异常接管设计

## 1. 文档状态

- 设计日期：2026-08-08
- 适用模式：普通群链接模式（`NORMAL_LINK`）
- 设计结论：采用“逐号码执行记录”方案
- 业务代码状态：本文只固化设计，不代表实现完成

本文取代 `2026-08-07-puller-invite-result-delay-design.md` 中“仅管理员邀请拉手固定等待 3 秒”的局部设计。实现时应使用本文统一的 3～5 秒随机静默策略，不能叠加两套延迟。

## 2. 背景与目标

当前普通群链接模式在计划批量拉人时，会预先把整批站台号和料子号绑定到一次 `pull_task_pull_call`。拉手异常后，现有逻辑倾向于重置或保留整个批次，不能可靠表达同一批次内“部分成功、部分失败、部分没有结果”的事实。

本次调整需要实现以下目标：

1. 所有会实际改变 WhatsApp 状态的相邻协议操作之间增加 3～5 秒随机静默。
2. 站台号和料子号均按号码记录本次拉取结果，不能用单个结果代表整批结果。
3. 明确成功的号码永久保留成功，不得再次拉取。
4. 明确失败的号码最多重试 3 次；首次执行不算重试，因此单个号码最多执行 4 次。
5. 拉手异常导致结果未知时，先对该异常批次查询一次群成员名单；仍不能确认成功的号码必须释放并重新进入待拉池。
6. 失败重试或未知接管必须创建新的批次和命令，不能复用旧命令。
7. 迟到回调必须落到原执行记录，不能覆盖更新批次；迟到成功可以把号码提升为成功。
8. 下一可用拉手优先接管；没有其他可用拉手时，如果原拉手仍可用，可以继续使用原拉手。

## 3. 范围

### 3.1 包含范围

- Armada 后端普通群链接任务的批次规划、状态机、回调收口和资源等待。
- 数据库结构变更脚本及 MyBatis 映射。
- Web 协议端批量拉人结果语义。
- Android 协议端批量拉人结果语义。
- 站台号和料子号的统一失败重试、未知释放与迟到回调处理。
- 自动化测试和本地代码级验证。

### 3.2 不包含范围

- 不调整前端创建页、配置页和任务参数。
- “失败最多重试 3 次”是固定业务规则，不新增页面配置项。
- 不处理或回填历史任务、历史失败和历史批次数据。
- 不负责发布、环境开关、灰度、线上迁移执行和回滚操作。
- 不执行远程环境、真实数据库或生产数据操作。
- 不修改普通群链接模式以外的进群任务重试规则。

## 4. 术语

| 术语 | 定义 |
| --- | --- |
| 拉手 | 实际调用 WhatsApp 批量加群能力的执行账号 |
| 站台号 | 由拉手加入群内的站台账号，存储于 `pull_task_group_account` |
| 料子号/目标号 | TXT 中需要被拉入群的号码，存储于 `pull_task_material_member` |
| 参与者 | 一次批量拉人命令内的站台号和料子号统称，不包含拉手 |
| 批次 | 一次真实发送给 WhatsApp 的批量加成员命令，对应 `pull_task_pull_call` |
| 执行记录 | 某个号码在某个批次中的一次拉取事实 |
| 明确失败 | WhatsApp 针对该号码返回确定失败结果 |
| 结果未知 | 没有获得该号码的明确成功或失败结果 |
| 失败重试次数 | 明确失败后的额外执行次数；上限为 3，不包含首次执行 |

## 5. 已确认业务规则

### 5.1 三类号码结果

| 结果 | 号码最终状态 | 是否释放 | 是否增加失败计数 | 后续处理 |
| --- | --- | --- | --- | --- |
| 明确成功 | 成功 | 否 | 否 | 永久排除，不再拉取 |
| 明确失败且仍有重试机会 | 待拉取 | 是 | 是 | 由可用拉手重新执行 |
| 第 3 次重试仍明确失败 | 最终失败 | 否 | 是 | 停止重试 |
| 结果未知且群成员名单确认在群 | 成功 | 否 | 否 | 永久排除 |
| 结果未知且确认不在群 | 待拉取 | 是 | 否 | 重新执行 |
| 结果未知且群成员查询失败 | 待拉取 | 是 | 否 | 重新执行 |

所有明确失败均执行相同的 3 次重试规则，不按失败原因或协议 `retryable` 值区分。

结果未知不消耗失败重试次数，也没有独立次数上限。只要没有获得明确结果，该号码在核实和释放后仍可继续进入待拉池，直到成功、累计明确失败达到上限，或任务按现有生命周期被人工结束。

### 5.2 失败次数

固定参数：

```text
MAX_FAILURE_RETRY_COUNT = 3
MAX_EXPLICIT_FAILURE_COUNT = 4
```

状态转换：

```text
首次执行失败：explicit_failure_count = 1，安排第 1 次重试
第 1 次重试失败：explicit_failure_count = 2，安排第 2 次重试
第 2 次重试失败：explicit_failure_count = 3，安排第 3 次重试
第 3 次重试失败：explicit_failure_count = 4，最终失败
```

任意一次执行明确成功后立即成功收口，取消后续尚未提交的重试。

### 5.3 拉手选择

失败重试和未知释放后的新批次按以下顺序选择拉手：

1. 按当前执行行内拉手顺序，从上一拉手之后选择下一可用拉手。
2. 如果存在其他可用拉手，不立即再次选择上一拉手。
3. 如果没有其他可用拉手，但上一拉手仍然可用，可以继续使用上一拉手。
4. 如果上一拉手已经封禁、失效、离线或不可继续执行，且没有其他可用拉手，执行行进入“拉手不足”资源等待。
5. 补充拉手后从待拉号码检查点继续，不重新获取已经成功的号码。

站台号和料子号遵循完全相同的拉手选择规则。

### 5.4 用户验收示例

拉手 A 的批次包含 10 个目标号：

- 1～4 号明确成功：保留成功，不再拉取。
- 5 号明确失败：失败计数加 1，释放后进入第 1 次重试。
- 6～10 号没有明确结果：触发一次群成员名单核实；未确认在群的号码释放，失败计数保持 0。
- 拉手 A 已不可用：5～10 号后续由下一可用拉手 B 获取；新批次不得包含 1～4 号。

## 6. 总体架构

### 6.1 职责边界

Armada 后端是业务状态和重试决策的唯一来源：

- 规划批次和占用号码；
- 保存逐号码执行事实；
- 计算失败次数；
- 判断成功、重试、释放和最终失败；
- 选择下一拉手；
- 安排 3～5 秒随机静默；
- 处理迟到和重复回调。

Web 和 Android 协议端只报告本次真实执行事实：

- 执行一次批量加成员操作；
- 报告每个号码的成功、失败或未知；
- 报告操作是否确定已经发起；
- 保证相同命令 ID 不重复产生 WhatsApp 副作用；
- 提供既有的群成员名单查询能力。

协议端不计算失败次数，不决定是否重新入池，也不自动创建业务重试。

### 6.2 批次不可复用

一次 `pull_task_pull_call` 只表示一次真实 WhatsApp 批量命令。

- 协议提交后，参与者集合不可修改。
- 已提交批次不得清除命令 ID 后重新投递。
- 失败重试和未知接管必须创建新的 `pull_task_pull_call`、命令 ID 和幂等键。
- 新批次只包含当前仍需执行的号码。
- 如果迟到成功发生在新批次尚未提交前，取消该未提交批次并基于剩余号码重新规划，不能把旧的计划批次修改后冒充同一次调用。

## 7. 数据模型

### 7.1 新增逐号码执行记录表

新增 `pull_task_pull_call_member_attempt`，一行表示一个站台号或料子号在一个批次中的一次执行。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 执行记录主键 |
| `tenant_id` | 租户 ID |
| `task_id` | 拉群任务 ID |
| `group_execution_id` | 群执行行 ID |
| `pull_call_id` | 所属批次 ID |
| `participant_type` | `MATERIAL` 或 `STATION` |
| `participant_ref_id` | 料子行 ID 或站台角色行 ID |
| `target_phone` | 归一化号码快照 |
| `target_jid` | 目标 JID；协议返回后可补齐 |
| `puller_group_account_id` | 本次执行拉手角色行 ID |
| `attempt_no` | 该号码单调递增的计划执行序号；未知重拉和提交前取消均不复用旧序号，不用于判断失败上限 |
| `failure_count_before` | 本次执行前累计明确失败次数 |
| `lifecycle_status` | `PLANNED/SUBMITTED/CLOSED/RELEASED/CANCELED` |
| `protocol_outcome` | `SUCCESS/FAILED/UNKNOWN`，未回调时为空 |
| `execution_state` | `NOT_STARTED/STARTED/UNCERTAIN` |
| `reason_code` | 本次结果原因码 |
| `reason_message` | 本次脱敏结果描述 |
| `submitted_at` | 协议提交时间 |
| `result_at` | 协议结果时间 |
| `released_at` | 本次占用释放时间 |
| `created_at/updated_at` | 创建和更新时间 |

约束和索引：

- 唯一约束：`tenant_id + pull_call_id + participant_type + participant_ref_id`。
- 唯一活动约束：同一执行行、参与者类型和参与者 ID 同时只能有一条 `PLANNED/SUBMITTED` 记录。
- 回调索引：批次命令 ID 先定位 `pull_task_pull_call`，再以目标 JID/号码定位执行记录。
- 调度索引：`tenant_id + group_execution_id + lifecycle_status + id`。
- 记录只表达本次执行，不因创建后续重试而被覆盖或删除。

`lifecycle_status` 和 `protocol_outcome` 分离：前者表达本次占用是否仍有效，后者表达协议最终返回了什么。未知释放后如果收到迟到失败，可以保存迟到结果但不重新激活该执行；迟到成功可以提升号码的全局状态。

### 7.2 料子号聚合状态

`pull_task_material_member` 继续保存料子号当前业务状态，并增加：

- `pull_failure_count`：累计对当前有效执行生效的明确失败次数，默认 0；
- `active_pull_attempt_id`：当前有效执行记录 ID，释放或终态后置空；
- `last_puller_group_account_id`：最近一次真实执行拉手，用于选择下一拉手。

既有 `pull_call_id` 在执行中指向当前批次；释放回待拉池时清空；成功或最终失败时保留最后一次生效批次，兼容现有详情查询。

### 7.3 站台号聚合状态

`pull_task_group_account` 的站台角色增加：

- `membership_failure_count`：累计明确入群失败次数，默认 0；
- `active_pull_attempt_id`：当前有效执行记录 ID；
- `last_puller_group_account_id`：最近一次真实执行拉手。

站台释放时：

- `membership_status` 恢复为 `NOT_JOINED`；
- 清空当前 `pull_call_id` 和 `active_pull_attempt_id`；
- 保留逐次执行记录和最后拉手；
- 重新进入待拉站台池。

站台第 3 次重试仍明确失败后进入 `JOIN_FAILED`，不替换为另一个站台号码；本次规则重试的是同一个失败号码。

### 7.4 历史数据边界

数据库变更只新增结构，不回填历史执行记录。只有存在新版逐号码执行记录的批次进入本设计的新重试和接管状态机；历史批次和历史失败保持原状。

## 8. 批次规划与提交

### 8.1 待拉条件

一个号码可被选择必须同时满足：

- 聚合状态为料子 `UNCONSUMED` 或站台 `NOT_JOINED`；
- `active_pull_attempt_id` 为空；
- 没有数据库唯一活动约束冲突；
- 任务和执行行处于允许发起新动作的状态；
- 明确失败次数未达到 4。

### 8.2 事务边界

一次规划在同一数据库事务中完成：

1. 锁定待拉号码。
2. 选择符合规则的拉手。
3. 创建 `pull_task_pull_call`。
4. 为每个站台号和料子号创建执行记录。
5. 写入聚合表的当前批次和活动执行记录。
6. 将聚合状态改为执行中。
7. 提交事务后由调度器发送协议命令。

任一步失败时整个规划回滚，不能只创建批次却没有参与者，也不能只占用号码却没有执行记录。

协议载荷必须从该批次的逐号码执行记录生成，不再根据最初计划人数强行重建旧批次。批次提交后不允许因为部分结果而重新水合并发送同一批次。

## 9. 回调与批次收口

### 9.1 逐号码回调

回调使用 `tenant_id + command_id + target_jid/target_phone` 定位执行记录，并在事务中锁定执行记录和参与者聚合行。

- 重复回调只允许幂等补齐相同事实。
- 同一执行记录的成功事实不能被失败或未知覆盖。
- 只有当前活动执行明确失败时，才增加聚合失败计数。
- 旧的已释放执行迟到失败或未知只更新历史事实，不增加聚合失败计数。
- 任意执行记录迟到成功都可以把聚合状态提升为成功。

### 9.2 批次关闭条件

批次必须等到所有逐号码执行记录均满足以下一种状态后才能关闭：

- 已明确成功；
- 本次明确失败，且号码已进入重试或最终失败；
- 未知核实后已确认成功；
- 未知核实后已经释放；
- 协议提交前因迟到成功等原因被取消。

批次聚合状态只描述该次调用是否已经完成收口，混合结果由执行记录表达。不能因为首个 `ACCOUNT_NOT_ONLINE` 回调立即重置整批。

### 9.3 结果收集窗口

沿用现有未知结果收敛配置：

- 默认结果收集窗口：从批次提交开始 60 秒；
- 所有号码提前获得结果时立即进入批次收口；
- 窗口结束后仍缺失的号码按 `UNKNOWN + UNCERTAIN` 处理。

## 10. 拉手异常与群成员核实

拉手出现封禁、失效、离线或无法继续执行时：

1. 标记拉手不可用或进入既有冷却状态。
2. 保留已经收到的逐号码成功和失败结果。
3. 不再把整批目标统一标记为失败。
4. 等待已提交批次的结果收集窗口结束；如果结果已齐则提前处理。
5. 如果存在 `UNKNOWN + UNCERTAIN` 或缺失结果，通过任一可用群内账号调用协议一次，获取完整群成员名单。
6. 在后端本地批量比对所有未知站台号和料子号。
7. 已在名单中的号码成功收口。
8. 不在名单中的号码释放并重新入池。
9. 没有可用查询账号或名单查询失败时，不重复查询，直接释放全部待核实号码。

每个异常批次最多增加一次群成员名单协议查询，不按目标号码逐个发起协议调用。群成员名单查询是只读操作，不参与 3～5 秒副作用静默计算。

如果协议端能够确定 WhatsApp 调用根本没有开始，返回 `UNKNOWN + NOT_STARTED`。后端直接释放该批次相关号码，不需要查询群成员名单，也不增加失败次数。

## 11. 失败重试与接管

当前活动执行明确失败时：

```text
new_failure_count = current_failure_count + 1
```

- `new_failure_count <= 3`：关闭本次执行、清空当前占用、恢复待拉状态并创建后续重试机会。
- `new_failure_count >= 4`：关闭本次执行并进入最终失败，不再释放。

每次重新执行必须：

- 重新选择拉手；
- 创建新批次；
- 创建新的逐号码执行记录；
- 使用新命令 ID 和新幂等键；
- 在真实协议操作前满足静默时间约束。

按参与者原稳定顺序重新入池，因此失败重试和未知释放的号码优先于尚未执行的后续号码继续处理。已经成功的号码不再参与选号。

## 12. 迟到回调与状态优先级

全局状态优先级：

```text
成功事实 > 当前活动执行结果 > 已释放或已被替代的旧执行结果
```

规则：

- 旧执行迟到成功：聚合状态提升为成功，即使当前已处于待拉、执行中或最终失败。
- 新批次尚未提交：取消未提交批次并基于剩余号码重新规划。
- 新批次已经提交：不能撤回真实协议操作；保留两次执行事实，聚合状态仍为成功。
- 旧执行迟到失败或未知：只保存到旧执行记录，不能覆盖新批次，不能增加当前失败次数。
- 聚合状态一旦成功，任何失败、未知、释放或取消都不能使其降级。

并发处理采用行锁和条件更新；重复 Kafka 消息、多实例调度和服务重启均必须保持上述优先级。

## 13. 协议合同

### 13.1 逐号码结果

Web 和 Android 对每个号码统一返回：

- `SUCCESS`：WhatsApp 明确确认成功；
- `FAILED`：WhatsApp 明确确认失败；
- `UNKNOWN`：没有明确成功或失败结果。

同时返回本次副作用状态：

- `NOT_STARTED`：确定没有调用 WhatsApp；
- `STARTED`：已经调用 WhatsApp，并取得该号码的明确结果；
- `UNCERTAIN`：已经调用或无法确认是否调用成功，且该号码结果不明确。

合法组合及后端处理：

| 协议结果 | 后端处理 |
| --- | --- |
| `SUCCESS + STARTED` | 成功终态 |
| `FAILED + STARTED` | 增加失败次数并重试或最终失败 |
| `UNKNOWN + NOT_STARTED` | 直接释放，不查名单 |
| `UNKNOWN + UNCERTAIN` | 查询一次群成员名单后成功或释放 |
| 缺失回调 | 窗口结束后等价于 `UNKNOWN + UNCERTAIN` |

### 13.2 Web 与 Android 统一要求

- 拉手在调用前不可用时，不能再把整批映射为明确失败。
- `FAILED + STARTED` 只能来自 WhatsApp 对具体号码的明确报告，不能由批次级异常批量合成。
- 批量返回部分报告时，保留已明确结果，其余号码为未知。
- 调用超时、调用后异常或缺少单号码报告时，不能把所有号码统一标记为失败。
- 站台号和料子号使用同一结果映射。
- 同一命令 ID 重复投递时不得重复调用 WhatsApp。
- `retryable` 保留用于诊断，但不参与本次业务重试判断。
- 两端使用相同原因码和合同测试数据。

## 14. 3～5 秒随机静默

### 14.1 适用操作

所有会实际改变 WhatsApp 状态的相邻协议操作之间增加随机静默，包括：

- 管理号通过链接进群；
- 设置管理号为管理员；
- 保存联系人；
- 邀请拉手进群；
- 连续的邀请操作；
- 拉手批量拉入站台号和料子号；
- 连续的批量拉人命令；
- 设置料子号为管理员；
- 异常接管后新拉手的第一条 WhatsApp 操作。

一次批量拉 10 个号码仍然是一条 WhatsApp 操作，不在 10 个号码内部增加逐号码静默。

### 14.2 不适用操作

- 数据库状态切换和批次规划；
- 失败次数计算和待拉池释放；
- 任务进入等待、暂停、结束等内部状态；
- 群成员名单查询和后端本地比对；
- 不产生 WhatsApp 副作用的内部协议或查询动作。

### 14.3 调度计算

随机延迟满足：

```text
3_000ms <= random_silence_ms <= 5_000ms
```

后端通过可注入的统一延迟策略生成随机值，并把实际截止时间持久化到执行行 `next_run_at`。禁止使用 `Thread.sleep` 占用调度线程，禁止服务重启后重新抽取随机时间。

已确认发起或无法排除已经发起的操作，无论最终结果是成功、失败还是未知，都从本次结果时间开始安排随机静默。协议明确返回 `NOT_STARTED` 时没有 WhatsApp 副作用，不单独增加静默；后续动作仍受它之前最后一次真实副作用操作的截止时间约束。

与现有批次拉取间隔取较大值：

```text
next_run_at = max(
    last_batch_submitted_at + pull_interval,
    last_whatsapp_result_at + random_silence
)
```

两种间隔不相加。例如原批次间隔 10 秒、随机静默 4 秒，实际等待 10 秒；原批次间隔 2 秒、随机静默 4 秒，实际等待 4 秒。

## 15. 查询、统计与任务完成

- 成功数量只统计聚合成功状态，不按执行记录累加。
- 最终失败只统计失败次数达到 4 的号码。
- 明确失败后等待重试、未知释放后的号码都属于待拉取，不得计为已使用。
- 执行中只统计当前存在有效执行记录的号码。
- 历史执行记录只用于审计和故障分析，不直接叠加到看板人数。
- 只要仍有待拉、执行中、待核实或资源等待号码，执行行不能完成。
- 没有可用拉手时进入资源等待，不丢失待拉号码。
- 任务被人工结束时，继续沿用现有生命周期取消尚未提交动作；本次设计不改变人工结束语义。

## 16. 错误处理与可观测性

至少记录以下结构化指标或日志计数：

- 每批成功、明确失败、未知和缺失结果数；
- 失败重试第 1、2、3 次的号码数；
- 达到最终失败的号码数；
- 拉手异常批次数；
- 群成员名单查询成功、失败和跳过次数；
- 未知释放号码数；
- 迟到成功、迟到失败和重复回调数；
- 因无可用拉手进入资源等待的执行行数；
- 超过结果收集窗口仍未收口的执行记录数。

日志不得输出未脱敏凭据、会话信息或完整敏感载荷。号码沿用项目现有脱敏规则。

## 17. 测试与验收

### 17.1 Armada 后端

必须覆盖：

1. 1～4 成功、5 失败、6～10 未知的用户示例。
2. 成功号码不会进入新批次。
3. 首次失败加 3 次重试，总共最多执行 4 次。
4. 第 1～3 次重试中任意一次成功后停止重试。
5. 第 3 次重试仍失败后进入最终失败。
6. 未知释放不增加失败次数。
7. 下一可用拉手优先，无其他拉手时复用仍可用的原拉手。
8. 原拉手不可用且无其他资源时进入“拉手不足”。
9. 站台号与料子号执行相同状态转换。
10. 一个异常批次最多查询一次群成员名单。
11. 名单确认在群后成功收口；不在群或查询失败后释放。
12. `UNKNOWN + NOT_STARTED` 直接释放且不查询名单。
13. 迟到成功提升全局成功，迟到失败和未知不覆盖新执行。
14. 新批次尚未提交时收到旧成功，取消并重新规划剩余号码。
15. 新批次已提交时收到旧成功，保留两次事实且聚合保持成功。
16. 重复 Kafka 回调不重复增加失败次数。
17. 多实例并发规划不能重复占用同一号码。
18. 部分结果后不能重新发送原批次，接管必须创建新命令。
19. 服务重启和暂停恢复后不提前执行静默动作。
20. 随机静默上下界分别为 3,000 和 5,000 毫秒。
21. 随机静默与原批次间隔取较大值。
22. 聚合查询把失败待重试和未知释放统计为待拉取。

### 17.2 Web 协议端

必须覆盖：

- 全部成功；
- 成功、失败混合；
- 部分报告缺失；
- 调用前拉手不可用；
- 调用后超时或异常；
- 同一命令 ID 重复投递；
- 站台号和料子号相同结果映射。

### 17.3 Android 协议端

使用与 Web 相同的合同数据覆盖相同用例，保证同一输入产生相同 `outcome + execution_state + reason_code`。

### 17.4 本地验证边界

本次实现完成时只运行本地单元测试、数据库映射测试、集成测试和协议端自动化测试，不执行真实环境发布、远程操作或线上数据变更。

## 19. 设计约束总结

1. 只有明确结果才能完成号码状态收口；未知必须核实或释放。
2. 成功是不可降级的最高优先级事实。
3. 明确失败最多额外重试 3 次，未知不占失败次数。
4. 站台号和料子号使用同一逐号码状态机。
5. 拉手异常不能触发整批成功、整批失败或原批次重投。
6. 每次真实重试都是新批次、新命令和新执行记录。
7. 每个异常批次最多查询一次完整群成员名单。
8. 所有 WhatsApp 副作用操作之间统一使用持久化的 3～5 秒随机静默。
9. 数据库内部阶段切换和只读群成员查询不增加静默。
10. 本设计不包含历史数据处理和发布工作。
