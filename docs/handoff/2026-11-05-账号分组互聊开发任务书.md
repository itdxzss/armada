# 账号分组互聊开发任务书

日期：2026-11-05。状态：离线开发完成；实现及验证见 [交付记录](../../.harness/changes/account-group-mutual-chat/summary.md)，真实验收尚未执行。

完整方案与取舍理由见 [账号分组互聊：简版分析方案](../business/2026-11-05-account-group-mutual-chat-analysis.md)，本文只写要做的事。两份文档有冲突时以分析方案为准，并告知用户。

## 1. 要做什么

账号列表增加"互聊"按钮。运营选两个账号分组 A、B，填 A 的文案、B 的文案和单账号发送间隔，预览后创建后台任务。A 组每个账号向 B 组每个账号发 A 文案，B 组每个账号向 A 组每个账号发 B 文案；2×M×N 条消息，每对账号双方各一条。

任务可停止；失败、待确认、已取消的方向可重试。整体做法照搬已上线的"两个分组互加好友"，只是把"保存联系人"换成"发私聊文本"。

### 不做

- 不加 yml、环境变量配置项；发送间隔是页面上的任务参数。
- 不做送达/已读追踪，不做收到消息后自动回复，不做多轮剧本、随机文案、循环发送。
- 不让协议层自动重发。重试只由用户在页面点按钮触发。
- 只发固定纯文本，不发图片、链接卡片、按钮。

## 3. 与互加的差异（实现时最容易照抄错的地方）

| 项 | 互加 | 互聊 |
|---|---|---|
| 动作 | `contact.save.requested`，经 `ProtocolMutualContactCommandService` 和 Hydrator 补 payload | 消息命令 `MessageSendPort.enqueue`，`PRIVATE + TEXT`，文本直接放命令里，不用 Hydrator |
| 来源 | `account_group_mutual_contact` | `account_group_mutual_chat`，关联字段 `mutualChatTaskId`、`mutualChatItemId` |
| 结果入口 | `ProtocolGroupEventConsumer` 的群动作结果 | `ProtocolMessageEventConsumer` 的消息发送结果，新增 Sink |
| 失败是否可重试 | 看协议返回的 `retryable` | 消息结果没有该字段，不设 `retryable` 列，所有失败都可重试 |
| 重试范围 | 失败（可重试）+ 待确认 | **失败 + 待确认 + 已取消** |
| 文案 | 无，联系人名称用对方号码 | 主表存 A、B 两段文案；明细表存"方向"，调度时按方向取文案 |
| 间隔 | 默认 0，范围 0~3600，常量在 `AccountMutualContactPolicy` | 默认 10（前端初始值），范围 1~3600，规模上限 5000，文本上限 1000 字符，常量放新建的 `AccountMutualChatPolicy` |
| 协议层间隔 | 不涉及 | 间隔只由控端调度控制，命令里 `sendIntervalMs` 填 0 |
| 重复风险 | 保存联系人覆盖写，重试无害 | 重试待确认项可能让对方收到重复消息，界面要提示 |

## 4. 数据

迁移走 Flyway，版本号从 **V225** 起（开发时再核对一次是否撞号，当前最新是 V224）。新建两张表，命名和注释风格对齐 `V202`。按 `数据模型规范.md` 一、二节：每列有 `COMMENT`，状态列逐值说明，时间用 `xxx_at`（epoch 毫秒），不留死列。

**`account_mutual_chat_task`**：租户、创建人、请求幂等键、两个分组 ID 与名称快照、两侧参与数、**A 文案、B 文案**（长度按 1000 字符留够）、发送间隔秒数、任务状态、创建/更新时间。唯一键 `(tenant_id, created_by, request_id)`，分页索引同 `V202`。任务状态沿用互加的四值：1 执行中、2 已停止、3 全部成功、4 需关注。

**`account_mutual_chat_item`**：租户、任务 ID、发送账号 ID、目标账号 ID、发送方与目标方 WS 号码快照、协议账号 ID 与协议后端（WEB/ANDROID）快照、**方向**（1=A→B 发 A 文案，2=B→A 发 B 文案）、状态、当前命令 ID、尝试序号、**协议消息 ID**、原因码、提交时间、结果时间、下次可派发时间、创建/更新时间。**没有 `retryable` 列。**

- 状态沿用互加的六值：1 待发送、2 已提交、3 成功、4 失败、5 待确认、6 已取消。
- 唯一键：`(tenant_id, task_id, actor_id, target_id)` 保证同一任务同一方向只有一条；`command_id` 唯一。索引照 `V202`。
- 成功数、双向成功对数现场聚合（照 `stats` 的写法），不另存。

迁移完成后：重跑 `.harness/wiki/gen_datamodel.py` 刷新 `数据模型.md`；按数据模型规范第四节补 `.harness/changes/<本任务>/db-migrations.sql` 和 `rollback.sql`。

## 5. Armada 后端

### 5.1 账号域（照 `AccountMutualContact*` 的骨架新建 `AccountMutualChat*`）

- Controller：前缀 `/api/accounts/mutual-chat-tasks`。`POST /preview`、`POST /`（创建）、`GET /`（分页）、`GET /{id}`、`GET /{id}/items`、`POST /{id}/stop`、`POST /{id}/retry`。读权限 `tenant:account:view`，写权限 `tenant:account:edit`，和互加一致。
- Service：预览、创建、列表、详情、明细、停止、重试。
  - 预览/创建里的账号选择、去重、归属校验、`previewToken` 防参与范围变化，**抽取互加的公共逻辑后共用**，不要复制粘贴。两组都有的账号归 A 组。
  - 创建时校验：两个分组不同；间隔在 1~3600 秒；消息数 2×M×N 不超过 5000；A、B 文案去除首尾空白后不为空且不超过 1000 字符；请求幂等键格式同互加。
  - 创建同事务写主表和全部方向明细（批量 200 条一插），方向明细按"左→右"为方向 1、"右→左"为方向 2。
  - 停止：任务置已停止，待发送转已取消；已提交的继续收回执。
  - **重试：把状态为 4、5、6 的方向改回待发送，任务置执行中。** 对应 Mapper 的 `retryFailed` 条件是 `status IN (4,5,6)`，不含 `retryable`。
- 调度器（照 `AccountMutualContactScheduler`）：每 500ms 扫描；超过 300 秒未回执的已提交转待确认；`TenantContext` 先设后还原。
- 事务派发（照 `AccountMutualContactTransactions.dispatch`）：
  - 先锁任务再锁账号；同账号在途（已提交）或冷却未到则跳过；单任务在途不超过 100。
  - 派发前复核：发起人权限、账号归属、账号资格（`AccountMutualContactAccess.eligible`）、号码与协议身份是否变化；不满足则该方向记失败并写原因码。
  - 组装 `MessageSendCommand`：账号引用用 `ProtocolAccountRef(actorId, backend, protocolAccountId, actorPhone)`；目标 `MessageTarget(targetPhone + "@s.whatsapp.net", PRIVATE)`；`MessagePayload(TEXT, 内容=对应方向的文案, mentionAll=false, replyTo=null)`；关联 `source = account_group_mutual_chat`，带任务 ID、方向明细 ID；命令 ID `cmd_` + 去掉连字符的 UUID，**每次派发都新生成**；`sendIntervalMs = 0`、`notBeforeAt = 0`。
  - 调用 `MessageSendPort.enqueue`。返回 `accepted=false` 记该方向失败；整批抛异常则事务回滚，下个周期重试。
  - 下次可派发时间 = 结果处理时间 + 任务间隔；原因码含 `RATE` 或 `LIMIT` 时至少退避 60 秒（同互加）。
- 回执规则见 5.3。

### 5.3 结果回写

- `platform/kafka/consumer/message/ProtocolMessageSendResultReportedEvent.java`：增加两个字段（保留兼容构造器）。
- `ProtocolMessageEventConsumer.java`：
  - `toSendResultReportedEvent`（约 210 行）：互聊来源免除 `marketingTaskId`、`targetId`、`attemptId`、`roundNo`、`groupJid` 的必填，必填 `mutualChatTaskId`、`mutualChatItemId`；不免除会让每条结果解析失败、进 Kafka 重试。
  - `businessId`、`businessItemId`（约 146~164 行）增加互聊分支，保证风控元数据正确。风控本身由消费者统一处理，Sink 里不用再接。
- 新增 `AccountMutualChatResultSink`，同时实现 `ProtocolMessageSendResultReportedSink` 和 `ProtocolMessageAckSink`：
  - 发送结果：`supports` 只认互聊来源（默认营销 Sink 不会误吞）。按命令 ID 找方向，并核对任务 ID、方向明细 ID、发送账号、协议账号、目标 JID，全部一致才处理。只接收状态为"已提交"或"待确认"的方向。
  - 判定：`success=true` 且有消息 ID → 成功并写消息 ID；`outcome=UNKNOWN`，或原因码为 `SEND_RESULT_UNKNOWN`、`UNKNOWN`、`EMPTY_MESSAGE_ID` → 待确认；其余 → 失败。待确认可被同一命令晚到的明确结果升级；重试换了命令 ID 后，旧命令的回执核对不上，直接忽略。
  - ACK：`supports` 认互聊来源，`handleAck` **空实现**。原因：Web 对所有已记录关联的消息都会发 `message.ack`（`event-bridge.ts` 约 329~376 行，不按来源过滤），后端 `selectAckSink` 没有匹配处理器会抛 CONFLICT，触发 Kafka 反复重试。开发时用测试确认这一点。

## 11. 真实验收（另行，需用户确认环境和账号后执行）

用 A=2、B=3 的小样本，在明确授权的测试账号上分别覆盖纯 Web、纯 Android、混合协议：

1. 核对 12 条方向、6 对结果，双方文案正确，间隔约 10 秒。
2. 制造一次单方向失败，停止任务后重试，确认只重发失败方向。
