## 代理失败仍在循环

17 个样本在 35 分钟内共收到 3,429 条 `PROXY_FAILED` 事件；对应账号出现 3,430 条“事件未携带 proxyId”跳过日志。两种日志并非严格一一对应。本次筛选没有检出“IP代理失败标记不可用”日志；这只是日志观察，不是全库代理状态计数。

这些次数来自事件接收和 outbox 写入前的代理分配日志，不能当作互不重复的 WhatsApp 登录成功/失败次数。它们足以证明失败后的恢复流程持续选中相同代理。账号 1777 与 1558 都反复选到 9235、9245，说明失败资源仍被跨账号循环使用。

当前实际链路是：

`协议报 PROXY_FAILED → 后端收不到 proxyId → 跳过失败代理隔离 → 恢复流程重新分配 → 再次选中同一失败代理 → 再次 PROXY_FAILED`

这与原设计的“失败代理置为不可用，禁止继续分配，定时检测成功后恢复”不一致。失败代理在隔离这一步就没有被正确处理，定时检测不能补上该缺口。

Android 当前失败账号的节点日志中存在大量 `proxy_connect`，支持失败发生在代理连接阶段；错误输出做了脱敏，尚不能进一步区分 DNS、TCP、认证或代理出口故障。Web 六个账号反复在 `VERIFYING` 后产生 `PROXY_FAILED/408` 或 `/428`，再用相同代理重新上线；该事件分类并不单独证明每条代理的底层网络故障类型。
