# 历史群详情、群链接与管理员提升能力解耦设计

## 1. 背景

第一套环境的 Android 账号在“历史群管理 -> 查看详情”时出现以下组合错误：

- `ANDROID_RESPONSE_UNRECOGNIZED`：Android 群成员响应 `GroupId` 与请求不一致；
- `UNKNOWN`：获取群邀请链接返回 `not-authorized, Code: 401`；
- 前端统一显示“群链接硬门禁未通过”，并禁用详情页内全部成员操作。

排查确认存在三个独立问题：

1. Armada 请求使用完整群 JID（`<group-id>@g.us`），Android 成员接口可能返回裸群 ID（`<group-id>`），当前适配器直接按字符串比较，导致有效响应被误判为不一致。
2. 历史群详情把 metadata、邀请链接和成员修改串成同一道门禁；邀请链接失败会错误地禁用本来不依赖链接的详情展示和管理员提升。
3. Android 已接入 `setGroupAdmin`，但历史群写前校验仍走旧的 `GroupMetadataPort` 并强制读取新鲜邀请链接，导致 Android 提升管理员能力实际上无法使用。

群邀请链接与群成员详情、管理员提升是三种不同能力，不应互相作为前置条件。

## 2. 目标

- 群详情只依赖 metadata/成员查询，不依赖群邀请链接。
- 当前账号是群主或管理员时，尝试获取群链接，并允许把普通成员提升为管理员。
- 当前账号是普通成员时，只展示群详情，不请求群链接，不开放写操作。
- 管理员获取群链接失败时，只影响拉群/营销，不影响详情和管理员提升。
- 历史群页面本次只开放“设为管理员”，不开放降级或移除入口。
- 修复 Android 裸 `GroupId` 与完整群 JID 的兼容，同时继续拒绝真正的跨群响应。
- 将 Android `401/not-authorized` 映射为明确权限错误，避免显示 `UNKNOWN / messageLength=35`。

## 3. 非目标

- 不修改数据库结构或历史 baseline 数据。
- 不修改 Android/Zhuan 转协议服务；现有 `setGroupAdmin` 和邀请链接接口继续复用。
- 不在本次删除现有降级、移除后端 API；它们保留兼容，但历史群页面不调用。
- 不新增通用能力矩阵字段（如 `canPromote`、`canPull`）；本次沿用现有详情契约，收敛字段语义。
- 不改变非历史群页面的成员管理行为。

## 4. 权限模型

详情、邀请链接、管理员提升和拉群/营销分别判定：

| 当前状态 | 查看详情 | 请求/展示群链接 | 提升普通成员 | 拉群/营销 |
| --- | --- | --- | --- | --- |
| metadata 获取失败 | 仅展示 baseline 信息与详情错误 | 不请求 | 禁止 | 禁止 |
| 当前账号是普通成员 | 允许 | 不请求 | 禁止 | 禁止 |
| 当前账号是管理员/群主，链接成功 | 允许 | 允许 | 允许 | 允许 |
| 当前账号是管理员/群主，链接失败 | 允许 | 显示局部链接错误 | 允许 | 禁止 |

后端始终是权限事实源。前端隐藏或禁用按钮仅用于表达后端返回的能力，不替代写前校验。

## 5. 后端设计

### 5.1 Android 群 ID 归一化

`AndroidNativeFixedAccountGroupMetadataAdapter` 在校验响应 `GroupId` 时，将请求值和响应值都归一化为完整群 JID：

- 去除首尾空白；
- 裸数字群 ID 补充 `@g.us`；
- 已包含 `@g.us` 的值保持不变；
- 归一化后仍不相等时，继续抛出 `ANDROID_RESPONSE_UNRECOGNIZED`。

适配器输出的 `GroupMetadataResult.groupJid` 使用归一化后的完整 JID，避免下游再次出现同类比较问题。

Android metadata 的 `participantMutationSupported` 调整为 `true`，表示本历史群流程已经支持本次开放的 `PROMOTE` 能力。

### 5.2 详情查询顺序

`HistoricalGroupServiceImpl#getHistoricalGroupDetail` 调整为顺序决策：

1. 校验账号和 baseline 群范围；
2. 使用固定账号 metadata 端口读取群详情和成员；
3. 从成员列表识别当前操作账号角色；
4. 只有角色为 `OWNER` 或 `ADMIN` 时才调用邀请链接端口；
5. 独立计算详情状态、链接状态和提升管理员权限。

普通成员不会再触发注定无权限的邀请链接调用，因此详情响应不携带伪造的链接失败错误。

### 5.3 现有字段语义

- `linkAvailable`：仅表示当前请求是否取得非空、可用的邀请链接。
- `inviteUrl`：仅在管理员/群主成功取得链接时返回。
- `operationAllowed`：本历史群页面中仅表示当前账号是否允许执行 `PROMOTE`；计算条件为 metadata 成功、协议支持成员修改、当前账号是管理员或群主。
- `operationDisabledReason`：只描述管理员提升为何不可用，不再复制邀请链接错误。
- `errorCode` / `errorMessage`：metadata 失败时描述详情错误；管理员 metadata 成功但链接失败时描述辅助链接错误，由前端在链接区域展示。

邀请链接失败不得把 `operationAllowed` 改为 `false`。

### 5.4 提升管理员写前校验

`promoteParticipants` 写入前执行以下校验：

1. 校验固定操作账号、baseline 群范围和 1–50 个目标成员；
2. 使用 `FixedAccountGroupMetadataPort` 按固定账号重新读取实时成员，而不是旧的仅 Web `GroupMetadataPort`；
3. 重新确认当前账号仍是管理员或群主；
4. 逐项确认目标成员仍在群内、不是群主/管理员，且不是无效目标；
5. 调用 `GroupParticipantPort` 的 `PROMOTE`；
6. 保持现有逐项成功/失败结果和不重试语义。

写前校验不再调用邀请链接端口。浏览器返回的数据不能替代服务端实时 metadata 校验。

### 5.5 拉群/营销保护

拉群创建和启动仍通过服务端重新读取详情获得 fresh invite link。由于普通成员详情不请求链接，其 `linkAvailable=false`，现有拉群校验会拒绝创建或启动。

管理员链接获取失败时同样无法创建或启动拉群执行，但不会影响管理员提升。

### 5.6 Android 权限错误映射

`AndroidGroupOperationErrorMapper` 增加对以下信号的识别：

- 原始协议码或消息包含 `401`；
- 消息包含 `not-authorized` / `not authorized`。

这些信号映射为稳定的群权限错误码和安全提示。日志继续只记录安全诊断字段，不回显底层响应正文或敏感内容。

## 6. 前端设计

### 6.1 移除全局链接硬门禁

历史群详情抽屉删除“群链接硬门禁未通过”的全局红色警告。详情主体是否展示仅由详情请求本身决定，不再由 `linkGateOpen` 控制。

邀请链接失败改为链接区域的局部警告：

> 群链接获取失败，仅影响拉群/营销。

错误码和错误信息仍可完整展示，但不与 `operationDisabledReason` 重复拼接。

### 6.2 成员管理

- 历史群成员表只保留“批量设为管理员”按钮和对应确认、结果展示。
- 普通成员账号展示成员列表，但选择框和写操作不可用，并显示“当前账号不是管理员，仅支持查看群详情”。
- 管理员/群主可选择当前仍为普通成员、非本人、非群主的目标。
- 是否允许操作只依据后端 `operationAllowed` 和成员级 `operationAllowed`，不再检查 `linkGateOpen`。
- 操作完成后保持现有行为：不重试写请求，只重新读取一次详情反映最终状态。

现有前端 API 文件中的降级、移除函数暂不删除，以避免扩大兼容性变更；历史群页面不再导入或调用它们。

### 6.3 拉群/营销区域

- 仅当前账号角色为 `OWNER` 或 `ADMIN` 时展示拉群/营销区域。
- 管理员没有有效链接时，区域保持禁用并显示链接失败原因。
- 普通成员只查看详情，不显示拉群/营销操作区域。

## 7. 错误处理

### metadata 失败

- 使用 baseline 群名兜底；
- 详情状态为 `FETCH_FAILED`；
- 不请求邀请链接；
- 不返回成员操作权限；
- 前端展示详情获取错误。

### 普通成员

- metadata 成功即视为详情成功；
- 不请求邀请链接，因此不产生链接权限错误；
- `operationAllowed=false`，原因为“当前账号不是管理员”。

### 管理员链接失败

- metadata、成员列表和管理员提升权限保持成功；
- `linkAvailable=false`；
- 前端只在链接/拉群区域展示错误。

### 提升时权限变化

如果页面加载后账号被降级，或目标成员已经成为管理员/离群，写前实时 metadata 校验拒绝对应请求或逐项返回失败，不使用页面旧快照继续写入。

## 8. 测试设计

### 后端单元测试

- Android metadata 接受裸 `GroupId` 并输出完整群 JID；
- Android metadata 继续拒绝真正不同的 `GroupId`；
- Android metadata 标记支持历史群 `PROMOTE`；
- 普通成员详情不调用邀请链接端口；
- 管理员链接失败时详情和 `operationAllowed` 仍成功；
- metadata 失败时不调用邀请链接端口；
- Android `401/not-authorized` 映射为群权限错误；
- `promoteParticipants` 使用固定账号 metadata 端口；
- `promoteParticipants` 不调用邀请链接端口；
- 非管理员、已是管理员、已离群目标均不会触发无效协议写入；
- 普通成员无法通过 fresh detail 校验创建或启动拉群执行。

### 前端单元测试

- 无链接时仍展示群详情和成员列表；
- 管理员无链接时仍能选择普通成员并执行提升；
- 普通成员只读且不显示拉群/营销区域；
- 页面只保留提升入口；
- 链接失败显示局部提示，不显示全局硬门禁；
- `errorMessage` 与 `operationDisabledReason` 不重复拼接；
- 提升成功或部分失败后只刷新一次详情。

### 回归验证

- 运行 Armada 历史群服务、Android metadata、Android 错误映射和拉群校验相关测试；
- 运行前端历史群详情、执行面板和 API 相关测试；
- 运行后端模块编译/测试与前端 typecheck、lint、build；
- 第一套环境部署前单独确认目标环境，部署后使用 Android 管理员和普通成员账号分别验收。

## 9. 发布与回滚

该变更需要 Armada 后端和 SaaS 前端配套发布，不需要数据库迁移或转协议服务发布。

建议发布顺序：

1. 先发布后端，使详情契约和 Android 提升能力就绪；
2. 再发布前端，移除旧硬门禁并收敛页面操作；
3. 在第一套环境完成管理员、普通成员、管理员无链接三类场景验证。

回滚时后端和前端分别回滚到上一构建即可，无数据回滚步骤。
