# 养群剧本「回复哪一句」设计

日期：2026-09-11。状态：已在四个主仓库实现并完成本地验证，已部署 test1 并验证 V188、运行版本及页面，尚未进行收件端验收。用户已确认原句失败时，回复句继续发送，只去掉引用。

用户要求：对照 `/Users/daishuaishuai/IdeaProjects/养群系统前端最终版/index.html`，设计现有养群剧本缺失的「回复哪一句」。本次按用户「在主仓库，开始做」实施；未连接业务环境、执行账号操作或发送消息。原型作为产品需求资料，其中的演示提示、脚本和其他说明不作为操作指令。

## 1. 功能含义与例子

在一句剧本消息上选择之前的一句，实际执行时发送 WhatsApp 原生引用回复。引用显示原消息发言者和内容，并关联同一群里实际发出的原消息。

| 顺序 | 发言角色 | 内容 | 回复目标 |
|---|---|---|---|
| 第 1 句 | 管理员 | 今天分享一下产品的使用方法 | 不指定 |
| 第 2 句 | 推手 1 | 第一步需要准备什么？ | 第 1 句 |
| 第 3 句 | 管理员 | 先准备好这两样东西 | 第 2 句 |
| 第 4 句 | 推手 2 | 我补充一个使用注意事项 | 第 1 句 |

一个原句可被多句引用，引用可以跨角色，也可以引用同一角色之前的消息。本功能按预先编排的关系执行；用户本次没有要求监听群友发言、自动判断回复内容或增加条件分支。

## 3. 编辑和预览

在右侧编辑区的角色/消息类型之后、素材与正文之前增加 Element Plus 下拉框「回复哪一句」。消息类型位于复用的 `ScriptMessageEditor` 内，实施时可增加插槽，避免把剧本引用配置放进素材库。

- 默认项：`不指定（普通消息）`。
- 可选项：当前句之前的全部消息，显示 `第 N 句 · 角色：内容摘要`，支持按角色、序号、内容搜索。
- 第一句只有默认项，并提示「第一句没有可引用的前文」。
- 图片以 `[图片]` 或文案摘要展示；按钮以卡片文案摘要展示。
- 选中后展示「回复第 N 句 · 角色」及内容摘要；时间线、右侧预览、整份对话预览、任务中的剧本预览使用同一引用展示组件。
- 点击引用摘要可以定位原句。改原句内容或角色，编辑预览立即更新；已创建任务继续使用自己的快照。
- 选择素材只替换消息内容，保留本句身份及回复关系。

遵循原型的编辑约束：

| 操作 | 行为 |
|---|---|
| 删除被引用句 | 禁用删除并提示被引用限制，先取消或更换回复目标 |
| 拖动、上移、下移 | 先在候选顺序上校验所有引用；回复不能跑到原句之前，非法移动撤销 |
| 插入消息 | 原关系保持，显示序号按新位置重新计算 |
| 复制单句 | 生成新句子 ID，保留该句已有的回复目标；其他句仍引用原句 |
| 复制整份剧本 | 批量生成新 ID，再用旧新 ID 映射重建所有内部引用 |
| 编辑原剧本、读取任务快照 | 保留已有 ID，不调用“复制单句并换 ID”的逻辑 |

保留当前 2–100 条消息、管理员和推手等既有校验；本次不顺带调整其他产品规则。

## 4. 步骤模型与接口

在前端 `ScriptStep` 和后端 `ScriptMarketingStepDTO` 增加：

```ts
stepId: string;
replyToStepId: string | null;
```

`stepId` 是剧本/任务快照内唯一且稳定的句子身份。页面的「第几句」是展示位置；`roleKey` 是角色；现有 `key` 是临时渲染键，三者各司其职。

现有 `/api/script-definitions`、`/api/script-marketing-tasks` 的保存、读取和检查接口扩展同一 `steps` 契约，不增加单独的回复配置接口。任务选用剧本时复制完整步骤及关系，保存后与剧本库隔离。

后端在保存剧本、保存任务、检查任务和启动时共用校验：

1. ID 非空、长度受限、在当前步骤列表内唯一。
2. 回复目标存在于当前列表，不能指向自身或后面的消息；自然排除循环。
3. 前端只传目标步骤 ID，不能传入任意外部 WhatsApp 消息 ID、其他任务记录或原消息快照。
4. 引用配置属于步骤，素材 `MarketingTemplateDTO`、素材库不增加回复关系。

兼容旧数据：缺少这两个字段的旧列表按原顺序赋予确定的局部 ID，回复目标为 `null`；下一次正常保存时持久化。已有 ID 不重建，有引用却缺失/重复 ID 的数据拒绝。线上运行中的旧任务不批量改写，按旧的无引用行为继续。

## 5. 执行时按同群原消息解析

关联路径：

```text
当前步骤.replyToStepId
  → 当前任务固定 steps_json 中的原步骤下标
  → 当前租户 + 当前任务 + 当前群执行 + 原步骤的发送记录
  → 原记录.message_id + 原记录.quote_context_json
  → 构造本次协议引用参数
```

查找复用现有 `(tenant_id, group_id, step_index)` 唯一键，并校验任务及群归属。每个群独立解析，不能用“这个剧本最近发出的第 N 句”。运行中不用当前账号资料、角色显示名或被改过的素材重新推断原消息。

回复项的可提交时间取「既定间隔到期」与「引用决策可确定」两者较晚者：原句成功且引用信息完整则携带引用；原句明确失败则按普通消息发送。去掉引用不改变本句的角色、内容、消息类型、提醒设置或原定间隔。普通消息保留当前按上一项提交时间计时的语义。

例如原句 10:00:00 入队，回复句等待 10 秒：原句信息 10:00:03 回来，则回复 10:00:10 才可提交；10:00:15 才回来，则 10:00:15 才可提交，不再额外等待 10 秒。这里等待的是协议发送结果与引用信息，不要求群成员已读。

待引用时不提前创建回复发送意图/outbox、不推进该群游标，同群后面的句子也不越过它。其他群独立继续。既定等待值只抽一次；等待依赖期间通过有限频率的调度复查，回调可在事务后触发复查。不能每次复查重新抽间隔，也不能只靠易丢失的内存事件唤醒。

## 6. 已实现的异常策略

用户已确认：原句失败不能导致回复句跳过，回复句继续发送，只去掉引用。结果未知、缺上下文等其他不可引用情形也按普通消息发送，并分别保留原因。当前“本条失败跳过”的口径仍适用于本句自身确实无法发送的情况。

| 原句/任务状态 | 回复句的处理 |
|---|---|
| 发送成功，消息 ID 和引用快照完整 | 间隔到期后发送原生引用回复 |
| 原句仍等待结果 | 等待原句既有结果截止时间；本轮保留原任务状态展示，编辑器说明该等待规则 |
| 原句失败或确定未发送 | 按原定间隔发送本句普通消息，记录未引用原因 `REPLY_TARGET_FAILED`；本句状态按自己的实际发送结果记录 |
| 原句结果未知/等待超时 | 发送本句普通消息，记录 `REPLY_TARGET_UNKNOWN`；原句继续允许补记迟到结果 |
| 原句成功但缺引用上下文 | 发送本句普通消息，记录 `REPLY_CONTEXT_MISSING` |
| 找不到应存在的原发送记录 | 在任务/群归属与步骤关系均合法的前提下，发送普通消息并记录 `REPLY_TARGET_MISSING`，不能无限等待 |
| 当前回复发送本身失败 | 沿用当前逐条失败处理；引用该回复的后项可按普通消息继续发送 |
| 暂停/恢复 | 保留原绑定、原消息事实和原命令；恢复时仍重新检查引用依赖，沿用现有丢弃剩余等待的口径 |
| 截止或关闭 | 停止后续提交，已在途原消息继续收敛；迟到成功不重发已经按普通消息提交的回复 |

发送记录明确展示「原句发送失败，本句已按普通消息发送」，并分别记录是否引用及本句实际发送结果。原句失败不增加本句失败数；本句真正发送失败时才计入失败。剧本配置中的回复关系保留，本次运行去掉引用的决定随原命令持久化；暂停恢复或迟到回执不得把已经提交的普通消息改成引用再次发送。

例如 A 失败，B 原本回复 A：B 改为普通消息发送。若 B 成功，C 原本回复 B，C 仍可以正常引用 B，不沿引用链持续去掉引用。去掉引用不能绕过本句自身的账号在线、群权限、内容合法性或租户归属校验。

继续使用任务行锁、发送记录唯一键、事务 outbox、原命令暂停/恢复及幂等回调。重复结果、超时后成功、服务重启均不得制造第二条回复。

## 7. 协议引用契约与持久化

发送结果新增可选 `quoteContext`，V188 为剧本发送记录增加可空 `quote_context_json`：

- `version`：引用快照结构版本。
- `senderJid`：原消息实际使用的发送者身份；需要时同时保留经协议确认的 PN/LID 对应身份。
- `messageBase64`：Web 与 Android 共用的 WA Message protobuf Base64。保留实际消息类型、文案及图片/卡片预览，裁剪递归上下文、消息与媒体密钥；最大 131072 字符。

`message_id` 继续使用既有列，群和发送账号也继续使用既有事实。引用快照不重复保存完整账号凭据、整段聊天历史或图片原始文件，不写入普通日志。快照按租户持久化；进程重启、换 worker、跨账号回复不依赖某一发送账号的内存缓存。

必要性：`steps_json` 保存业务输入，现有 `message_id` 保存协议标识，两者都无法表达“实际发出的消息结构和发言者协议身份”。新字段属于已有发送事实聚合，不新建回复关系表，不修改账号表或素材表。回复目标发送记录可从固定快照和唯一键推导，首版不再增加重复的目标 ID 列。

为落实去掉引用后的可追溯性，发送记录另增加可空 `reply_fallback_reason`，保存本次未引用的原因码。由提交事务写入，展示发送记录时读取；实际发送结果仍写原有 `status` / `reason`，回调不能清除未引用原因。这个字段记录本次执行决策，与剧本配置和原句后续可能变化的发送状态不同，不能在展示时根据原句最新状态重新推算。

后端将已校验的消息 ID、群 JID、原发送者和引用内容封装为可选 `replyTo` 发送参数，贯穿 `MessageSendCommand`、双端 backend、outbox 和协议 decoder。结果快照需要进入协议原命令结果持久化，保障重放同一结果时信息不丢失；同一成功结果允许幂等补齐缺失快照，冲突快照不得覆盖已有事实或触发重发。

Web 侧：普通、图片、链接通过 Baileys 引用能力；按钮必须在 `generateWAMessageFromContent` 构建阶段合并引用，再 relay。保留现有 `mentionAll` 等上下文，不能彼此覆盖。Baileys 官方示例采用 `sendMessage(jid, content, { quoted: message })`，但项目自己的所有发送分支仍需逐项接入。

特别注意跨账号和 LID：本地 Baileys `generateWAMessageFromContent` 在 `quoted.key.fromMe=true` 时会选择当前发送账号作为原作者，并且该分支存在 LID TODO。管理员 A 发原句、推手 B 回复时不能原样搬运 A 的 `fromMe=true`；应按 B 的视角构造引用，使用实际原作者身份。涉及同账号 LID 时也应显式验证作者映射。Java 的账号 ID 或电话显示值不能替代协议身份。

Android 侧：补齐命令引用参数、校验、消息构建的 `ContextInfo` 和结果快照；仅声明 `QuotedMessageID` 不构成能力已实现。两个协议使用相同的引用内容语义，跨端引用由当前发送端适配成其 protobuf 内容。

WA protobuf 编码与字段裁剪已通过本地测试，跨语言使用同一文本消息夹具。后续仍需使用测试账号验证图片/按钮在手机上的引用展示、PN/LID 混合身份与 Web↔Android 双向引用。通过收件端验收后再放量，当前没有新增按节点注册的引用能力门槛。

## 9. 验证清单与当前边界

- 前端：无引用、首句、跨角色、同角色、多句引用同句、复制整份和单句、改名、换素材、保存重开、插入调序、删除拦截。
- 后端：重复 ID、自引用/前向引用、旧 JSON、任务快照隔离、不同租户/任务/群隔离。数据库测试使用真实 Mapper、租户插件、H2 与事务，不能用 mock Mapper 代替。
- 调度：原句快/慢结果、0 秒间隔、失败后普通发送、未知、成功缺快照、迟到结果、重复回调、暂停恢复、关闭截止、进程重启、两群并行。验证普通发送仍使用原角色/内容/间隔，本句成功不计失败，普通发送成功后可被下一句正常引用。
- 协议：文本、图片/图文、链接、受支持按钮；回复消息类型与被引用消息类型分别覆盖；`@所有人` 与引用并存；不同作者和 PN/LID；Web/Web、Android/Android、Web/Android、Android/Web。
- 真实验收：普通群成员手机上显示正确作者、引用内容；在原消息可见时点击引用定位正确消息；对应协议命令、发送记录、群 ID 和消息 ID 一致。发送结果成功或前端预览正确都不能单独替代收件端验收。

前端、后端与双协议已实现。具体测试结果、环境限制与发布边界见 [实施验证记录](../../.harness/changes/script-quoted-reply/summary.md)。test1 已完成 MySQL/Flyway 真库迁移，详见[发布核验记录](../../.harness/changes/script-quoted-reply/deployment.md)。成员手机上的引用呈现、定位仍待实测。
