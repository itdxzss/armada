# 用多个 AI 会话执行独立验证

用户拥有充足的 Codex 使用额度。本设计不追求节省 token，而是用更多 AI 时间换取更少的人工等待、点击、日志阅读和失败整理。

多账号和多会话不被假设为自动互通的计算集群，也不用于绕过平台限制。不共享登录信息，不编写账号轮换工具。跨账号的交接媒介是固定候选版本和文件化证据，不是对话记忆。

## 车队角色

| 角色 | 责任 | 权限 | 必须交付 |
|---|---|---|---|
| 主控 | 冻结需求、生成唯一任务状态、分配工作、固定候选版本、聚类失败和裁决下一步 | 可写总状态；不可代替人做 `D2/D3` 决策 | 验收合同、版本清单、验证计划、一页结论 |
| 实现者 | 在指定仓库/worktree 实施一个边界清晰的任务并运行本地测试 | 一个 worktree 仅一个写者；不能宣布测试环境验收通过 | commit/digest、diff 摘要、测试证据、迁移和回滚 |
| 黑盒验证者 | 从干净上下文按验收合同测 UI/API/协议行为 | 默认只读；先报结论再阅读实现说明；不边测边修 | 精确步骤、`PASS/FAIL/BLOCKED/INCONCLUSIVE`、证据索引 |
| 对抗评审者 | 主动查并发、重复、乱序、超时、恢复、权限、兼容和观测盲区 | 不改实现分支 | 可复现风险、缺失测试和反例 |
| 长跑观测者 | 读取 Kafka、Redis、CPU、内存、重启、WhatsApp 流量和错误趋势 | 夜间默认只读；不擅自修复、部署或扩大动作 | 心跳、时间序列、异常簇、恢复时间和晨报 |
| 证据综合者 | 对多轮结果去重、聚类、评估完整性并生成人读结论 | 不改原始证据 | 代表性证据、失败次数、置信度和最小升级项 |

实现者和验证者必须隔离。验证者只收到需求合同、候选版本和测试资源说明，不先读实现者的“为什么这样写”，减少锨定偏差。

## 两个或三个账号的车道

### 三账号

- 账号 A：主控、需求、状态和最终裁决。主任务只保留决策和摘要。
- 账号 B：实现车道，在隔离 worktree 中实施四项目任务。
- 账号 C：质量车道，用全新任务执行黑盒验证、对抗评审和长跑观测。

### 两账号

- 账号 A：主控和实现。
- 账号 B：全部独立验证。黑盒、对抗和晨报仍使用不同新任务，不沿用实现对话。

单账号内可使用 subagents 并行读代码、跑测试和聚类日志。跨账号的主要价值是上下文独立和验证容量，不是一个共享额度池。

## 唯一事实源与交接

每个变更使用唯一 `change_id`。建议的交接结构如下，其中 `{change-id}` 和 `{run-id}` 是稳定标识符，不是人工描述：

```text
armada/.harness/changes/{change-id}/
├── 00-contract/
│   ├── acceptance-contract.yaml
│   ├── acceptance-cases.yaml
│   └── safety-envelope.yaml
├── 10-candidate/
│   ├── versions.lock
│   ├── deployment.json
│   └── rollback.md
├── 20-implementation/
│   ├── backend/
│   ├── frontend/
│   ├── web-protocol/
│   └── android-protocol/
├── 30-validation/
│   └── {run-id}/
│       ├── plan.json
│       ├── result.json
│       ├── events.ndjson
│       ├── heartbeat.json
│       └── evidence-index.json
├── 40-review/
├── 50-soak/
└── 90-decision/final.md
```

大体积日志、trace、视频和时间序列不提交到仓库，放在：

```text
_codex_artifacts/acceptance/{change-id}/{run-id}/
```

变更记录仅提交摘要、证据索引、文件哈希和可恢复命令。

写入规则：

- `acceptance-contract` 和 `versions.lock` 只由主控写入。
- 每个实现者只写自己的仓库/worktree。
- 每次验证创建新 `run-id`，证据只追加不覆盖。
- 验证者只提交 finding，不改实现分支。
- 候选版本任一 commit/image digest 改变后，旧验收自动失效。
- 任务、日志和报告仅记录测试资源别名或不可逆 token，不记密码、Token、二维码、PEM、真实联系人或消息正文。

## 不用 AI 在页面上手点一整夜

额度充足也不应消耗在重复执行脆弱的手工浏览器操作。正确的分工是：

1. AI 首次在页面探索并产生稳定 Playwright 用例。
2. 确定性 runner 用固定候选版本、资源租约和随机 seed 重复运行。
3. AI 只负责启动、读检查点、聚类失败、选代表性证据并决定是否需要增加测试。

Runner 必须：

- 每一步有 timeout，整场有 deadline。
- 每轮定期写入 `heartbeat.json` 和检查点。
- 成功、失败、取消、中断和超时都在收尾阶段生成报告。
- 长跑分为可恢复块；单个 Codex 任务超时后，新任务可从状态文件继续。
- 长跑进程由 runner/CI 存活，AI 执行可恢复轮询和结果综合，不要求一个对话窗口连续活 12 小时。

## 验证矩阵和 AI 重复策略

| 验证面 | 候选快速门禁 | 正常验证 | 高风险/夜间 |
|---|---|---|---|
| 四项目版本、构建、单测 | 固定版本全量 1 次 | 易抖用例重复 3 次 | 属性/随机测试 100～1000 seeds |
| API/事件契约 | 正常链路 1 次 | 正常、错误、幂等各 3 次 | 重复、乱序、延迟 100 次以上 |
| 前端页面 | 核心旅程冷会话 1 次 | 冷/热会话合计 5 次 | 20 次，多数据量和随机顺序 |
| 后端业务 | 核心 API 1 次 | 正常、边界、权限、重试 | 并发、突发、超时和恢复 |
| Kafka | 生产消费与 Lag | 重平衡、重复消息、恢复各 3 次 | pause、乱序、积压恢复各 10 次 |
| Redis | 连通、延迟、pending、内存 | 慢响应、过期、并发、恢复 | 隔离环境故障注入各 3 次 |
| Web/Android 协议 | 模拟链路 + 受控 canary | 重连、离线、重复事件 | 模拟器 50～500 次，6～12h 观察 |
| 资源与流量 | 开始/结束快照 | 30～60min 趋势 | 6h/12h/24h soak |

重复次数按风险自适应：

- 低风险单项目修改：1 名实现者 + 1 名独立验证者。
- 普通跨前后端变更：5 次核心旅程 + 1 名对抗评审者。
- Kafka、Redis、Web/Android 协议、账号上线和流量变更：随机/故障验证 + 6～12h soak。
- 数据迁移、资源泄漏、流量模型或重连机制：12～24h 候选观察 + 回滚演练证据。

大规模重复只打模拟器和已授权的测试环境。真实 WhatsApp 动作不随额度增加而扩大，每个协议通道通常只做 1～3 轮受控 canary。

所有随机测试保存 seed，任何失败都能用同一 seed 重放。

## 夜间长跑

长跑拆为：

1. **基线窗口**：正式动作前持续采集，证明候选版本和采集器稳定。
2. **候选窗口**：执行预定义负载和故障场景。
3. **恢复窗口**：停止负载后继续观察，判断积压是否清空、资源是否回落。

每个窗口持续采集：

- Kafka 生产/消费速率、Lag 峰值、恢复时间和重平衡。
- Redis 延迟、OPS、内存、blocked clients、Stream pending 和 slowlog 摘要。
- 实例 CPU、RSS/heap、GC、重启、OOM、连接数和错误率。
- API 吞吐、p95/p99、5xx、超时和重试。
- Web/Android 在线率、上线耗时、重连次数、断连原因和事件丢失/重复。
- Web/Android WhatsApp 上下行、业务分类、重连流量、未归因流量和采集丢弃。

自动停止条件：

- 环境或版本与 manifest 不符。
- 采集器失效或证据出现超过允许窗口的断层。
- 真实账号出现锁定、限流、异常状态或重连风暴。
- CPU、内存、Lag、错误率或流量越过已批准 abort threshold。
- 同一失败簇持续重复且不再产生新信息。
- 达到规定观察时间和置信度。

长跑观测者看到异常时只停止受控负载、保全证据、聚类和给建议，不夜间擅自修改并部署。

## 故障注入边界

隔离测试环境可自动执行：

- 前端 API 5xx、超时、登录过期、菜单/路由失败。
- 后端依赖延迟和单实例重启。
- Kafka consumer pause、重平衡、重复、乱序和积压恢复。
- Redis 延迟、短时不可用和连接恢复。
- Web/Android 协议模拟器返回锁定、限流、超时、断连和重复事件。
- 单节点重启后的恢复和积压清理。

禁止自动执行：

- 生产 kill/restart、限流或网络注入。
- 真库写入、批量修改、清库、Redis FLUSH/DEL、Kafka topic/offset 删除或重置。
- 对真实 WhatsApp 制造重连风暴、批量登录、群操作、营销或媒体发送。
- 绕过 WhatsApp 风控、锁定、限流或账号保护。
- 使用真实联系人、真实客户群或未批准的代理资源。

真实 WhatsApp 验证每次都必须引用安全信封：环境、允许账号/群、允许动作、动作数量、最大并发、最长时间、冷却期、中止条件和清理。超出信封立即 `BLOCKED`。

## 失败聚类和自动裁决

统一 reason code：

```text
ENV_UNAVAILABLE
VERSION_MISMATCH
TEST_RESOURCE_OR_AUTH
HARNESS_FAILURE
UI_FLOW
API_CONTRACT
BACKEND_LOGIC
KAFKA_LAG_OR_ORDER
REDIS_LATENCY_OR_PENDING
WEB_PROTOCOL
ANDROID_PROTOCOL
WA_EXTERNAL_OR_ACCOUNT
TRAFFIC_REGRESSION
RESOURCE_REGRESSION
OBSERVABILITY_GAP
FLAKY
UNKNOWN
```

聚类指纹由“阶段 + 项目 + test ID + 失败步骤 + endpoint/status + 异常类型/标准化栈顶 + 候选版本”组成。

自动处理：

- 同一 seed 连续两次失败：标记可复现。
- 单次瞬态失败：清理会话后最多重试两次。
- WhatsApp 锁定/限流/账号异常：不连续轰炸重试，立即停止并进入冷却。
- 关键旅程偶发失败：标记 `FLAKY` 并阻止无条件放行。
- 环境、测试工具、产品代码和外部 WhatsApp 故障分开计数。
- 每个失败簇只留一份代表性证据，附发生次数、seed 范围和首末时间。

放行规则：

- `GREEN`：候选版本固定，机器门禁通过，独立验证和对抗评审无严重问题，观测完整，资源/流量未越界。
- `RED`：有可复现产品错误、安全边界违规或明确性能/流量回归。
- `YELLOW`：证据不足、环境阻塞或验证者意见冲突。主控自动派第三个干净上下文复核。
- 第三个验证者仍无法裁决，或验收合同本身不明确时，才升级给人。

## 只升级少量问题

主控只向人升级：

- 业务语义、优先级、范围或验收标准变化。
- 是否接受剩余风险或性能/流量阈值。
- 生产、真库、远程、部署、真实 WhatsApp 动作授权。
- 不可逆迁移或回滚取舍。
- 多轮独立验证仍冲突且合同无法解释。

升级包最多三项，每项包含问题、推荐、默认不回答时的安全行为、选项后果和证据。

每天的人读摘要只包含：

```text
候选版本
总体状态：GREEN / RED / BLOCKED
置信度和证据完整度
执行轮数、seeds 和观察时间
新失败簇（最多 3 个）
Kafka / Redis / 资源关键变化
Web / Android WhatsApp 流量相对基线变化
需要人决定（0～3 项）
AI 已自动继续的下一步
```

测试失败、环境短时不可用、重复运行、日志分析、失败聚类和报告生成不应再打断人。

## 资源调度与 WIP

- 同时梳理的需求最多 2 项。
- 同时开发的业务变更最多 2 项；一个变更内可四项目并行。
- “本地完成等待测试环境”候选最多 2 个，超过后停止拉新需求。
- 一套测试环境同时只有 1 个正式候选版本。
- 每个测试 WhatsApp 账号/群同时只有 1 个租约。
- 同一环境同时只有 1 个主动故障注入或协议 canary。
- 同时只有 1 个正式长跑候选，保留 1 条隔离的 hotfix 通道。

额外 AI 并发优先用于代码探索、静态评审、日志分析、独立验证和长跑观测。候选版本冻结、部署、共享测试数据写入、同一真实账号动作、放行和回滚必须串行。

## 衡量是否真的减负

- 每项需求需要人回答的问题数是否降到 0～3 个。
- 测试是否 100% 留下明确结果，而不是超时消失。
- 失败自动归类率是否达到 80% 以上。
- 是否消除测错版本、资源冲突和证据丢失。
- `LOCAL_VERIFIED` 到测试环境结论的等待时间是否持续下降。
- 人每天阅读验收材料是否能收敛到 10～15 分钟。
- 真实 WhatsApp 主动测试是否始终位于已批准安全信封内。
- 发布后逃逸缺陷、流量回归和资源回归是否下降。

最重要的设计选择是：**让 AI 多花时间做可恢复、可重复、彼此独立的验证，而不是让人同时陪多个 AI 聊天。**
