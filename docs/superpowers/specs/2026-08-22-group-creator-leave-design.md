# 群主退群设计

## 目标

为群详情提供手动“群主退群”，并允许标准拉人任务在单群执行结束时按任务开关自动执行。两条入口复用同一套领域服务，且退群结果不改变已经完成的拉人结果。

## 已确认边界

- 判断依据只读取本地数据库。群成员、角色和账号状态由 WhatsApp 群事件持续投影，不在点击或任务收尾时调用 `groupMetadata`。
- 手动入口位于群详情抽屉底部。
- 标准任务在 `PASTED_LINK` 与 `NEW_GROUP` 两种模式下都展示“拉人完成后群主退群”开关，默认关闭，创建后冻结。
- 群主退群与群组分组、迁移没有联动，沿用现有已使用群组处理。
- 离线但账号状态正常的控端管理员/普通成员都可参与判断；在线普通成员仅在需要提升时优先。
- 不新增独立操作记录表，不额外设计防重复点击或并发锁。

## 可用账号与选择规则

当前协议账号必须是数据库快照中仍在群内且 `role=3` 的建群者，并且账号状态正常、协议在线，才能发起 WhatsApp 操作。

系统先判断是否存在另一个我方控端管理员：属于当前云控、仍在群内、账号状态正常且 `role=2`；登录离线不影响可用性。只要存在一个，就不选择接管账号、不再发提权命令，建群者直接退群。

只有不存在我方控端管理员时，才从仍在群内、账号状态正常且 `role=1` 的我方普通成员中固定选择一个。普通成员排序为：在线优先、入群时间更早优先、账号 ID 更小优先。选中后先设为管理员，成功后才允许建群者退群。

`NEW_GROUP` 自动退群优先使用任务冻结的 `PROMOTER` 账号作为建群者；`PASTED_LINK` 和手动入口从当前群成员快照中选择 `role=3` 的账号。

## 执行流程

1. 查询群、建群者和我方控端成员的本地事件投影。
2. 有我方控端管理员：直接执行建群者退群。
3. 无我方控端管理员但有普通成员：先执行 `PROMOTE`；手动 HTTP 链路以同步协议结果为准，任务链路等待 Web/Android 统一结果回调成功后再下发 `LEAVE`。
4. 不重新读取 metadata，也不要求再等一条群成员变更事件确认。
5. 无管理员和普通成员、提升失败或退群失败时返回独立结果，不回滚或重做拉人任务。

## 接口与持久化

- `GET /api/group-links/{id}/creator-leave-capability`：返回按钮是否可用及不可用原因。
- `POST /api/group-links/{id}/creator-leave`：执行手动群主退群并返回终态。
- `pull_task_standard_setting.is_creator_leave_after_pull`：任务级开关。
- `pull_task_group_execution.creator_leave_result`、`creator_leave_reason`：记录该群任务的最小执行结果。

结果编码：`0` 未执行、`1` 成功、`2` 当前账号不是建群者、`3` 建群者不可用、`4` 无控端管理员且无可提升普通成员、`5` 管理员设置失败、`6` 退群失败。

## 任务接入点

标准任务在现有单群执行进入 `CLOSING` 时生成技术动作行与 Outbox 命令。Web 账号走 master topic，Android 账号走 `protocol.android.group-action.commands.v1`；两端统一回传 `group.action_result_reported` 唤醒 `CLOSING`。开关关闭时不执行；任意退群终态只写入该群执行记录，不改变 TXT、拉人统计、任务状态或群组既有流转。

## 非目标

- 不调用 WhatsApp metadata 刷新群快照。
- 不新增退群操作历史表。
- 不新增群组分组选择或迁移逻辑。
- 不新增重试、幂等键、按钮防重复点击或跨请求并发控制。
