# 独立设计合理性复核指南

> 目标：判断当前方案是否符合用户想要的“AI 全流程干活”，并提出更合理的设计；代码和进度核验只是其中一部分
> 角色：独立产品与系统设计评审者，可以否定、删减或重构现有方案

## 开始复核

为降低被现有架构锚定的风险，必须按以下顺序进行。

### 第一阶段：从原始目标独立设计

只读取 [original-intent.md](original-intent.md)。暂时不要读取本目录其他文件，也不要查看 `staging-accept` 实现。

先独立写出：

- 你理解的用户核心预想；
- 用户未来每天应如何与 AI 协作；
- 一条需求从原始想法到真正完成的理想状态机；
- 哪些事情必须由耐久程序、AI、自动测试和人分别承担；
- 最小可行方案，以及你认为不应首期建设的内容；
- 判断体系是否成功的度量。

把这份基准保留下来，再进入第二阶段。不要事后用当前方案覆盖它。

### 第二阶段：评估当前设计

依次读取：

1. [README.md](README.md)
2. [requirements-governance.md](requirements-governance.md)
3. [staging-acceptance.md](staging-acceptance.md)
4. [ai-validation-fleet.md](ai-validation-fleet.md)
5. [implementation-backlog.md](implementation-backlog.md)
6. [acceptance-report.schema.json](acceptance-report.schema.json)

将第一阶段的独立方案与当前设计比较。重点不是“文档是否自洽”，而是：

- 当前设计是否直接服务原始目标；
- 是否把人的工作真正拿走，还是换成管理流程、配置和 agent；
- 是否存在没有收益证据的过度设计；
- 是否遗漏自动返修、接班、真实业务验收或负责人决策体验；
- 需求治理、Runner、观测、真实 WhatsApp、独立 AI 复核之间的边界是否合理；
- 是否有更简单、可渐进交付且同样可靠的替代方案。

允许给出以下任一结论：保留现有设计、局部调整、重排阶段、删除模块或重新设计。不要因为已有实现投入而回避指出方向错误。

### 第三阶段：核对当前进度

进入仓库根目录后先读取 `AGENTS.md`，再读取：

- `.harness/changes/2026-08-25-staging-accept-six-stage-validation.md`
- `armada-deploy/staging-accept/README.md`
- `armada-deploy/staging-accept/` 下的代码、计划和测试

同时检查同级的三个仓库：

- `../wheel-saas-pure-web`
- `../armada-protocol`
- `../whatsapp-server-feature-android-zhuan`

记录四个仓库的当前分支、完整 commit SHA、upstream 和工作区状态。把文档中的状态、清单和部署记录视为“待验证声明”，不能直接作为完成证据。

只运行安全、只读、本地的测试。未经用户另行授权，不部署、不 SSH、不访问真库、不操作真实 WhatsApp 账号，也不修改代码。

### 第四阶段：形成建议方案

结合原始目标、当前设计和实际进度，给出你认为下一版应该采用的方案。必须明确区分：

- 方向正确且应保留的部分；
- 方向正确但实现方式需要简化的部分；
- 与原始预想不一致的部分；
- 当前缺失但必须补齐的部分；
- 目前没有必要、应后置或删除的部分。

## 必须回答的问题

1. 用一句话复述用户真正想得到的工作方式。
2. 当前设计对原始预想的结论是 `ALIGNED`、`PARTIALLY_ALIGNED` 还是 `MISALIGNED`？
3. 当前方案最有价值的三个机制是什么？
4. 当前方案最可能增加人工或维护成本的三个机制是什么？
5. “需求决策系统 + staging-accept + AI 验证车队”的分层是否必要，边界是否正确？
6. 当前方案是否真的包含自动修复回路，还是主要停留在自动发现和报告？
7. 当前完成状态定义是否过严、过松或正好？
8. 1h/6h/24h soak、真实 WhatsApp canary 和全量观测应默认执行、按风险触发，还是后置？
9. 如果只能用三个月逐步建设，最先落地哪三个纵向切片？
10. 当前已经写出的 `staging-accept` 是合理基座、需要收缩，还是应被其他方式替代？

## 输出格式

### 结论摘要

- 原始预想：用自己的话复述。
- 总体判断：`ALIGNED` / `PARTIALLY_ALIGNED` / `MISALIGNED`。
- 最重要的理由：最多五条。

### 目标—设计追踪矩阵

| 原始目标 | 当前设计如何满足 | 证据 | 差距 | 建议 |
|---|---|---|---|---|

### 复杂度与收益

列出当前设计每个主要模块的收益、建设成本、运行成本、人工成本和是否应该首期保留。不要只讨论技术可行性。

### 建议的目标架构

给出你推荐的职责划分、状态流转和人机交互方式。与当前设计相同时也要说明为什么；不同时给出迁移路径。

### 当前进度真值表

每个工作包使用：

- `VERIFIED`：代码、测试和证据可以独立复现；
- `PARTIAL`：只有部分能力或部分证据；
- `NOT_STARTED`：实际实现不存在；
- `BLOCKED`：实现存在，但被环境、资源、授权或外部条件阻塞；
- `CLAIM_UNVERIFIED`：文档声称完成，但现有材料无法证实。

每项必须附文件路径、行号、测试命令和实际结果。

### 应保留、修改和删除

分别给出明确清单，避免只给原则性建议。

### 下一步

最多给出三个可独立验收的实施切片。每个切片说明它能减少哪一项人工工作，以及不做什么。

## 复核质量标准

- 不把“已有代码很多”当作方案正确的理由。
- 不把文档中的 checkbox、状态或测试记录当作独立证据。
- 不只找缺陷，也必须提出更合理的目标方案。
- 不把所有自动化都视为收益；必须计算新增维护和协调成本。
- 明确区分事实、推断、建议和无法验证项。
- 所有进度判断形成 Evidence → Finding → Path：证据指向发现，发现指向保留、修改或替代路径。
