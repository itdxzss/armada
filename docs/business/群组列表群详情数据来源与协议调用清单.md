# 群组列表－群详情数据来源与协议调用清单

## 1. 文档目的

本文说明“任务中心－群组列表－群组信息”抽屉中各项展示和操作的数据来源，明确区分：

- 仅查询或修改 Armada 本地数据库；
- 调用 Web/Baileys 或 Android Zhuan 协议；
- 先调用协议，再回写或异步刷新本地数据库；
- 当前协议尚未支持的操作。

梳理基线：

- Armada：`1.0.3-snapshot`
- Web 前端：`1.0.2-snapshot`
- Web/Baileys 协议层：`1.0.1-snapshot`
- Android Zhuan：`1.0.2-snapshot`
- 梳理日期：2026-08-10

## 2. 总体模型

群详情采用“本地快照展示、协议执行写操作、异步刷新快照”的模型。

```text
打开群详情
  -> Armada 查询最后一次成功的本地快照
  -> 页面展示群资料、权限、限时消息和成员

执行群设置或成员操作
  -> Armada 自动选择在线且在群的执行账号
  -> 调用对应 Web/Android 协议
  -> 必要时使用同一账号回读 WhatsApp metadata 确认
  -> 创建 metadata 异步同步任务
  -> 后台重新读取协议数据并覆盖本地快照
```

页面展示的数据不等同于打开页面时的 WhatsApp 实时数据。它表示最后一次成功同步到 Armada 的快照。

## 3. 主要本地数据表

| 表 | 作用 |
|---|---|
| `group_link` | 群链接基础数据、本地群名镜像、运营备注等 |
| `group_link_preview` | 群 metadata 快照，包括群 JID、WhatsApp 群名、成员数、邀请信息、头像、权限、限时消息等 |
| `whatsapp_group_member_snapshot` | 最后一次完整群成员快照及成员角色 |
| `group_metadata_sync_task` | 单群 metadata 异步同步任务及其状态、时间和错误信息 |

## 4. 页面操作总表

| 页面展示或操作 | 本地数据库 | 协议调用 | 结论 |
|---|---:|---:|---|
| 打开“群组信息” | 是 | 否 | 读取最后一次成功快照 |
| 群成员搜索 | 否 | 否 | 仅在前端过滤已加载成员 |
| 群成员“重新读取” | 是 | 否 | 重新读取本地快照，不读取 WhatsApp |
| 刷新群信息 | 是 | 是，异步 | 写同步任务，后台调用协议并覆盖快照 |
| 修改群备注 | 是 | 否 | Armada 本地运营备注 |
| 修改群名称 | 是 | 是 | 修改真实 WhatsApp 群名，成功后更新本地镜像 |
| 更换群头像 | 是 | 是 | 修改真实群头像，再尽力同步头像 URL |
| 修改限时消息 | 间接 | 是 | 协议写入并实时回读确认，再异步刷新快照 |
| 编辑群组设置 | 间接 | 是 | 协议写入并回读确认 |
| 发送新消息权限 | 间接 | 是 | 协议写入并回读确认 |
| 添加其他成员权限 | 间接 | 是 | 协议写入并回读确认 |
| 通过链接邀请 | 读取快照 | 当前不支持写入 | 页面禁用，协议无稳定写能力 |
| 管理员批准新成员 | 间接 | 是 | 协议写入并回读确认 |
| 设置管理员 | 间接 | 是 | 实时预检、协议提权、异步刷新快照 |
| 取消管理员 | 间接 | 是 | 实时预检、协议降权、异步刷新快照 |
| 踢出成员 | 间接 | 是 | 实时预检、协议移除、实时回读确认、异步刷新快照 |

“间接”表示操作本身不直接修改对应快照数据，而是在协议操作成功后创建异步同步任务，等待后台刷新数据库。

## 5. 详情读取

### 5.1 打开群详情

前端请求：

```http
GET /api/group-links/{id}/detail
```

该接口只读取本地数据库，不选择执行账号，也不请求协议层。返回内容包括：

- 群名称、群备注、群头像；
- 群 JID；
- 限时消息模式；
- 群权限快照；
- 最后一次完整成员快照；
- metadata 同步状态、最后成功时间和错误信息。

如果尚无成功快照，接口返回降级详情，页面显示“详情待同步”或对应失败原因。

### 5.2 群成员“重新读取”

当前“重新读取”按钮仍然调用上述详情接口，只重新加载数据库快照。

它不会：

- 实时请求 WhatsApp；
- 创建 metadata 同步任务；
- 等待后台同步完成。

因此按钮名称容易使用户误以为正在实时读取协议数据。

### 5.3 群成员搜索

搜索仅在前端对已经加载的成员数组进行过滤，不请求后端，也不调用协议。

支持按以下字段匹配：

- 昵称；
- WS 号码；
- 成员 JID。

## 6. 刷新群信息

前端请求：

```http
POST /api/group-links/{id}/metadata-sync
```

执行链路：

```text
校验群记录
  -> 新建或更新 group_metadata_sync_task
  -> 接口返回 PENDING
  -> 后台调度器领取任务
  -> 自动选择在线且在群的账号
  -> 调协议读取完整群 metadata
  -> 校验成员快照完整性
  -> 必要时使用管理员账号读取邀请码
  -> 原子更新 group_link_preview
  -> 替换 whatsapp_group_member_snapshot
  -> 同步任务改为 SUCCEEDED
```

同步内容包括：

- WhatsApp 群名和群描述；
- 成员数和完整成员列表；
- 群主、管理员和普通成员身份；
- 群头像 URL；
- 邀请码或邀请链接信息；
- 限时消息；
- 编辑、发言、加人和入群审批权限；
- 群创建时间、群主国家等派生信息。

当前前端提交同步任务后会立即重新读取一次详情。由于任务异步执行，该次读取可能仍返回旧快照。只有任务状态更新为 `SUCCEEDED` 后再次加载，才能稳定看到新数据。

## 7. 保存群资料

“保存群资料”会把群名称和群备注拆成两个相互独立的请求。

### 7.1 群名称

```http
POST /api/group-links/{id}/subject
Content-Type: application/json

{"subject":"新群名称"}
```

执行链路：

```text
校验群名称
  -> 自动选择执行账号
  -> 调协议修改真实 WhatsApp 群名称
  -> 若超时，使用同一账号回读 metadata
  -> 只有回读群名与目标一致才确认成功
  -> 更新 group_link.group_name
  -> 创建 metadata 异步刷新任务
```

群名称是“协议修改 + 本地镜像更新”。

### 7.2 群备注

```http
PATCH /api/group-links/{id}
Content-Type: application/json

{"remark":"运营备注"}
```

群备注只更新 Armada 本地数据库，不修改 WhatsApp 群描述。

## 8. 更换群头像

```http
POST /api/group-links/{id}/avatar
Content-Type: multipart/form-data
```

执行链路：

```text
校验图片类型和大小，最大 5 MiB
  -> 自动选择执行账号
  -> 图片转换为 Base64，仅发送给协议层
  -> 调协议修改真实 WhatsApp 群头像
  -> 超时时回读头像 URL 判断是否已生效
  -> 尽力更新 group_link_preview.avatar_url
  -> 创建 metadata 异步刷新任务
```

返回值区分：

- `applied`：WhatsApp 群头像是否确认应用；
- `mirrorSynced`：本地头像 URL 镜像是否同步成功；
- `avatarUrl`：协议返回或回读得到的新头像地址。

当前群资料修改端口只有 Web/Baileys HTTP 实现，没有像群设置、群成员操作一样按 Web/Android 后端路由。Android 账号场景需要单独验证群名称和头像修改能力。

## 9. 限时消息

```http
POST /api/group-links/{id}/timed-message
Content-Type: application/json

{"mode":"24h"}
```

支持四档：

- 关闭；
- 24 小时；
- 7 天；
- 90 天。

执行链路：

```text
调协议设置限时消息
  -> 使用同一账号实时回读 metadata
  -> 严格比较实际秒数与目标秒数
  -> 一致才返回成功
  -> 创建 metadata 异步刷新任务
```

后端不会在该请求内直接修改本地限时消息快照，因此写入成功和页面显示更新之间存在异步时间窗口。

## 10. 群组权限

统一请求：

```http
POST /api/group-links/{id}/settings
Content-Type: application/json

{"key":"SEND_MESSAGES","enabled":true}
```

通用执行链路：

```text
自动选择执行账号
  -> 调协议修改单项权限
  -> 使用同一账号回读 metadata
  -> 严格确认实际状态
  -> 创建 metadata 异步刷新任务
```

### 10.1 编辑群组设置

权限键：`EDIT_GROUP_SETTINGS`

- 开启：普通成员可以编辑群资料；
- 关闭：仅管理员可以编辑群资料。

### 10.2 发送新消息

权限键：`SEND_MESSAGES`

- 开启：所有成员可以发言；
- 关闭：切换为仅管理员发言模式。

该操作只修改发言权限，不发送公告文本。

### 10.3 添加其他成员

权限键：`ADD_MEMBERS`

- 开启：普通成员可以直接添加其他成员；
- 关闭：仅管理员可以添加成员。

该权限不是实际添加成员动作，也不控制邀请链接能力。

### 10.4 通过链接邀请

权限键：`INVITE_VIA_LINK`

当前不可修改：

- 本地快照不提供实时 capability 声明；
- 前端因此禁用开关；
- Web/Baileys 适配器没有对应稳定写能力；
- Android Zhuan 同样不支持。

后端禁止把该设置错误映射为“直接添加成员”或“入群审批”。

### 10.5 管理员可以批准新成员

权限键：`ADMIN_APPROVE_NEW_MEMBERS`

- 开启：新成员入群需要管理员批准；
- 关闭：关闭入群审批。

| 读取邀请信息 | 支持 | 支持 |

| 修改群头像 | 支持 | 当前需重点验证 |

## 12. 群成员操作

### 12.1 接口

设置管理员：

```http
POST /api/group-links/{id}/members/promote-batch
```

取消管理员：

```http
POST /api/group-links/{id}/members/demote-batch
```

踢出成员：

```http
POST /api/group-links/{id}/members/kick-batch
```

请求体：

```json
{
  "jids": [
    "8613800000000@s.whatsapp.net"
  ]
}
```

每次允许选择 1～50 个去重后的成员 JID。

### 12.2 通用执行链路

```text
校验成员 JID
  -> 自动选择执行账号
  -> 实时调用协议读取当前 metadata
  -> 过滤不在群内的成员
  -> 保护群主，禁止降级或踢出
  -> 调协议执行批量升权、降权或移除
  -> 超时时使用同一账号回读确认
  -> 有成功项时创建 metadata 异步刷新任务
```

### 12.3 踢出操作的额外确认

踢出操作即使收到协议 `OK`，也会再次读取 WhatsApp metadata：

- 目标成员已不在群内：确认成功；
- 目标成员仍在群内：降为 `UNKNOWN`；
- 回读失败：降为 `UNKNOWN`。

这样可以避免协议“已接收请求”但实际成员仍在群内时，页面显示假成功。

### 12.4 成员快照更新

成员操作成功后不会直接修改 `whatsapp_group_member_snapshot`。后端会创建 metadata 同步任务，等待后台读取完整成员列表后原子替换快照。

因此成员操作成功后，页面在短时间内仍可能展示旧角色或旧成员列表。

## 13. 当前已知体验和一致性问题

### 13.1 “重新读取”名称与实际行为不一致

当前行为是重新加载数据库快照，建议：

- 改名为“重新加载”；或
- 改为触发 metadata 同步，并轮询等待任务完成。

### 13.2 “刷新群信息”后可能仍显示旧数据

刷新接口只受理异步任务，前端却立即读取详情，没有等待任务完成。建议前端按以下状态轮询：

```text
PENDING -> RUNNING -> SUCCEEDED / FAILED
```

### 13.3 展示与写操作的数据源不同

```text
页面展示：数据库最后成功快照
写前校验：协议实时 metadata
写操作：协议
写后展示：等待异步快照刷新
```

该设计可以避免协议临时不可用导致详情页面完全无法打开，但会形成短暂的最终一致性窗口。

### 13.4 本地快照没有实时 capability

详情接口返回的“通过链接邀请” capability 当前固定为不支持实时声明。即使未来协议补充能力，仍需要扩展快照模型或详情读取逻辑，页面才能正确启用开关。

### 13.5 Android 群资料修改路由待完善

权限和成员操作已经按 `WEB/ANDROID` 路由，但群名称、群头像仍使用单一 Web HTTP 适配器。建议后续增加 Android 群资料 backend，并统一通过路由端口选择实现。
