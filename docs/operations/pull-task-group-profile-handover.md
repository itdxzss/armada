## 一、这是什么需求

拉群任务「新建任务」弹窗里有一整块「群信息设置」，12 个字段（设置顺序、群名、料子文件名为群名、群头像、群描述、任务后自动解除禁言、任务后自动关闭拉人权限、编辑权限、禁言、链接权限、限时消息）。

**审计发现：这 12 个字段只写不读，是个静默的假功能。** 全仓只有 Mapper、读服务回显、头像占用查询三类地方碰它，没有任何调度器或执行器消费。运营填了群名、传了头像、点保存成功，执行时一个字都不会下发给 WhatsApp。

本次做两件事：
1. 加总开关，关闭时整块不走（止损：不让运营对着不生效的字段做无用功）
2. 把群资料真正下发出去（治本）

## 三、契约（三仓一致，权威文档见 `docs/business/pull-task-group-profile-command-contract.md`）

- 命令类型 `group.profile.apply`、来源 `pull_task_group_profile`
- 关联 `PULL_TASK_ACCOUNT_ACTION` + 动作行 ID
- **留空 = 这一项别动**，线上表达是字段整个不出现（不发 null）
- 群名字段叫 `subject`（与 Baileys / 安卓一致）；原因码字面仍是 `GROUP_NAME_SET_FAILED`，有意保留不改
- 八项执行顺序（「只报第一个失败项」的定义依据）：
  群名 → 头像 → 群描述 → 禁言 → 编辑权限 → 加人权限 → 入群审批 → 限时消息
- 头像：**armada 侧转 640×640 方形 JPEG**后 base64 下发，协议两侧纯透传
- 一项失败不挡其余项；只回第一个失败项的码；失败一律 `UNKNOWN` + retryable
- 失败不阻断执行行；**只发一次，不重发**

### 几条踩出来的硬事实
- **WhatsApp 没有独立的「获取群链接权限」开关**。底层群权限只有「谁能发消息」(announcement) 和「谁能编辑群资料」(locked)，拿不拿得到邀请链接跟后者绑定。故表单那两项已合并成一项，`link_permission_mode` 列保留不用。
- 表单没有「入群审批」列，`joinApprovalEnabled` 恒空。
- **必须另起执行器，不能扩建群那条**：建群 `parsePayload` 硬判 source、correlation 形状与拉群互斥、群名只在 `autoGeneratedSubject` 时才设。
- **「不阻断执行行」与「靠卡住执行行驱动重试」互斥**，本次取前者，所以不重发。
- **拉群任务没有编辑功能**（列表只有启动/暂停/继续/结束/详情，后端无 PUT），别假设能编辑。

## 五、明确的遗留（不是 bug，是本刀没做）

1. **结果回路没接** —— `ProtocolGroupEventConsumer` 的 source 白名单里没有 `pull_task_group_profile`，协议事件也还没有「失败在哪一项」字段（`ProtocolGroupActionResultAdapter` 目前传 null）。**命令发得出去，执行结果回不来。** 这是下一刀的头号活。
2. **「任务完成后自动解除禁言 / 自动关闭拉人权限」没做** —— 这两项是任务结束时再发一次同类命令，时机不同，本刀不做。
3. **自动补发没做** —— 已决「不做」，只发一次。将来若要做：需要按动作行扫 `APPLY_GROUP_SETTINGS` + UNKNOWN 的对账任务 + 重试间隔 + 次数上限，届时才消费协议侧的 `retryable`。做之前先看主链路跑出的真实失败率。
4. **四个仓都还没 push**。共享分支 `1.0.3-snapshot`，push 前建议先过第一层验证。

## 六、给接手 agent 的提醒

- 本项目有一套「循环工程」的做法：先定断言清单 → 写成失败的测试（考卷）→ 冻结 → 跑到全绿。**考卷冻结用 `shasum` 存指纹机器验证**，不要口头保证。
- 停止条件不能用「全部测试通过」——两个仓基线本来就有红。用「本份考卷全绿 + 基线通过数一条不少」。
- 负向断言（"不该产生 X"）在实现前必然空转绿，要用差分写法（同一用例先跑正向对照再验负向）。
- 共享 checkout 里**禁止 `git add .`**，只能精确加路径。
- 前端仓的 `.codegraph/`、协议层仓的 `protocol-layer/node_modules`（是软链）都不要提交。
