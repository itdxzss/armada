## 3. 三个必须处理的陷阱

### 3.1 V118：在 perf2 上是 35 GB 表建索引，且会拖垮 test1

V118 内容：

```sql
ALTER TABLE protocol_command_outbox ADD KEY idx_..._cleanup (status, created_at)
```

test1 上 1.6 秒，因为该表只有 746,424 行。**perf2 该表 1,041 万行 / 35 GB**，占 `armada_perf` 全库 86%。

35 GB ÷ 125 MB/s = **280 秒纯顺序读的理论下限**；加排序、写索引、redo，实际 20–40 分钟，且全程压满共享 RDS。

按状态分布：

| status | 行数 | 含义 |
|---|---|---|
| 2 | **10,406,529** | 已发送（99.96%）|
| 3 | 4,229 | |
| 4 | 694 | |
| 0 | 4 | |

**处置**：先清理 `status=2` 的已发送行（见 §4.1），表缩到约 50 MB 后 V118 变秒级。这不是顺手优化，是**前置条件**。

### 3.2 V126：顺序陷阱，会让 perf2 永久残留 PN/LID 双行

V126 的作用是归并同群同号码的 PN/LID 双行，使一个 WhatsApp 人在一个群内只有一行 participant（test1 有 **56,928 组**双行）。

问题在执行时机：

```
一次性容器启动 → Flyway 按序跑 V117…V127 → 此时六表是空的 → V126 空操作
              → 回填才灌数据进去 → 灌进去的正是 PN/LID 双行
              → Flyway 已记录 V126 成功，不会再跑第二次
```

**后果**：perf2 的 `wa_group_participant` 永久残留双行，成员数虚高接近一倍，与 test1 数据形态不一致。

**处置**：回填完成后**手工重放一次 V126 的完整 SQL**（见 §5.4）。脚本自身声明幂等（`HAVING COUNT(*)=2` 归并后不再命中），重跑安全。

> V126 脚本注释里的血泪教训：
> > test1 实测未加索引时第 3 步 UPDATE 单条即运行 **47 分钟**并阻塞实时成员写入
>
> 重放时**必须整个文件执行**，含第 2.1 步的建索引，不能只挑 UPDATE 语句。

### 4.1 🔴 清理 protocol_command_outbox —— 用户已批准范围，保留期 7 天

#### 4.1.1 status 枚举（权威定义在 `V013__protocol_command_outbox.sql:17`）

```sql
status TINYINT NOT NULL DEFAULT 0
  COMMENT '状态:0=PENDING 1=LOCKED 2=SENT 3=DEAD 4=CANCELED'
```

| status | 含义 | 处置 | perf2 现状 |
|---|---|---|---|
| 0 PENDING | 待发送，在途 | 🚫 **绝对不能删** | 4 |
| 1 LOCKED | 已被 publisher 抢占，在途 | 🚫 **绝对不能删** | 0 |
| **2 SENT** | Kafka producer ack 成功，outbox 职责终结 | ✅ 删（超 7 天的）| 10,406,529 |
| 3 DEAD | 死信，重试耗尽 | 🚫 **保留**，排查证据 | 4,229 |
| 4 CANCELED | 已取消 | 🚫 **保留**，量小有诊断价值 | 694 |

> 只删 SENT，不删 CANCELED —— 与内置清理器语义严格一致。
> `ProtocolCommandOutboxCleanupScheduler` 的类注释：「死信与已取消量小且有诊断价值，不在清理范围」。

**保留期：7 天（用户 2026-08-17 拍定）**，与 `PROTOCOL_COMMAND_CLEANUP_RETENTION_DAYS` 默认值一致。

#### 4.1.2 为什么要手动删（内置清理器已开着却没生效）

核查结论：

- perf2 `.env` **没有** `PROTOCOL_COMMAND_CLEANUP_*` 配置 → 走默认 `enabled=true` / `retention-days=7` / `batch-size=10000` / 每小时一轮
- 容器自 2026-08-14 16:06 起未重启（约 60 轮清理机会）
- **近 48 小时日志中「outbox 已发送行清理完成」出现 0 次**
- 同期日志有 `DeadlockLoserDataAccessException`

根因推断（**执行者应先验证再动手**）：

```java
do {
    batch = mapper.deleteSentBefore(createdBefore, batchSize);
    deleted += batch;
} while (batch == batchSize);
if (deleted > 0) { log.info("...清理完成..."); }   // ← 在循环之后
```

1,040 万行 ÷ 每批 1 万 = **单轮要连删 1,040 批**，全部在一次 `@Scheduled` 调用内。中途任一批撞死锁 → 整轮抛异常夭折 → 永远走不到 `log.info` → 下一小时从头再来 → **净进度恒为零**。

而 V118 那个 `(status, created_at)` 索引正是为了让该清理跑得动，于是形成死循环：**没索引清理不动，表不缩小索引又建不起来。**

手动分批删是破局点：每个 `mysql -e` 是**独立事务**，撞死锁只损失当批 1 万行，下批继续。表缩小后 V118 秒建，清理器此后自动恢复正常，不会再积压。

> `deleteSentBefore` 的 SQL 已核实无额外条件（`ProtocolCommandOutboxMapper.xml:44-49`）：
> `DELETE FROM protocol_command_outbox WHERE status=#{sentStatus} AND created_at < #{createdBefore} LIMIT #{limit}`
> 现有索引 `idx_dispatch (status, next_retry_at, id)` 以 `status` 打头，删除走得到索引。

#### 4.1.3 执行

删除条件（**必须显式带 status 和时间两个条件，不要简写**）：

```sql
DELETE FROM armada_perf.protocol_command_outbox
WHERE status = 2
  AND created_at < <7天前的 epoch 毫秒>
LIMIT 10000
```

分批删，每批之间停顿，保护共享 RDS：

```bash
DBU=$(ssh -i $PERF_PEM $PERF_HOST "grep -m1 '^DB_USER=' /home/app/armada-deploy/.env | cut -d= -f2-")
DBP=$(ssh -i $PERF_PEM $PERF_HOST "grep -m1 '^DB_PASSWORD=' /home/app/armada-deploy/.env | cut -d= -f2-")

ssh -i $T1_PEM $T1_HOST "
  CUT=\$(( (\$(date +%s) - 7*86400) * 1000 ))
  echo \"保留期截止 epoch 毫秒 = \$CUT (\$(date -d @\$((CUT/1000))))\"
  for i in \$(seq 1 1200); do
    MYSQL_PWD='$DBP' mysql -h $RDS -u '$DBU' -N -e \
      \"DELETE FROM armada_perf.protocol_command_outbox
        WHERE status=2 AND created_at < \$CUT LIMIT 10000;\" \
      || { echo \"\$(date +%T) 第 \$i 批失败(可能死锁)，继续下一批\"; sleep 5; continue; }
    echo \"\$(date +%T) 已删 \$((i*10000)) 行(上限)\"
    sleep 2
  done"
```

- 单批失败（死锁）不中断整体，`continue` 到下一批即可——这正是手动删优于内置清理器之处
- 循环上限 1200 批留了余量；实际删完后 DELETE 影响行数会归零
- 收尾用 `SELECT COUNT(*) ... WHERE status=2 AND created_at < <CUT>` 确认归零。⚠️ 该 COUNT 在**索引建好前**极慢（实测超过 5 分钟未返回，且会占用共享 RDS I/O 影响 test1），建议**改为观察 DELETE 影响行数连续为 0**，不要反复跑全表 COUNT

耗时约 **30–60 分钟**。

**执行期间必须观察 test1**，任一指标异常就停下：

### 5.4 一次性回填容器

同一构建物，加 `run-once` 启动。它会先跑完 Flyway V117→V127，再执行回填，然后自行退出。

```bash
ssh -i $PERF_PEM $PERF_HOST 'docker run --rm \
  --env-file /home/app/armada-deploy/.env.backfill \
  --name armada-backfill-once \
  armada-perf-backend \
  java -jar /app/app.jar \
    --armada.group-model-backfill.run-once=true \
    --spring.kafka.listener.auto-startup=false \
    --armada.group-link-health-check.enabled=false \
  2>&1 | tee /home/app/backfill-$(date +%Y%m%d-%H%M).log'
```

`.env.backfill` = 从 `.env` 复制一份，把 §3.3 表中所有开关改成 `false`。**不要直接改 `.env`**，正常服务还要用它。

回填阶段顺序（`BackfillStage` 枚举，见 `GroupModelBackfillRunner.java`）：

```
GROUPS → PROFILES → MEMBER_SNAPSHOT_HEADERS → INVITES → CURRENT_INVITE_POINTERS
→ PROFILE_OWNERS → LEGACY_MEMBER_SNAPSHOTS → PARTICIPANTS → ACCOUNT_PARTICIPANTS
→ PARTICIPANT_JOIN_FACTS → PARTICIPANT_EXIT_FACTS → ACCOUNT_GROUP_BINDINGS
→ ACCOUNT_GROUP_SYNC_STATES
```

支持 `--armada.group-model-backfill.start-stage=<阶段>` / `--end-stage=<阶段>` 断点续跑。若中途失败，从**已提交的下一阶段**续跑，不要从头再来。

预估耗时：Flyway 约 2–3 分钟（V118 已因 §4.1 瘦身变秒级；V120–V127 作用于空表；只有 V123 动 `group_link` 9,441 行约 2 分钟）+ 回填 **5–15 分钟**。

> 回填 wall-clock 是本次**唯一没有实测依据**的估值。test1 那几次回填只留了批次数和影响行数，没留时间。perf2 的 `LEGACY_MEMBER_SNAPSHOTS` 源行 78,377 → 约 16 批（test1 是 95 批）。
> **建议**：正式跑之前，先用 `--start-stage=GROUPS --end-stage=PROFILES` 单跑最便宜的两个阶段计时，用真实吞吐反推总时长，再决定窗口。
