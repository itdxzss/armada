# 手动接码与 Go 注册三接口对接核对

日期：2026-11-05。范围：当前源码与合同核对，不执行买号、发码、验码、迁移或部署。

结论：可以复用 ARMADA 现有 Grizzly 能力对接 Go 三接口；当前尚未接通。缺少 ARMADA 的 Go 注册调用与持久化关联，且 Go 生产网络 Transport 尚为空。短信平台 API 已有实现，不需要再实现一套供应商客户端。

## 数据如何衔接

| ARMADA 数据/动作 | Go 合同/处理 |
| --- | --- |
| 取号获得 phoneNumber（已验证为不带加号的国际数字） | 规范化为显式 `+` 国际号码；与合格 `profile_id` 一起提交 code-requests |
| 一条接码记录 | 持久关联租户、操作者、activation_id、Go transaction_id、profile_id 和协议目标 |
| Go 发码响应 | 保存真实返回的 version、state、operation_id；HTTP 202 或非零 Code 不能当成功 |
| getStatus 确认 RECEIVED 的 code 字符串 | 保留前导零，使用该事务 ID、实际 expected_version 与固定验码操作键提交 code-verifications |
| WAIT_RETRY / WAIT_RESEND | 前者只含旧码，不能再次当新码提交；后者不代表查询触发了短信发送 |
| Go OUTCOME_UNKNOWN / 请求超时 | 查询原事务或同键原参重放；不换键补发、不另买号码 |
| Go REGISTERED 且结果已保存 | 才在自动注册流程中确认接码订单完成；不能把 RECEIVED 或人工 complete 当注册成功 |

请求幂等键、版本与阶段必须落库；不能只存在页面变量或进程内存。三个号码乱序收码时，按各自 activation_id 与 transaction_id 映射推进。当前 Go 仅承接指定 iOS 个人版配置，不得沿旧 Cobalt 的 accountType 入参自动开放商业注册。

## 实际缺口与建议范围

1. **ARMADA → Go 调用适配。** 需要三个方法和明确 JSON/错误映射：Go 采用 snake_case 与大写 Code/Data/Msg，带 Bearer 和 Idempotency-Key；不能把现有 Cobalt 地址直接替换。Go token 的租户/操作者归属须与 ARMADA 一致，不能用所有租户共享固定归属的 token 绕过隔离。
2. **接码订单 → 注册事务关联及推进。** 今天的手动接码是同步取号、查询时轮询，不包含无人值守任务。若要页面关闭后继续推进，需要服务端调度、阶段持久化和停止/未知处理。现有手动 create 先购买后落库，没有采购幂等意图，不能直接由自动重试器反复调用；未知采购禁止盲目再买。
3. **Go 真实网络适配。** 请求参数、ENC、token、原生会话与条件证明尚须闭合并装配 Transport；ARMADA 收码能力无法补足这一层。当前即便写好 ARMADA 调用，也会停在 Go 缺能力响应。
4. **运行入口。** Go coordinator 目前按登录/手机号路径分类，没有注册事务路由。首次对接应明确受控注册服务地址；若必须走 coordinator，需要另补事务路由，不能假设现有协议 base URL 自动兼容。

最小推进建议：先针对现有接码记录增加显式“发起 Go 注册”的受控服务端调用与关联，保留今天的人工接码行为；不把同一订单同时交给旧 Cobalt worker 和新 Go 流程。具体在已有聚合扩列还是建立独立关联，由编码前的数据模型对账确定，本轮没有决定或执行 schema 变更。

注册成功后的账号导入/上线不在这三个接口合同中；旧 Cobalt exportSix 链也不能直接作为新 Go 完整身份的交接方式。
