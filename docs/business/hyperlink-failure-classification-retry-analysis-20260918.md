# 超链失败归属、未知结果与自动补发分析

日期：2026-09-18。状态：分析建议，未修改业务代码、数据库、任务或部署。

依据：本次 perf2 任务 10/11 的只读数据与协议日志、当前 Armada / Android 协议 / 前端源码。历史运行证据与当前源码分别标注；未将本地主仓源码等同于任务执行时的完整运行制品。三个主仓当前均存在其他修改，分析没有覆盖这些修改。

## 1. 结论

“发送系统内部故障不能消耗目标数据、未知不能算失败”应采纳。但不能直接按现有错误码划分“换号重发 / 目标失败”：现有错误码丢失了发送阶段和结果确定性。

需要先判断消息是否确定没有发出，再判断故障归属。账号故障也可能发生在实际发送之后；目标会话失败也可能来自发送端数据库、映射或协议缺陷。两者不能只按错误名称决策。

三个必须修正的需求：

1. RECIPIENT_SESSION_UNAVAILABLE 不能直接判目标无效；LID_TARGET_CIPHERTEXT_MISSING 也不能。
2. SEND_FAILED 不能直接加入自动换号白名单；ACCOUNT_BANNED 若发生在发送后也不能直接换号。
3. 前端可以隐藏内部错误，但必须保留处理中、结果确认中、等待恢复/已暂停等业务状态。不能保证所有任务最终都只有成功或目标失败，更不能无限换号直至得到两者之一。

上一轮“77 个优先候选”只是人工小批次排查分组，不是可直接自动化的安全重发名单。其中 35 个 SEND_FAILED、40 个 ACCOUNT_BANNED 必须先补足发送阶段证据。

## 2. 错误实际语义

| 错误码 | 当前事实 | 建议默认归类 | 自动动作条件 |
|---|---|---|---|
| ACCOUNT_OFFLINE | 在线客户端解析失败；当前 PrepareSend 路径发生在发消息前 | 发送资源不可用 | 本次 attempt 明确未发出时重新分配可用账号；暂无资源则等待 |
| ACCOUNT_BANNED | 当前账号封禁事实；既可能发送前发现，也可能在发送失败/ACK 异常后的归因中覆盖原错误 | 账号不可用，发送结果另判 | 先停用该账号；仅确定未发送/明确拒绝时重发，其余对账 |
| SEND_PREPARE_FAILED | 多种准备错误的兜底，包含非明确类型错误、领取冲突等 | 准备/内部问题，归属未明 | 严格证明尚未执行消息写出；按具体子因恢复，不盲目换号 |
| SEND_FAILED | dispatch 错误、无 ticket 异常/panic、ACK 错误/超时的归一化出口 | 未细分，需要阶段与原始错误 | 明确拒绝后依原因决定重试；有发送可能而无确认则待确认 |
| RECIPIENT_SESSION_UNAVAILABLE | CreateSession 返回错误或设备会话集合为空 | 会话准备失败，不能断言坏数据 | 保留目标；会话修复/查询重试，受控换正常账号验证；仍无明确证据则暂停待处理 |
| LID_TARGET_CIPHERTEXT_MISSING | 本地加密结果中缺目标 LID 主设备密文，发生在 build 阶段、消息写出前 | 加密构建/路由会话问题，非目标无效证据 | 修复/刷新目标设备、映射与会话；恢复后重试；同类集中失败则暂停该路径 |
| RECIPIENT_CAPABILITY_QUERY_FAILED | 目标能力查询本身失败，没有取得注册事实 | 查询/协议问题 | 退避重查，不能转“未注册” |
| SEND_RESULT_UNKNOWN | 没有取得确定结果；某些来源是执行状态超时保护 | 结果待确认 | 对账，不生成下一次实际发送 |
| RECIPIENT_UNREGISTERED | 本地 PN 私聊校验要求 USync 注册已知、Registered=false、ContactType=out | 有明确证据的目标未注册 | 保存查询证据与时间，当前任务目标结束；不假定号码永久无效 |

“重试多次仍失败”“换几个账号仍失败”“目标设备列表空”均不是独立的目标无效证明。共享协议缺陷、共同的陈旧映射或服务端临时异常可以让全部发送账号失败。

## 3. LID_TARGET_CIPHERTEXT_MISSING 的具体含义

`internal/service/node/prepared_peer_send.go:154` 先对设备集合加密；随后检查输出 map 是否包含同时满足以下条件的条目：目标 LID 用户相同、LID 域相同、device=0、密文非空。没有则在第 166 行抛出 `build / LID_TARGET_CIPHERTEXT_MISSING`。第 168 行之后才创建消息 ID；实际 dispatch 在另一个函数中执行。

因此它表示“本次构建没有生成目标主设备的可用密文”，不是 WhatsApp 明确拒绝目标，更不是收到一条“号码无效”回执。

当前源码中存在这些能够形成该现象的路径，均需进一步证据区分：

- `app/peer_prepared_send.go:70–96` 将发送账号其他设备和目标设备合并，再创建会话；仅检查最终集合非空。可能仅剩发送者其他设备会话，尚不足以构造目标主设备密文。
- `node/node_processor.go:334–405` 的 CreateSession 会查询本地会话、补取预密钥；某个设备建会话失败会记录告警并跳过，所以可能返回部分设备集合。
- `axolotl/axolotlmanage.go:387–393` 将设备 PN 转 LID；映射失败时回退到原 JID。这样 map 中存在密文，也未必满足目标 LID 主设备检查。
- 目标预密钥响应、目标设备集合、主设备兼容规则和本地映射一致性都可能参与。不能仅凭这一错误断言某个发送账号坏了，也不能保证换号就能修复。

本次两条记录的历史协议日志确认反复发生在 prepare/build，未保留足够关联细节区分上述各子因。建议补充脱敏的目标主设备是否在输入集合、会话建成数量/目标主设备会话存在性、映射是否成功、缺失阶段；不记录私钥/会话密钥或消息正文。

## 4. RECIPIENT_SESSION_UNAVAILABLE 为何不能直接算目标失败

`app/peer_prepared_send.go:88–96` 把 CreateSession 的全部 error 和空集合包装成同一个错误。往下看：

- 会话存储读取出错会返回 error（node_processor.go:350–357）。
- 补查设备失败会返回 error（370–373）。
- 向 WhatsApp 获取用户密钥的请求失败会返回 error（387–390）。
- 创建某个设备会话失败会跳过该设备（395–400）。

所以这是一次“发送者—接收者—设备”关系的准备结果，不是目标号码自身的固有属性。首轮 17 个该类号码中确实有 1 个在第二轮成功，也已经反证该错误码不能无条件永久终结目标。

## 5. SEND_FAILED 为何必须拆分

当前 Android 超链路径至少有三个入口：

1. `internal/armada/message_sender.go:363–384`：dispatch 返回错误，超链走通用 SEND_FAILED；未把原错误和原消息 ID作为这条结果的充分结构化依据。
2. `message_sender.go:446–491`：等待 ACK 不成功，超链走通用失败归因。明确的 ServerAckError 和 ErrAckTimeout 在此没有像 contact_task 分支那样区分。
3. `consumer_account_message.go:304–322`：无 ticket 的 dispatch 错误或 panic，代码注释明确说发送副作用不确定，但结果被写成 SEND_FAILED。

`resolveFailedMessageResult` 第 550 行会先检查当前账号封禁；私聊第 553–554 行直接返回默认失败。因此“发送之后等待 ACK 出错，同时账号已封禁”也可以被归成 ACCOUNT_BANNED，原始不确定性被覆盖。

这说明“错误责任在发送账号”与“消息确定没有发出”是两个问题。不能用事后账号状态替代单条消息发送事实。

历史 35 条 SEND_FAILED 目前不能从业务库精确还原每条是拒绝、超时还是写出异常。关联日志中的 messageId 多为 Kafka topic:partition:offset，不是 WhatsApp 消息 ID。不能编造具体错误码分布，也不能仅凭 recipient.protocol_message_id=NULL 就认定未发送。

## 6. UNKNOWN 当前有确定的契约和恢复缺口

### 6.1 结果契约不一致

Android `internal/armada/message_event.go:32–65` 的结果事件没有 outcome/terminal。UNKNOWN 目前通过 success=false + reasonCode=SEND_RESULT_UNKNOWN 表达。

后端 `HyperlinkProtocolResultService.java:74–89` 只有明确 outcome=UNKNOWN 或 FAILED+terminal=false 才保留 SENDING；outcome 缺失时按 success 进入最终失败分支。该路径与本次任务中 UNKNOWN 被记作失败的事实一致。

需要版本化结果语义，兼容旧生产者，禁止把缺字段直接解释为“明确可重发失败”。不能只修 UI。

### 6.2 原 commandId 对账不是一定能查到上游最终结果

当前 `HyperlinkUnknownResultRecoveryService` 是将同一个 outbox command 重排；`ProtocolCommandOutboxServiceImpl.replay` 并没有调用一个可查 WhatsApp 最终状态的接口。

协议 Redis 状态若已保存 UNKNOWN，再重放会返回既有状态；这并不会凭空获得最终事实。若缓存过期、状态丢失，重放发送入口甚至可能重新执行，因此当前已有 29 天窗口保护，但时间窗口本身也不能证明缓存一定存在。

需要独立的无发送副作用的查询/对账接口，合并已持久化发送阶段、command/attempt/messageId 关联、server ACK、delivery/read、明确拒绝等事实。查无记录只能视为未知，不能视为未发送。

### 6.3 迟到成功不能被“旧失败”吞掉

- `message_state.go:179–201` 会把超时 PROCESSING/SENDING_OWNED 固定为 UNKNOWN；`StoreResult` 对已 RESULT_STORED/PUBLISHED 不允许更新。
- `message_executor.go:249–265` 若已有固定结果，会放弃迟到本地结果，使用 Redis 既有结果。
- `node/processor/ack.go:97–111,117–150` 在 ACK 等待器超时后仍记录迟到 ACK，但已摘除等待器不会正常交付这个 ACK。
- `HyperlinkRecipientStateMachine.java:14–15` 将最终失败锁死，后续成功/送达不会提升它。
- `resolveCurrentRecipient` 对同 recipient 的旧 command 直接忽略，适用于排除旧失败污染，但不能无差别丢掉真实迟到送达证据。

因此只把 UNKNOWN 改成 SENDING 还不完整：可能从“错误地失败”变成“永远等待”。需要单独保存、验证并合并迟到事实，验证账号、租户、消息身份与 attempt，不能简单允许任意成功覆盖任意失败。

## 7. 建议的后台决策模型

不要仅有一个 failCode。至少分开：

- 发送事实：成功 / 确定未发送 / 明确被拒绝 / 可能已发送但未确认。
- 原因归属：发送资源 / 基础设施或协议 / 消息内容或任务配置 / 已证实目标问题 / 未确定。
- 执行阶段：准备、取得执行权、可能写出、收到 server ACK、送达/已读。
- 恢复动作：同 attempt 重试准备、等待资源、新 attempt、只对账、等待配置修复、目标终结。

决策优先级：

| 事实 | 业务动作 |
|---|---|
| 原消息有可信成功或 delivery/read | 目标只成功一次；取消尚未开始的新尝试 |
| 确定未写出，属于暂时系统/资源故障 | 退避恢复，必要时重新分配账号 |
| 明确拒绝且证实属于目标 | 当前目标结束，显示目标无法发送 |
| 明确拒绝但属于账号、速率或临时服务问题 | 恢复资源/等待限制解除后再试；不能热循环换号 |
| 内容非法、素材损坏、协议构建缺陷 | 暂停任务/受影响路径等待修复；不能无限消耗发送账号 |
| 可能已经写出，无确定结果 | 只对账，不创建下一次发送 |
| 没有可用账号或重试预算耗尽 | 保留目标，等待恢复/暂停；不改成目标失败 |

新 attempt 前必须确认旧 attempt 已被明确终止且不能再次写出；仅清空业务行的 accountId/commandId 不够。必须有执行权校验、租约或等价隔离来阻止旧 worker 恢复后继续发送。单目标同时最多一个有写出资格的 attempt。

账号封禁/受限时不可再向其派发，但已在途消息逐条依据发送事实处理，不能把整个账号所有在途记录直接清空换号。

## 8. 无限补发与前端二态的边界

“直到成功或证实目标失败”可以作为服务目标，不能作为无限自动执行条件：素材/协议 Bug、所有账号不可用、上游持续故障、永久无法对账都可能让任务无法收敛。

建议设置可配置的自动恢复窗口、累计尝试预算、指数退避、同账号重复失败限制、同原因集中失败暂停。预算耗尽的结果是“暂停待恢复”，而不是“目标数据失败”。停止/取消、任务到期、没有资源和未解决 UNKNOWN 都要有独立业务状态。

前端隐藏原始 failCode、安卓设备、密钥与封禁等技术细节是合理的；普通受众列表显示业务状态，运维诊断保留权限控制的原始证据。

建议业务显示：等待发送 / 正在处理 / 结果确认中 / 已发送（附送达与已读） / 目标无法发送；任务级另显示等待资源、待修复、已暂停、已停止。自然完成时仅对已确定结果汇总成功与目标失败，但不能让进行中/待确认凭空消失。

成功口径建议沿用至少服务器 ACK 的“已发送”；双钩表示送达。如果把成功改成“必须双钩”，长时间不在线的接收者可能让任务永久等待，不能因迟迟没有双钩而自动再发。

还有遗漏的第四类：内容或任务配置导致无法发送。它不属于坏账号，也不属于坏目标。面向用户可显示“任务待修复/暂未完成”，不必暴露内部码，但必须给出可行动的业务提示。

## 9. 数据与跨模块影响

逻辑 recipient 保留一次业务结果；多次发送 attempt 分开记录。当前 recipient 只有最新 command/账号快照，换号会清掉 messageId 与 shortCode；不能将其直接扩展成通用历史账本。

优先复用 protocol_command_outbox 作为不可变命令事实；完整结果历史/attempt 信息先核查现有记录覆盖范围，不预先堆重复表。若需要新表，其唯一职责应为“单次发送尝试的不可变身份、发送阶段和结果证据”，recipient 保存当前逻辑结果及活动 attempt，避免两个地方维护同一个总状态。

需要同时调整：

- 协议：结构化错误、发送前与发送后边界、持久化 messageId、结果版本、无副作用对账、迟到 ACK/receipt。
- 后端：旧事件兼容、决策分类、恢复队列、资源等待、账号容量释放与逻辑未完成分离、attempt 互斥、成功幂等。
- 数据包：内部恢复/待确认不写入目标失败池；保留目标领取，禁止 UNKNOWN 混入“失败重置”；跨数据包历史成功排除策略应显式限定本次重试来源，不能全局禁止未来合法重复任务。
- 统计计费：目标只计一次，内部尝试另计；更新投影、失败数、账号统计、完成条件与计费冻结/结算，不提前完成任务。长期未确认的冻结资金需要单独业务口径。
- 归因：原短链和成功发送归属不能被换号直接清空；即便内部存在多个 attempt，点击 UV 与发送成功仍按逻辑 recipient 去重。
- 前端/API：业务状态与内部诊断分层；同步列表、详情、导出、数据包操作和筛选。
- 租户隔离：所有 command/attempt/messageId 对账均验证 tenant、source、recipient 和实际发送账号；不使用仅消息 ID 的跨账号全局归并。

现有 ACCOUNT_REACHOUT_RESTRICTED 已有重排逻辑，可复用部分结构，但它并不等于所有账号类失败都具备安全换号条件。

## 10. 历史 105 条处理与实施顺序

历史失败记录不能仅改 failCode 后整批补发。任务 11 的 105 条中尚无确证未注册；18 条会话失败与 2 条 LID 缺密文没有资格直接改成“目标数据失败”。35 条原生失败和 40 条封禁需依发送阶段再分；8 条未知继续隔离。

实施建议顺序：

1. 修协议结果语义和原始证据保存，使未知不再落最终失败；同时补后端旧事件保护。
2. 打通只查询的对账和迟到事实恢复，确保 UNKNOWN 能被可信成功消解且不误触发发送。
3. 完成 attempt 执行互斥，再将明确未发送的资源故障纳入自动恢复。
4. 修会话/LID 诊断与恢复，区分可修复准备错误和确证目标问题。
5. 同步统计、完成/计费、前端和导出。
6. 对现有 105 条做带来源的独立历史恢复方案，排除已成功号码；先只读演算，再做经授权的小批次验收。

部署应先使消费者兼容新旧事件，再逐步启用协议结构化结果与后台恢复，最后切换展示。回滚必须关闭新补发入口而保留 attempt/UNKNOWN/回执证据，不能回退为旧逻辑后自动重放所有待处理命令。全流程与共享的 contact_task、群营销、剧本营销路径隔离，避免改变它们的语义。

## 11. 必须验证的场景

- 发送前离线：新账号恢复，目标只成功一次。
- socket 可能已写出但 ACK 丢失：不换号，迟到成功能归并。
- ACK 超时后出现封禁：仍待确认，不能借封禁覆盖未知。
- 只有发送者其他设备会话，没有目标主设备密文：目标不能终结。
- 会话库/映射服务故障：不能出现目标未注册。
- 明确注册 type=out：当前目标可终结，保留时间与证据。
- UNKNOWN 重复回放、缓存缺失/过期：禁止变成新发送。
- 两个 worker 并发恢复、旧 worker 租约过期后恢复：最多一个有写出资格。
- 多 attempt 迟到成功、重复回执：统计、计费、UV、账号容量均不重复。
- 无账号、重试预算耗尽、内容缺陷、用户停止：正常暂停/停止，不假造目标失败。
- 部署混合版本、旧 UNKNOWN 事件、历史已失败记录：不会误重发或丢弃可信成功。
