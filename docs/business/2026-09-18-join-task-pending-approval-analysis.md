# 进群任务：待审核自动处理分析

日期：2026-09-18。范围：独立进群任务 `JoinTask`。下文保留分析时事实；用户随后授权在主仓库实施，当前实现和验证见 [实施记录](../../.harness/changes/join-task-pending-approval/summary.md)。未部署或操作真实 WhatsApp 群。

## 需求口径

- 正常发起进群，不增加进群前的审核开关检测。
- 仅实际收到 `PENDING_APPROVAL` 后，由目标群原有且有权调用的管理员关闭“管理员批准新成员”。
- 关闭成功后让本条目标账号完成入群，入群确认后接已有设置管理员流程；提权和清理仍遵守已有任务开关。
- 关闭失败或后续入群无法确认必须有明确结果与截止时间，不能无限停在待审核。
- 截图用于说明现象；不能据此推断第二套环境运行代码与本地工作区一致。

## 当前代码事实

1. `task/service/impl/JoinTaskResultServiceImpl.java:181`：待审核直接调用 `markTerminalFailure`，原因 `JOIN_PENDING_APPROVAL`，随后激活同账号下一行并刷新任务计数。截图中的“失败 / 进群待审核 / 提权未执行”与这个本地分支一致。
2. `JoinTaskAdminTransactions.pending()` 只处理进群 `SUCCESS` 的明细。`JoinTaskAdminFacts.inspect()` 会检查目标已经在群里，因此不能直接拿这整个方法处理尚未入群的申请。
3. 原群管理员候选已经具备：`GroupExecutionAccountSelector.findJoinTaskAdminCandidates` 与 `AccountGroupMembershipMapper.xml` 按同租户、同群、在线、可执行、发起人名下或共享账号筛选，排除当前进群账号。应复用候选选择，按需核实原号角色。
4. `JoinTaskServiceImpl` 目前只在开启 `setAdminEnabled` 时记录 `ownerUserId`。若新逻辑按本次要求覆盖所有进群任务，需在可信登录上下文保存任务归属；不能用空归属扩大管理员调用范围。
5. 两个协议的待审核返回都缺失群 JID：Web `protocol-layer/src/commands/group-join-executor.ts` 返回 `groupJid: null`；Android `internal/armada/join_sender.go` 的待审核结果也未设置 `GroupJID`。
6. 已有 `GroupSettingsPort.setJoinApprovalEnabled(ProtocolAccountRef, groupJid, false)`，Web / Android adapter 均支持。无需重新实现关闭开关的原生协议。
7. Web `/v1/groups/:groupJid/pending/approve`、Android `/ws/v1/groups/members/approve/:key` 已有处理指定申请的底层接口，但 Armada `platform/protocol/port` 中没有统一待审批成员查询/批准端口。
8. 当前群设置 Kafka 链路绑定拉群 `pullTaskId/groupExecutionId/actionId`。不能把进群任务 ID 填进这些字段冒用该链路。若采用异步命令，需要单独扩展来源和进群关联字段；若复用现有 HTTP 设置端口，则不需要为了关闭开关新造命令协议。
9. 前端详情将 `PENDING` 显示成待执行，原因列名是“进群失败原因”。仅后端改状态还不足以展示“正在关闭审核 / 正在完成进群”。

以上针对主仓库 `1.0.3-snapshot` 当前工作区（HEAD `6aa319cd` 加在途修改），不代表 HEAD 单独包含这些能力，也不代表已部署。

## 建议处理流程

```text
现有进群请求
  ├─ JOINED / ALREADY_JOINED → 沿用现有成功与提权流程
  ├─ FAILED → 沿用现有失败策略
  └─ PENDING_APPROVAL
       → 登记本条自动处理阶段，暂不记失败、不推进同账号下一条
       → 确认目标群 JID → 选择原群可用管理员
       → 关闭审核
       → 完成并确认本条账号入群
       → 复用进群成功写入、群关系与营销衔接
       → 按现有开关进入提权，以及已有清理/退群流程
```

### 群身份只在异常分支补齐

优先使用群域中邀请码与真实群的可靠映射；缺失时，收到待审核之后才查询邀请信息解析群 JID。该查询用于确定操作对象，不用于进群前检测审核。当前 `GroupPreviewPort` 是 Web 风格接口；Android 的邀请信息查询及统一路由需要补齐或按底层现有能力适配。不能按群名匹配，也不能拿不明归属的管理员遍历修改群。

### 关闭开关与完成入群是两个结果

现有代码只能证明关闭设置接口存在，不能证明真实 WhatsApp 在关闭后必然自动放行已经提交的申请。建议：

1. 关闭成功后，查询或接收入群事实；已在群内则直接接成功流程。
2. 若申请仍在待审列表，使用同一个原群管理员仅批准本条目标账号，不批量批准其他申请。
3. 若已确认既不在群也无待审申请，在关闭成功的前提下允许一次受控续进群，使用新的命令 ID / 尝试标识；不能拿已完成命令重投期待重新执行，也不能把待审核当普通网络错误循环重发。
4. 成员事实不足、请求超时或返回结果不明时，限时核实；到期明确结束本条，保持“结果未确认”的真实表述。

这是“当前待审核账号继续完成进群”的建议实现细化，不是已经通过真实群验证的协议结论。实际放行路径需用 Web、Android 实群各验证后确定。

### 失败回执

| 条件 | 用户回执示例 |
|---|---|
| 原号明确无管理权限 | 关闭群组审核失败：无管理员权限 |
| 明确群不存在、已解散或异常 | 关闭群组审核失败：群组状态异常 |
| 无本群可用且有权调用的原管理员 | 关闭群组审核失败：未找到可用的原群管理员 |
| 操作原号离线 | 关闭群组审核失败：管理员账号离线 |
| 群 JID 无法解析 | 关闭群组审核失败：无法确认目标群组 |
| 设置请求超时且无法核实 | 关闭群组审核结果未确认：请求超时，后续已停止 |
| 关闭成功、申请放行失败 | 审核已关闭，完成进群失败：具体原因 |
| 关闭成功、最终成员状态未知 | 审核已关闭，进群结果未确认：等待超时 |

不能将通用网络异常一律归因为无管理员权限，也不能因 HTTP 200 就判定操作成功。保留稳定原因码和可理解的中文回执；同时更新 `JoinTaskFailureReason` / VO 映射，避免新原因被现有通用标签覆盖。

## 改动范围与约束

- **后端状态机**：待审核进入可持久化的处理阶段，业务状态保持 `PENDING`。记录阶段、执行管理员、请求/尝试关联、截止时间与失败原因。复用现有调度、短事务和条件更新方式；远程调用在事务外进行，不另造全局锁或消息队列。
- **数据设计**：属于 `JoinTaskResult` 明细聚合。现有 `admin_*` 专用于入群后提权，`join_task_cleanup` 专用于清理退群，不能挪用。`command_id/attempt_no` 保留进群尝试语义；新增恢复执行状态的具体列/子记录在实现前按现有约 30 列的主表规模确定，所有必要结构变更走 Flyway，不新增群设置事实镜像。
- **计数与顺序**：自动处理中不算失败、不提前完成任务；保持同账号串行。成功后才触发群关系、营销、提权；失败终结当前明细，再按现有排期推进其他明细。
- **管理员身份**：关闭审核按原管理员的协议路由，可能与目标入群账号协议不同。关闭执行者单独留痕；不能覆盖提权的 `adminActorAccountId`，否则可能改变已有“原号退出”的对象。
- **并发**：重复回执、旧尝试迟到回执不重复推进或重复提权。同群多个申请都只处理各自目标，关闭操作保持同一目标值 false；不引入群级全局调度。跨明细已有清理行为可能让原号离群，须收敛成明确权限/可用性失败，不能无限等待。
- **API / UI**：创建接口无需新增用户开关即可实现本次自动行为；详情增加或派生自动处理阶段与原因，进群状态显示“处理中”，提权显示“等待进群成功”。新增错误按阶段展示。
- **身份兼容**：历史任务归属为空时不能替用户猜测身份；应明确失败或经现有授权编辑/重建后执行。历史已经失败的待审核明细不自动批量回放。
- **超时建议**：自动处理整体建议默认 5 分钟、可配置，沿用已有管理员阶段的时间量级；这是设计建议，未确定生产配置。明确权限/群异常立即失败，不必耗尽整个等待时间。
- **协议影响**：最小路线复用现有 HTTP 群设置端口，补齐必要的群身份解析和指定申请处理适配。若选择沿用 Kafka 全异步路线，则后端、Web、Android 三端都必须扩展独立的进群处理来源与回执；不能只改后端冒用拉群命令。

## 验证与发布边界

实现后的必要验证：正常群零额外审核调用；仅待审核触发；管理员缺失/离线/失权；群身份缺失；关闭成功但尚未入群；指定申请放行；受控续进群；重复和迟到回执；重启与超时；账号顺序、计数、租户隔离；Web/Android 与混合协议；既有提权及原号退群对象保持正确。数据库行为使用真实 Mapper 的 H2 测试，真实 WhatsApp 验收另行确认环境后进行。

本轮只做静态代码分析，没有运行实现测试，没有查询第二套环境记录或日志，因此不对截图中某条任务的远程运行事实作断言。

后续发布需固定包含现有提权/清理在途功能的准确代码基线。若新增协议契约，先发布兼容协议端；新增状态上线后，回滚旧后端前必须排空或明确终结在途自动处理记录，保留阶段与错误记录。关闭审核属于真实群设置变更，代码回滚不会自动将其打开。
