# 营销任务群组执行情况设计

## 1. 背景

「营销任务明细」当前按发送账号展示实际产生过发送记录的群组列表。群组行已经包含发送时群状态、成功累计条数、失败累计条数、最近原因和最后发送时间，但没有直接表达该群最近一轮发送是成功还是失败。

本次在每个发送账号下的群组列表新增「执行情况」。任务执行期间以该账号、该群组最新一轮已经确认的发送结果更新；任务结束后，最后一轮已经确认的发送结果作为最终执行结果。

现有「状态」字段表示发送时观察到的群健康状态（正常、封禁、没有权限、未确认），与本次「执行情况」含义不同，两个字段同时保留。

## 2. 已确认需求

- 群组执行情况只展示「发送成功」或「发送失败」。
- 最新一轮仍在发送中或被业务规则跳过时，不覆盖上一轮已经确认的成功或失败。
- 从未产生成功或失败结果的群组，执行情况显示 `-`。
- 详情抽屉打开且任务处于「执行中」时，每 5 秒刷新一次。
- 关闭抽屉、切换任务、离开页面或任务离开「执行中」状态后停止刷新。
- 任务结束时允许已经投递的最后一轮结果继续回写；结果落库后，它成为该群最终执行结果。

## 3. 范围

### 3.1 包含

- Armada 后端扩展营销任务详情群组行契约。
- 后端从现有发送尝试记录投影最新有效执行结果。
- SaaS 前端展示中文执行情况。
- 前端仅对打开的执行中任务进行 5 秒轮询。
- 后端和前端的聚焦测试及兼容性验证。

### 3.2 不包含

- 不修改协议层或 Kafka 事件。
- 不新增数据库表、列或 Flyway 迁移。
- 不修改营销任务调度、轮次生成、任务状态、计数、自动重试或账号占用规则。
- 不建设 WebSocket、SSE 或新的实时推送通道。
- 不新增群组最新结果快照表。

## 4. 方案选择

采用「查询时从发送记录计算 + 前端 5 秒轮询」。

`marketing_task_send_attempt` 已经记录任务、目标、实际群组、轮次、尝试序号和最终发送状态，是本需求的既有事实源。详情查询本身也已经按账号和实际群组聚合这些记录，因此直接扩展现有投影可以避免重复事实和双写一致性问题。

未采用以下方案：

- 群组最新结果快照表：查询更轻，但需要迁移、历史回填、并发防旧轮次覆盖和额外一致性维护，当前收益不足。
- WebSocket 或 SSE：可以即时推送，但需要新增连接、订阅、断线恢复和跨仓基础设施，明显超出本字段的实时性要求。

## 5. 后端设计

### 5.1 接口契约

保持现有接口：

```text
GET /api/marketing-tasks/{id}
```

在 `accountTargets[].groups[]` 增加可空字段：

```text
executionResult: "SUCCESS" | "FAILED" | null
```

含义如下：

| API 值 | 业务含义 | 前端文案 |
|---|---|---|
| `SUCCESS` | 最近有效轮次发送成功 | 发送成功 |
| `FAILED` | 最近有效轮次发送失败 | 发送失败 |
| `null` | 尚无成功或失败结果 | `-` |

该字段与现有 `groupStatus` 并列，禁止用 `groupStatus`、累计成功数、累计失败数或最近原因推断执行结果。

### 5.2 结果选择规则

在现有 `selectAccountGroupStatsByTaskId` 聚合中，对同一任务、账号和实际群组：

1. 仅把 `marketing_task_send_attempt.status=1` 和 `status=2` 视为有效发送结果。
2. `status=0`（已提交）和 `status=3`（已跳过）不参与执行结果选择。
3. 有效结果按 `round_no DESC, attempt_no DESC, id DESC` 排序并取第一条。
4. 第一条状态为 1 时返回 `SUCCESS`，为 2 时返回 `FAILED`。
5. 没有有效结果时返回 `null`。

必须以 `round_no` 为首要顺序，不能只按 `result_at` 或 `attempted_at`。这样即使旧轮次结果迟到，也不会覆盖已经完成的新轮次结果。`attempt_no` 和 `id` 用于同轮存在多条有效记录时稳定决胜。

### 5.3 数据流

1. 调度器照常为每轮、每个实际群组创建 attempt。
2. 协议发送结果照常把 attempt 更新为成功或失败。
3. 详情接口查询现有 attempt 历史并投影 `executionResult`。
4. 前端下一次详情请求读取新的投影值。
5. 任务进入终态后不再生成新轮次；已投递结果仍可回写，最终查询得到最后有效轮次结果。

### 5.4 数据与租户影响

- 不产生新事实，不改变现有数据归属。
- 查询继续通过任务 ID 和现有租户拦截器限制租户范围。
- 不需要历史数据迁移；历史 attempt 中已有成功或失败状态的群组可以直接计算。

## 6. 前端设计

### 6.1 类型与展示

`MarketingTaskGroupStatRow` 增加：

```text
executionResult?: "SUCCESS" | "FAILED" | null
```

群组组合列顺序调整为：

```text
状态 | 执行情况 | 单群发送条数 | 群组链接 | 群组名称 | 最近原因 | 最后发送时间
```

展示规则：

- `SUCCESS` 使用绿色标签「发送成功」。
- `FAILED` 使用红色标签「发送失败」。
- `null`、字段缺失或未知值显示 `-`。
- 账号收起状态下的第一条群组，以及展开后的每条群组，都展示执行情况。

执行结果映射放在群营销业务域的局部辅助模块中，避免在 Vue 模板里散落字符串判断。

### 6.2 轮询生命周期

1. 打开详情抽屉时立即请求一次详情，初次请求沿用现有 loading。
2. 初次或后续响应的任务状态为 2（执行中）时，确保存在一个 5 秒轮询定时器。
3. 后台轮询不启用整张详情的 loading 遮罩，避免界面周期性闪烁。
4. 后台请求成功后整体替换当前详情；响应状态不是 2 时立即停止轮询。
5. 抽屉关闭、查看其他任务或组件卸载时清理定时器并使旧请求失效。
6. 如果上一轮详情请求尚未完成，本轮定时触发直接跳过，不并发堆积。
7. 响应落地前校验当前查看的任务 ID 或请求代次，旧任务的迟到响应不得覆盖新任务详情。

轮询状态保留在现有群营销页面 composable 中，不放入 Pinia，也不让展示组件直接调用 API。

### 6.3 错误处理

- 初次详情加载失败：清空详情并显示现有可见错误提示。
- 后台刷新失败：保留最后一次成功数据，继续下一轮重试。
- 同一连续失败期间最多提示一次刷新失败；任一次刷新恢复成功后重置失败提示状态。
- 后台失败不关闭抽屉、不清空已有执行情况，也不启动额外定时器。

## 7. 兼容、发布与回滚

- 接口仅增加可空字段，属于向后兼容变更。
- 建议后端先发布：旧前端会忽略新增字段。
- 新前端连接未升级的后端时，字段缺失按 `-` 展示。
- 无数据库迁移和协议兼容窗口。
- 回滚时可独立回退前端展示/轮询和后端接口投影，不需要数据回滚。

## 8. 性能

新字段复用现有详情聚合查询，不新增额外请求接口。每个浏览器只在一个执行中详情抽屉打开时每 5 秒发起一次查询，关闭抽屉或任务离开执行中后停止，因此当前范围内不引入常驻列表轮询。

若未来单任务 attempt 历史规模导致详情查询成为实际瓶颈，再基于监控数据评估快照表；本次不预先引入冗余模型。

## 9. 测试与验证

### 9.1 后端

- 最新有效轮次成功返回 `SUCCESS`。
- 最新有效轮次失败返回 `FAILED`。
- 更新轮次仍为提交或跳过时保留上一轮有效结果。
- 旧轮次具有更晚 `result_at` 时仍不能覆盖新轮次。
- 从未有成功或失败结果时返回 `null`。
- 固定群组和账号动态群组都按账号与实际群组正确聚合。
- SQL 结构测试锁定状态过滤和 `round_no, attempt_no, id` 排序。
- 真库 DbTest 验证 MySQL 聚合结果、租户隔离和接口 VO 映射。

### 9.2 前端

- 状态映射测试覆盖「发送成功」「发送失败」和 `-`。
- 组件测试覆盖列顺序、收起行与展开行展示。
- 使用可控定时器测试每 5 秒刷新、仅执行中启动、进入终态停止。
- 测试关闭抽屉、切换任务和卸载时清理。
- 测试请求未完成时跳过下一次触发，以及旧响应不能覆盖新任务。
- 测试后台失败保留旧数据、连续失败只提示一次、成功后恢复提示能力。
- 执行前端聚焦测试、类型检查和生产构建。

## 10. 验收标准

- 营销任务明细每个实际群组都有独立「执行情况」位置。
- 最近有效轮次成功时显示绿色「发送成功」，失败时显示红色「发送失败」。
- 发送中或跳过不会擦除已确认结果；无结果显示 `-`。
- 执行中任务打开详情后最多约 5 秒看到新结果。
- 任务结束或关闭抽屉后不再产生详情轮询请求。
- 任务最后有效轮次的结果稳定作为最终执行结果，旧轮次迟到结果不会反向覆盖。
