# 拉群营销建群后立即保存群链接设计

## 背景与问题

拉群营销当前在创建 WhatsApp 群组后先执行营销账号入群、逐料入群、管理员设置和发言权限设置，直到 `SAVE_GROUP_INFO` 阶段才通过建群账号查询邀请链接。

任务 52 暴露了这个顺序的缺陷：群组已经创建并取得 `group_jid`，但建群账号在逐料阶段被封禁，执行没有机会进入 `SAVE_GROUP_INFO`，最终 `group_invite_url` 保持为空。前端只能显示“未获取群链接”，即使建群成功当时本可查询链接。

## 目标

- 群创建成功并持久化 `group_jid` 后，立即使用建群账号查询邀请链接。
- 查询成功后立即把完整邀请链接写入 `group_pull_marketing_execution.group_invite_url`。
- 首次查询失败不阻断拉料、权限和退群流程。
- 原 `SAVE_GROUP_INFO` 阶段保留为兜底：仅当执行记录仍没有链接时再次查询。
- 只有兜底查询也失败时，才把“群链接获取失败”写入执行的非致命失败原因。
- 不修改前端、协议层、数据库结构或现有任务/阶段枚举。

## 方案比较

### 方案一：建群后必须成功获取链接才能继续

优点是每个继续执行的群都有链接。缺点是协议层短暂超时也会阻断已成功创建的群，容易把非核心读取失败扩大为整群失败，不符合现有“群链接读取失败为非致命异常”的口径。

### 方案二：建群后立即尽力获取，群信息阶段兜底补取（采用）

群创建结果先按现有事务落库；随后立即查询并条件写入链接。首次失败只记录安全告警，流程继续。后续 `SAVE_GROUP_INFO` 从执行快照读取已有链接，有值时不重复调用协议；无值时执行第二次查询，并沿用现有非致命失败记录。

该方案能覆盖“建群号在后续阶段封禁”的真实问题，同时不会让瞬时网络问题阻断拉群流程，改动只落在现有 Worker、Mapper 和测试中。

### 方案三：修改协议层建群接口，使创建响应直接携带邀请链接

一次调用即可获得 JID 和链接，但需要跨后端、协议 master/worker、Android 适配器统一修改契约，发布耦合和回归面明显大于本次问题，不符合最小变更原则。

## 详细设计

### 建群成功后的立即取链

`GroupPullMarketingExecutionWorker.createGroup` 继续先调用 `saveCreatedGroup`，保证群 JID、下一阶段和营销账号额度按现有事务规则落库。只有该事务成功后，Worker 才调用新的私有辅助方法尝试获取链接。

辅助方法使用本次建群账号的 `ProtocolAccountRef` 和已确认的 `groupJid` 调用 `GroupInvitePort.getInvite`。协议适配器继续负责拒绝空链接或非法响应；Worker 不复制链接格式判断。

获取成功后，调用 Mapper 的条件更新：

- 只更新相同 execution ID 和 `group_jid` 的记录；
- 仅在 `group_invite_url` 为空时写入，保证重放和并发安全；
- 不修改执行状态、当前阶段、重试次数或调度时间；
- 不覆盖已经由其他恢复路径写入的链接。

协议查询异常或条件更新未命中时，仅输出不含完整链接、手机号或凭据的告警，并让执行继续。因为建群结果已经落库，立即取链的附加失败不能回滚或重试建群操作。

### `SAVE_GROUP_INFO` 兜底行为

进入 `SAVE_GROUP_INFO` 时，Worker 先读取 `execution.groupInviteUrl`：

- 已有非空链接：直接复用，不再次调用 `GroupInvitePort`；
- 链接为空：按现有逻辑调用 `GroupInvitePort` 补取；
- 补取失败：继续把“群链接获取失败：原因”加入非致命失败原因，并完成群入口、成员数和营销账号群关系登记。

`saveGroupInfo` 继续一次保存 `group_link_id`、最终邀请链接、成员数和非致命失败原因，不改变现有群组池登记时机。`group_link_id` 仍在完整群信息阶段生成；本次提前保存的是详情页直接使用的真实邀请 URL。

## 错误与并发语义

- 建群失败或建群结果缺少 JID：保持现有失败、重试和人工确认规则，不查询链接。
- 建群落库失败：不查询链接，沿用现有异常处理。
- 首次取链失败：不写 `failure_reason`，避免一次瞬态失败造成最终误报；仅在日志中保留 execution ID 和错误摘要。
- 首次取链成功但条件更新未命中：不覆盖数据库现值；记录告警，后续阶段仍可依据数据库状态兜底。
- 任务释放与本轮取链并发：不新增协议写操作，取链结果仅通过条件 SQL 落库；任务释放不会导致重复建群。
- `SAVE_GROUP_INFO` 兜底失败：沿用非致命失败规则，营销流程不因链接读取失败而整体失败。

## 测试设计

### Worker 单元测试

1. 建群成功后，在尚未进入 `SAVE_GROUP_INFO` 时即调用 `GroupInvitePort`，并调用 Mapper 条件保存邀请链接。
2. 首次取链抛出协议异常时，建群执行仍停留在已推进的后续阶段，不调用 `finalizer.fail`，也不写最终链接失败原因。
3. `SAVE_GROUP_INFO` 收到已有链接的执行快照时不再调用协议层，并把已有链接传给 `saveGroupInfo`。
4. `SAVE_GROUP_INFO` 收到空链接时仍执行兜底查询；查询失败时保存“群链接获取失败”的非致命原因。

### Mapper 数据库测试

1. 邀请链接为空且 execution ID、group JID 匹配时写入成功。
2. 已有邀请链接时不覆盖并返回零行。
3. group JID 不匹配时不写入。

### 回归验证

- 定向运行 `GroupPullMarketingExecutionWorkerTest` 和 `GroupPullMarketingMapperDbTest`。
- 运行拉群营销相关测试集，覆盖建群、首条料子延迟、释放收敛和最终结算。
- 运行 `mvn test`，确认整个后端测试通过。

## 不在本次范围

- 不回填已经失败的历史执行记录；历史群若需补链，应另做显式、可审计的恢复流程。
- 不改变前端“未获取群链接/链接获取失败”的文案规则。
- 不改变群组池 `wa://group/{jid}` 的内部稳定入口设计。
- 不部署到测试或生产环境；部署需要单独确认目标环境并执行部署验证。
