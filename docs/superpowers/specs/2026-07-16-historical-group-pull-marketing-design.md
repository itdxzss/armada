# Armada 历史群单群拉人及营销设计

> 状态：已确认
>
> 日期：2026-07-16
>
> 目标仓库：`armada`、`armada-protocol`、`wheel-saas-pure-web`
>
> 产品原则：一个前端菜单、baseline 全量展示、单群执行、协议错误直记、无自动重试

## 1. 背景与目标

账号首次上线后，Armada 已通过 `account_group_baseline` 保存该账号当时所在群的 JID 列表。该 baseline 原本用于把账号导入前已存在的群排除在当前营销群关系之外，不会被后续群同步覆盖，也不等同于 `account_group_membership`。

本功能把这份 baseline 作为“历史群管理”的唯一群范围。用户先选择账号分组，再选择操作账号，查看该账号全部历史群；手动刷新后判断账号当前是否仍在群、在群角色和发言状态。用户打开一个具体群时才加载完整成员、权限和邀请链接，并可在同一个页面内执行成员管理、单群拉人以及由营销账号发送模板消息。

一期目标是尽快交付可用闭环，不建设通用拉人任务平台，不接入现有营销任务列表。

## 2. 已确认业务口径

### 2.1 历史群范围

- 历史群列表只展示所选操作账号 baseline 中的全部群。
- 当前群列表中不属于 baseline 的群不进入历史群页面。
- baseline 是不可变历史范围；手动刷新只更新本次页面的当前状态，不覆盖 baseline。
- 历史群与现有群关系、营销任务保持独立。
- 所有账号号码、成员号码、群 JID 和协议错误在前端与业务接口中完整展示，不做掩码。账号凭据等不属于本功能的数据仍不得进入响应或日志。

### 2.2 单菜单与单群上下文

前端只新增一个菜单：`历史群管理`。主页面、群详情、单群拉人、执行进度和营销发送都收在该菜单内，不新增“拉人任务”或“历史群营销”等二级业务菜单。

所有拉人和营销动作只针对当前打开的一个历史群，不支持一次选择多个群。

### 2.3 拉手进群方式

- 拉手只能通过邀请链接踩进群。
- 不支持操作账号直接邀请拉手进群。
- 不允许用户手工填写或替换群链接。
- 只有群详情成功获取邀请链接时，才开放该群的成员管理、单群拉人和营销操作。
- 获取邀请链接失败时只展示历史记录及失败原因，其他操作全部禁用。

## 3. 当前事实与缺口

### 3.1 Armada 后端

当前事实：

- `account_group_baseline.baseline_group_jids` 已保存首次拍摄时的群 JID 数组。
- `AccountGroupMembershipReportServiceImpl` 在 baseline 拍摄完成后，不再用后续同步覆盖 baseline。
- `account_group_membership` 只表达账号当前群关系，并排除 baseline 群，不能直接用作历史群列表。
- 当前群详情相关在途实现已经覆盖群元数据、完整成员以及成员提升、降级和移除等能力，但普通群详情会自动选择执行账号。
- 后端没有与前端旧拉人任务壳对应的完整 `/api/pull-tasks` 业务闭环。

缺口：

- 没有按“账号分组 → 操作账号 → baseline”查询和刷新历史群的聚合接口。
- 历史群详情必须固定使用用户选择的操作账号，不能自动换执行账号。
- baseline 目前只有 JID，旧数据无法恢复账号已经退出群的名称、成员、权限或链接。
- 没有独立的历史群单群拉人执行聚合及逐号码结果记录。

### 3.2 armada-protocol

当前事实：

- 已有账号当前群列表接口。
- 已有单群 metadata、invite-code、join-by-link、联系人保存、参与者 add/promote/demote/remove 和消息发送等原子能力。
- 当前群列表的实际映射主要返回群 JID 和 subject，不能直接满足角色、发言状态和成员数量的摘要展示。

缺口：

- 轻量当前群列表只有 JID 和 subject；角色、发言状态和人数需要独立的有界批量摘要接口，且响应不能返回参与者数组。
- baseline 首次上报已经携带 subject，Armada 目前没有保存它，导致账号退出后只剩 JID。

### 3.3 wheel-saas-pure-web

当前事实：

- 已有账号分组、账号选择、群详情抽屉和营销模板等可复用组件或交互模式。
- 前端存在旧式拉人任务页面/API 壳，但后端没有对应完整业务，不适合作为本期入口。

缺口：

- 缺少独立的历史群单菜单、baseline 列表和当前状态标签。
- 缺少固定操作账号的历史群详情模式。
- 缺少单群拉人材料预览、执行进度和逐账号营销结果展示。

## 4. 方案选择

### 4.1 采用：历史群页面内的单群执行

在 `历史群管理` 中打开一个群详情，从详情内创建和查看单群拉人执行。Armada 保存最小执行记录并调用协议原子接口；前端轮询执行状态。

优点：范围与用户操作上下文一致，可复用现有群详情和协议能力，不依赖尚不存在的通用拉人后端，适合一期快速上线。

### 4.2 不采用：补齐通用拉人任务系统

现有前端壳并不代表后端能力已经存在。补齐通用任务需要额外设计多群调度、占用、任务列表、重试和统计，明显超出一期范围。

### 4.3 不采用：改造建群营销任务

建群营销以创建新群为核心，历史群拉人以加入已有群为核心，两者的群来源、执行角色和失败语义不同。强行复用会混淆领域状态。

## 5. 总体架构

```text
历史群管理（唯一菜单）
  -> Armada 历史群查询/刷新接口
     -> account_group_baseline（历史范围）
     -> armada-protocol 轻量当前群列表 + 有界批量 metadata 摘要（当前状态）
  -> Armada 历史群详情接口
     -> armada-protocol metadata + invite-code
  -> Armada 单群拉人执行
     -> 随机选择拉手
     -> armada-protocol join-by-link
     -> 联系人保存 + participants/add
  -> Armada 一次性营销发送
     -> 所有 A 账号分别发送完整模板一次
     -> 记录协议成功或错误，不重试
```

前端只调用 Armada，Armada 负责租户校验、baseline 范围校验、状态持久化和流程编排。协议层不保存 Armada 业务任务，也不新增复杂任务状态机。

## 6. 前端页面设计

### 6.1 主页面

页面顶部按顺序提供：

1. 账号分组选择器。
2. 操作账号选择器只展示已选分组内同时满足`账号状态=正常`和`登录状态=在线`的账号，完整展示账号号码、账号 ID、账号状态和登录状态。该筛选只约束历史群页面的操作账号选择，不改变账号分组总数口径或其它页面账号列表。
3. `加载群列表`按钮。

选择操作账号后立即从 Armada 读取 baseline，不调用协议。列表初始状态统一为`未验证`。

`加载群列表`属于显式协议刷新，前端仅为该请求设置 60 秒超时；全局请求仍保持 10 秒。该操作不自动重试，也不提高协议层并发；超时或其它错误继续沿用现有完整错误展示与逐群异常标记。

`当前状态`、`操作账号角色`和`发言状态`只表达本次成功刷新得到的当前事实；刷新前不使用 baseline 拍摄时的角色或禁言状态冒充当前值。baseline 摘要只作为明确标注的“导入快照”信息和群名称兜底。

列表字段：

- 群名称：优先本次刷新名称，其次 baseline 摘要名称，否则`群名称未记录`。
- 群 JID。
- 当前状态。
- 操作账号角色。
- 发言状态。
- 成员数量：优先当前刷新值；只有 baseline 有历史数量时才以`快照`标签展示旧值。
- baseline 拍摄时间。
- 本次最近加载时间。
- 详情入口。

列表只包含 baseline 群。当前群列表中新增但不在 baseline 的群不显示。

### 6.2 当前状态与分类

点击`加载群列表`后，Armada 调用所选操作账号的协议当前群摘要，并与 baseline JID 做集合对比：

- 调用成功且 JID 存在：`当前在群`。
- 调用成功且 JID 不存在：`当前不在群`。
- 整次调用失败：相关行显示`获取失败`，不能推断为不在群。

当前在群的群按操作账号身份分为：

- 管理员群组。
- 普通成员群组。

发言状态映射：

- 群未开启仅管理员发言：`正常发言`。
- 群开启仅管理员发言，且操作账号为管理员：`全员禁言，管理员可发言`。
- 群开启仅管理员发言，且操作账号为普通成员：`当前账号不可发言`。
- 协议摘要缺失、矛盾或返回群异常：`群组状态异常`。

### 6.3 群详情抽屉

只有用户打开一个群详情时，才并发加载：

- 完整成员及角色。
- 操作账号自身角色和群权限。
- 群发言/禁言配置。
- 群邀请链接。

所有协议请求固定使用页面选择的操作账号，不自动选择或切换其他账号。

详情响应分开提供 `linkAvailable` 与 `operationAllowed`：

- `linkAvailable` 只表示后端是否取得非空群邀请链接，是成员操作、单群拉人和执行营销的共同硬门禁。
- `operationAllowed` 在链接可用的基础上，再表示 metadata 与管理员权限是否允许成员管理。它不限制普通成员操作账号使用可用链接创建拉人或营销执行。

邀请链接获取失败时，抽屉保留只读信息和完整错误，成员操作、单群拉人、执行营销全部禁用。metadata 失败但链接成功时，成员管理禁用，拉人与营销仍按链接门禁执行。

### 6.4 单群拉人和执行结果

`linkAvailable=true` 且邀请链接非空时显示`单群拉人`入口。目标群和邀请链接由详情固定带入，用户不能修改链接。

弹窗包含：

- 拉手账号分组。
- 料子文件。
- 单次添加人数。
- 清洗预览：有效普通料子数、营销账号数、无效数、重复数。

同一页面展示该群最近的执行记录、总体进度、逐号码拉群结果和逐营销账号发送结果。关闭页面后重新进入仍可查询，不新增独立任务菜单。

## 7. baseline 数据设计

### 7.1 权威范围

`account_group_baseline.baseline_group_jids` 继续作为账号历史群范围的唯一权威字段。历史群刷新不得修改它，也不得把 baseline 群写入 `account_group_membership` 以制造第二套历史范围。

### 7.2 新 baseline 摘要

为了让以后新拍摄的 baseline 在账号退出群后仍保留基本名称，在 `account_group_baseline` 增加可空 JSON 字段 `baseline_group_subjects`。其内容是 JID 到拍摄时 subject 的映射，只保存协议轻量群列表已经提供的名称，不在账号首次上线时逐群调用 metadata。

`baseline_group_jids` 仍决定群是否属于 baseline；`baseline_group_subjects` 只补充静态群名，不表达当前成员关系。两个字段在首次 baseline 捕获时一次写入，之后均不可覆盖。

历史行的 `baseline_group_subjects` 为 NULL。刷新时可临时补充当前仍在群的名称和摘要，但不得反写成首次快照；当前不在群且旧 baseline 没有群名时只能展示 JID，无法反向恢复其他信息。

## 8. 协议摘要契约

协议查询分成两步。第一步继续调用现有轻量当前群列表，只返回：

- `groupJid`。
- `subject`。

Armada 先用该结果与 baseline 求交集并判定当前在群/不在群。第二步只把“当前在群且属于 baseline”的 JID 传给新增的有界批量 metadata 摘要接口。该接口逐群独立返回：

- `groupJid`。
- `success` 和 `error`。
- `subject`。
- `memberSize`。
- `selfRole`：OWNER、ADMIN、MEMBER。
- `announceOnly`。
- `stateAbnormal` 及可用错误信息。

批量摘要请求限制并发数和单次数量，单群失败不拖垮整批。协议内部为计算自身角色会读取该群 metadata，但响应不得返回参与者数组和邀请链接；完整成员、权限和邀请链接仍只由单群详情接口按需返回给页面。

首次 baseline 上报继续使用轻量群列表的 JID 和 subject，不增加逐群 metadata 请求。Armada 能兼容旧协议只上报 JID 的载荷，避免升级期间丢失 baseline。

## 9. 群详情与成员管理

### 9.1 角色权限

操作账号是管理员时：

- 可把普通成员提升为管理员。
- 可把其他管理员降为普通成员。
- 可踢出普通成员或其他管理员。
- 支持多选批量操作。

操作账号是普通成员时，只能查看详情，成员操作按钮全部禁用并提示`当前账号不是管理员`。

无论操作账号角色如何：

- 群主不能被降级或踢出。
- 操作账号本人不能被降级或踢出。
- 后端必须重复校验角色、群主和本人保护，不能只依赖前端禁用按钮。

### 9.2 批量结果

批量提升、降级和踢人使用同一个操作账号。每个成员独立返回成功或协议错误；某一成员失败不回滚成功成员，不影响后续成员，不自动重试。操作结束后重新加载群详情。

营销账号被拉入群后，用户也在此处手动多选并提升为管理员。系统不自动上管理。

## 10. 料子解析规则

复用现有 `FileLinesExtractor`，一期明确支持 TXT、CSV、Excel `.xlsx` 和 `.xls` 文件，并复用现有号码归一化规则，不新增另一套解析器。清洗后每个有效号码只保留一条：

- 普通号码：普通料子。
- 号码末尾带 `A`：营销账号；标记字符不进入实际号码。
- 同一号码同时以普通和 `A` 形式出现：营销账号身份优先。
- 重复普通行、重复营销行只保留首次有效顺序。
- 不符合号码规则的行计入无效数，不进入执行明细。

执行排序固定为全部营销账号在前、普通料子在后；各类型内部保持首次有效出现顺序。

`单次添加人数`表示一次 participants/add 请求中普通料子与营销账号的合计上限，不是每种类型分别计算。值必须大于零，并受协议接口单次参与者上限约束。

## 11. 拉人执行流程

### 11.1 创建与选取拉手

上传并解析料子后创建一条待执行记录及清洗后的号码明细，返回预览和执行编号。用户确认执行后，前端立即得到执行状态并开始轮询。

Armada 从用户选择的拉手账号分组随机选择一个满足以下条件的账号：

- 属于当前租户和指定账号分组。
- 业务状态正常。
- 当前在线。
- 有可用协议账号标识。

存量 Web 账号允许 `account.protocol_id` 为空；协议路由必须沿用
`ProtocolBackend.fromProtocolId` 的兼容语义，将空值按 `WEB` 处理。
只有手机号或 `protocol_account_id` 缺失时，才属于协议身份不完整。Web 拉手 SQL
必须使用同一口径，仅明确排除 `ANDROID`，不得因为 `protocol_id` 为空排除存量 Web 账号。

一期不检查拉手是否被其他任务占用。选中后立即写入执行记录；执行过程中不自动换拉手。

### 11.2 踩链接进群

Armada 只把群详情成功取得并固化到执行记录的邀请链接传给协议 join-by-link。没有“由操作账号邀请拉手”的分支。

- 进群成功或协议明确返回已经在群：继续。
- 进群失败：拉人状态直接失败，保存协议错误，不换号、不重试、不处理联系人。

### 11.3 保存联系人和分批添加

拉手进群成功后按营销优先顺序处理清洗后的号码：

1. 调用现有联系人保存能力。
2. 按单次添加人数切分批次。
3. 调用 participants/add 把该批号码加入目标群。

联系人保存失败时记录该号码的警告，但仍尝试 participants/add。参与者添加结果以协议返回为准：单个号码失败只记录错误，继续本批其他号码和后续批次。系统不自动重试。

拉人总体结果：

- 全部有效号码添加成功：成功。
- 至少一个成功且至少一个失败：部分成功。
- 没有号码添加成功，或前置拉手进群失败：失败。

联系人保存失败但最终添加成功时，该号码的拉人结果仍为成功，同时保留联系人警告。

## 12. 营销发送流程

拉人流程进入终态后，如果存在营销账号，用户可选择一个现有营销模板并点击发送。

发送范围固定为本次执行明细中的全部营销账号。每个营销账号完整发送所选模板一次；模板内容按现有模板顺序展开。系统不提供只选部分营销账号的入口。

发送前不调用协议检查以下条件：

- 账号是否在线。
- 账号是否实际进入目标群。
- 账号是否已被手动设为管理员。
- 账号当前是否有发言权限。

Armada 只按完整号码在当前租户查找系统账号并调用一次性消息发送能力：

- 找不到系统账号或缺少协议账号标识：本地记录失败，继续下一个营销账号。
- 协议发送成功：记录成功。
- 协议返回错误：完整记录业务可展示的协议错误，继续下一个模板内容或营销账号。
- 不自动重试任何失败消息。

同一执行记录只允许启动一次营销发送。重复提交返回已有发送状态，不能造成二次发送。若用户确需再次执行，需要新建一条单群拉人执行记录。

## 13. 持久化模型

### 13.1 `historical_group_pull_execution`

该表是历史群单群拉人聚合根，属于独立执行域，不写入现有营销任务表。主要字段：

- 租户和创建人：`tenant_id`、`created_by`。
- 目标：`operation_account_id`、`group_jid`、`group_subject_snapshot`、`invite_link`。
- 拉手：`puller_account_group_id`、`puller_account_id`。
- 配置：`single_add_count`、`marketing_template_id`。
- 清洗统计：普通数、营销数、无效数、重复数。
- 结果统计：拉人成功/失败数、发送成功/失败数。
- 独立状态：`pull_status`、`marketing_status`。
- 失败摘要：`failure_stage`、`error_code`、`error_message`。
- 时间：`started_at`、`finished_at`、`created_at`、`updated_at`。

`pull_status`：待执行、执行中、成功、部分成功、失败。

`marketing_status`：不适用、未开始、发送中、成功、部分成功、失败。

### 13.2 `historical_group_pull_member`

该表保存清洗后每个号码的唯一执行事实：

- `tenant_id`、`execution_id`、`line_no`。
- 完整 `phone`。
- `material_type`：普通或营销。
- 营销账号匹配结果：`account_id`、`protocol_account_id_snapshot`。
- 联系人保存状态及错误。
- 拉群状态及协议错误。
- 营销发送聚合状态及协议错误。
- `created_at`、`updated_at`。

同一执行内对归一化号码建立唯一约束。协议错误字段保留足够长度，但不得写入账号凭据或上传文件原始内容。

两张表都带 `tenant_id`，所有查询和更新受租户拦截器约束。账号、账号分组、模板和 baseline 必须再次校验属于当前租户。

### 13.3 异步中断

提交执行后由 Armada 后台异步处理，前端按执行编号轮询。服务启动时把上次进程遗留的“执行中/发送中”记录标记为失败，原因记录为服务中断；不自动恢复和重试。

创建和启动接口使用幂等键防止双击重复提交，但不实现跨任务账号占用锁。

## 14. Armada 接口边界

接口按以下职责拆分，最终路径遵循仓库现有 Controller 命名规范：

- 查询所选账号 baseline 历史群。
- 刷新所选账号当前群摘要并与 baseline 聚合。
- 用所选操作账号加载单群完整详情和邀请链接。
- 用所选操作账号批量提升、降级或移除成员。
- 上传材料并创建待执行记录。
- 启动单群拉人执行。
- 查询单群最近执行和执行明细。
- 选择模板并启动全部营销账号的一次性发送。

所有写接口都必须先验证目标 JID 存在于操作账号 baseline。群详情未成功获取邀请链接时，后端也拒绝成员管理、创建拉人执行和营销发送，不能只靠前端按钮禁用。

## 15. 错误处理

| 场景 | 处理 |
|---|---|
| 操作账号当前群列表调用失败 | 显示获取失败，不推断当前不在群 |
| baseline 当前不在群 | 保留历史记录；无法获取链接时所有操作禁用 |
| metadata 失败但邀请链接成功 | 展示完整业务错误；成员管理禁用，拉人与营销继续按链接门禁执行 |
| 邀请链接失败 | 展示完整业务错误；成员管理、拉人和营销全部禁用 |
| 没有可用拉手 | 拉人失败，不选择异常账号 |
| 拉手踩链接失败 | 拉人失败，不换号、不重试 |
| 单个联系人保存失败 | 记录警告，仍尝试拉群 |
| 单个号码拉群失败 | 记录协议错误，继续其余号码 |
| A 账号未录入 Armada | 该营销账号发送失败，继续其他账号 |
| 单条模板内容发送失败 | 记录协议错误，继续后续内容和账号 |
| 成员批量操作部分失败 | 逐人返回，不回滚成功项、不重试 |
| 服务执行中断 | 标记失败并记录服务中断，不自动恢复 |

## 16. 一期非目标

- 多群批量拉人。
- 通用拉人任务菜单和完整调度中心。
- 拉手或营销账号的跨任务占用检测。
- 自动换拉手。
- 自动重试。
- 自动设置营销账号为管理员。
- 营销发送前的在线、在群、管理员或发言权限检查。
- 用户手工填写或替换群链接。
- 把历史群或执行记录写入现有营销任务列表。
- 自动补齐老 baseline 已退出群的名称、成员、权限或链接。
- 新增第二个前端菜单。

## 17. 测试与验收

### 17.1 后端单测与真库测试

- baseline 全量返回，当前新增群不会混入。
- 当前群调用失败不会把 baseline 群标记为不在群。
- 当前在群/不在群、管理员/普通成员、四种发言状态映射正确。
- 新旧 baseline 载荷兼容，baseline 群名只首次写入且不可覆盖。
- 号码清洗、去重、A 优先和营销优先排序正确。
- 单次添加人数包含两类号码。
- 拉手只从指定租户和分组的在线正常账号中随机选择，不使用占用条件。
- 拉手 join 失败立即终止；联系人失败仍继续；号码添加部分失败继续。
- 所有营销账号都尝试发送一次完整模板；无前置协议检查；重复请求不二次发送。
- 成员批量操作保护群主和本人，部分失败不回滚。
- 两张执行表的租户隔离、唯一约束、状态及统计更新正确。

数据模型和 Mapper 变更必须通过 Flyway，并使用真实 MySQL DbTest 验证，不能以 H2 或 mock 替代。

### 17.2 协议层契约测试

- 当前群列表保持轻量，只返回 JID 和 subject。
- 批量 metadata 摘要只返回人数、自身角色和禁言状态，不返回完整成员；并发和逐群失败隔离有效。
- 单群详情返回真实成员、角色、权限和邀请链接。
- join-by-link、联系人保存、participants/add/promote/demote/remove 的成功与错误结构可被 Armada 稳定映射。
- 消息发送错误原样进入 Armada 业务结果，不触发协议层业务重试。

### 17.3 前端验收

- 系统只新增一个`历史群管理`菜单。
- 账号分组必须先于操作账号选择。
- 操作账号下拉只展示所选分组内账号状态正常且登录状态在线的账号，并展示账号 ID、账号状态和登录状态。
- baseline 群全部展示，账号号码、成员号码、群 JID 不脱敏。
- 列表加载、状态标签、身份分类和失败提示符合本设计。
- 只有打开单群详情才加载完整成员、权限和链接。
- 链接获取失败后所有操作入口均禁用且无手工链接输入框。
- 管理员可批量提升、降级、踢人；普通成员只能查看；群主和本人受保护。
- 单群拉人展示清洗预览、轮询进度和逐号码结果。
- 营销发送覆盖全部 A 账号并展示成功或协议错误。
- 刷新页面后仍能从同一历史群详情查看最近执行记录。

## 18. 发布与回滚

按协议层 → Armada 后端 → 前端的兼容顺序发布：

1. 协议层先兼容输出新增摘要字段，保留旧字段。
2. Armada 部署 Flyway、兼容新旧协议载荷并提供历史群接口。
3. 前端最后开放菜单。

回滚前端菜单和 Armada 接口不会删除 baseline。执行表是独立新增聚合，回滚应用时保留记录；如需回滚数据库，只能使用随变更提供的回滚脚本，并在确认目标环境和无新增执行数据后操作。任何远程、测试或生产部署均需另行确认目标环境。

## 19. 事实、推断与未确认项

### 已确认事实

- 用户已逐项确认本设计中的菜单、baseline、详情懒加载、链接门禁、单群拉人、A 标记、全部营销账号发送、成员管理、无预检、无重试和一期非目标。
- 当前 baseline 只有群 JID，因此老账号已经退出的群无法通过协议恢复详情或链接。
- 当前仓库存在群详情三仓在途修改，实施时必须在其基础上集成，不能覆盖或重做用户已有改动。

### 技术推断

- 保持轻量当前群列表，再只对 baseline 交集有界批量读取 metadata，比对全部当前群逐群加载详情更适合账号级刷新；单群详情仍使用 metadata 获取完整参与者。
- 单群执行独立建模比补齐通用拉人任务或复用建群营销更符合一期语义和上线速度。

### 未确认项

需求口径已经闭合，无阻塞实施计划的产品未确认项。具体 REST 路径、Flyway 版本号和类名由实施计划基于落地时当前代码确定，不改变本文业务契约。
