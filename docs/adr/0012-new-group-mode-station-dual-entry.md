# ADR-0012：站台两种进群方式并存，拉人执行阶段不改动

日期：2026-08-18
状态：已接受

## 背景

ADR-0006 第 5、6、9 条确定了群链接模式的站台语义：每一次单次拉人调用从站台分组选择「每次拉站台数量」个站台，由该次调用的拉手与料子同批加入；站台可跨群链接复用，但同一群链接内只加入一次。

新群模式的业务流程另有一种站台进群方式：站台在建群调用中作为初始成员一次性进群。

业务确认这两种方式**并存**，同一个任务里可能两种都需要，不是二选一。

## 决定

1. 两种站台进群方式并存：
   - **建群时进群**：站台作为初始成员随建群调用一次性加入。
   - **拉人时进群**：由拉手在每次拉人调用中与料子同批加入，沿用 ADR-0006 既有语义，不做任何修改。
2. `PullTaskAccountEntryMode` 追加取值 `4=建群时作为初始成员加入`。现有 `1=JOIN_BY_LINK`、`2=MANAGER_INVITE`、`3=PULLER_ADD` 语义与取值不变。
3. 建群成功后，初始站台必须落成本执行行的站台角色行：`role_type=3`、`entry_mode=4`、`membership_status=IN_GROUP`。
4. **`PULL_EXECUTION` 阶段与站台选号逻辑零改动。**
5. 创建任务时的资源校验必须同时计入「建群初始站台数」与「每次拉站台数量」两笔需求，不能只校验后者。

## 影响

- 第 3、4 条能同时成立，是因为 `PullTaskStationSelectionService.findCandidates` 已经把本执行行全部 `role_type=STATION` 角色行收进 `usedAccountIds` 并排除，且 `reusableStation` 要求 `membership_status = NOT_JOINED` 才允许复用。落成 `IN_GROUP` 的初始站台既不会被首次选中，也不会被当作可复用站台重新提交，因此不会在同群内重复入群。**实现时必须保证初始站台写入的 `membership_status` 是 `IN_GROUP`，写成 `NOT_JOINED` 会让它们被拉人调用重新选中并重复提交。**
- 枚举追加与 V102 增加 `role_type=4`、V119 增加 `action_type=5/6` 是同一模式：纯追加，现有取值不变，迁移只改列注释。
- 两种站台**共用同一个站台分组**。建群时占用的账号会减少后续拉人调用的可选站台。站台分组偏小时，执行行会进入既有的「等待站台」资源等待，这是资源机制正常工作而非缺陷；但创建任务时若不做双笔校验，用户会在配置阶段看不出问题、启动后才卡住。
- 建群时初始站台的加入结果由建群协议回执逐成员给出，与拉人调用的站台结果口径不同，统计和明细展示需要能区分两种来源，不能混为一次「站台入群失败」。

## 被否决方案

- **只保留拉人时进群**：与业务确认的场景不符，无法支持建群即需要站台在群内的情况。
- **只保留建群时进群**：会让 `PULL_EXECUTION` 阶段的站台分支失效，需要改动拉群测试覆盖最密的一段，且与 ADR-0006 已上线语义冲突。
- **两种方式在创建任务时二选一**：业务已明确同一任务可能两种都要。
