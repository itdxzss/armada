# 账号批量登录与批量离线设计

## 1. 背景与目标

账号列表当前只支持把当前页勾选账号的 ID 提交给批量上线、批量下线接口。未勾选账号时，前端提示必须选择数据；列表刷新又始终直接读取正在编辑的筛选表单，无法区分“用户刚修改但尚未查询的条件”和“当前列表实际使用的条件”。

本次改造实现以下目标：

1. 批量操作名称统一为“批量登录”“批量离线”。单行操作继续使用现有“上线”“下线”语义。
2. 有勾选账号时，只处理所选账号。
3. 未勾选账号时，按当前列表最后一次成功查询所使用的筛选条件处理全部匹配账号；空筛选条件代表当前租户全部账号。
4. 批量目标由 Armada 后端查询，不能由前端遍历当前页或分页收集 ID。
5. 执行前由后端预估匹配数、可执行数和跳过数，前端展示二次确认。
6. 保留已有 ID 批量接口并把单次接收上限提高到 2,000；后端内部仍使用安全的小批次执行。

本次不修改协议层的在线幂等判断，不新增异步批量任务表，不扩展迁移分组、删除、一键抢登等其它批量操作。

## 2. 已确认的业务规则

### 2.1 操作范围优先级

1. 当前存在勾选账号：操作范围固定为勾选 ID，不叠加列表筛选条件。
2. 当前没有勾选账号：操作范围为前端保存的已生效筛选条件。
3. 已生效筛选条件为空：操作范围为当前租户全部未软删账号。

### 2.2 批量登录跳过规则

Armada 后端在执行批量登录前跳过：

- 封禁账号，`account_state = 3`；
- 解绑账号，`account_state = 5`；
- 抢登中账号，`account_state = 7`；
- 缺少有效账号凭据的账号。

已在线账号不跳过，仍写入协议上线命令；协议层继续使用现有在线判断决定不重复执行。

批量离线不套用上述登录跳过规则。它对操作范围内的账号下发离线命令，且不要求账号凭据。

### 2.3 容量与分片

- 现有 ID 接口单次最多接收 2,000 个账号，2,001 个及以上按参数错误拒绝。
- 按查询条件执行的接口不限制总匹配数。
- 批量登录内部每 500 个可执行账号一批，保留代理分配短事务的现有安全边界。
- 批量离线内部每 1,000 个账号一批。
- 外部请求的总量与内部事务、outbox 批次容量是两个独立概念，不把代理分配单事务扩大到 2,000。

### 2.4 分片失败

各内部批次独立执行。某批失败时回滚该批，记录该批失败数量和摘要，后续批次继续处理。接口最终返回全部批次的汇总结果。

请求参数非法、筛选查询本身失败或无法建立批量执行上下文时，接口整体失败；进入分片执行后的局部业务或基础设施异常则进入汇总结果，避免前面已经受理的命令被误报为整体未执行。

## 3. 方案选择

### 3.1 采用方案：ID 与查询条件使用独立执行接口

保留现有 ID 接口供已勾选场景使用，新增按查询条件执行接口供未勾选场景使用。两种入口进入同一个后端批量编排服务，统一做目标解析、登录跳过、分片执行和结果汇总。

该方案保持现有调用方兼容，并避免把空 ID 隐式解释为“全部账号”。

### 3.2 未采用方案

- 在同一个执行请求中同时支持可空 `ids` 和可空 `query`：接口数量较少，但参数缺失可能意外放大操作范围。
- 前端分页查询全部账号 ID 后调用旧接口：存在分页数据漂移，也违反“以后端查询条件为准”的要求。
- 本次直接建设持久化异步批量任务：能承载超大规模任务和进度查询，但当前需求只要求命令批量入 outbox，现阶段会引入不必要的任务表、调度器和进度页面。

## 4. 后端接口设计

### 4.1 已勾选账号：保留现有接口

```text
POST /api/accounts/batch-online
POST /api/accounts/batch-offline
```

账号列表前端继续发送：

```json
{
  "ids": [101, 102, 103]
}
```

接口路径和已有请求兼容能力保留；账号列表的新代码只使用 `ids`。Controller 不再把最多 2,000 个 ID 直接作为一个底层批次执行，而是交给统一批量编排服务。

### 4.2 未勾选账号：新增查询接口

```text
POST /api/accounts/batch-online-by-query
POST /api/accounts/batch-offline-by-query
```

请求体只允许账号列表已经支持的筛选字段，不包含 `page`、`pageSize`：

```json
{
  "keyword": "628",
  "loginState": 2,
  "country": "美国",
  "accountGroupId": 10
}
```

空对象 `{}` 明确代表当前租户全部未软删账号。筛选字段与列表 `AccountQuery` 保持相同语义：

- `keyword`
- `phone`
- `accountType`
- `protocolId`
- `accountState`
- `riskStatus`
- `loginState`
- `muteStatus`
- `accountGroupId`
- `numberSource`
- `channelName`
- `country`
- `truthIp`

当前页面中尚未接入的 IP 分组、绑定客服字段不进入请求。

### 4.3 预估接口

```text
POST /api/accounts/batch-operation-preview
```

预估请求使用显式作用域，不能依靠字段是否为空猜测范围：

```json
{
  "operation": "ONLINE",
  "scope": "IDS",
  "ids": [101, 102, 103]
}
```

或：

```json
{
  "operation": "ONLINE",
  "scope": "QUERY",
  "query": {
    "loginState": 2,
    "country": "美国"
  }
}
```

响应示例：

```json
{
  "matched": 1256,
  "executable": 1200,
  "skipped": 56,
  "skipReasons": {
    "BANNED": 20,
    "UNBOUND": 10,
    "TAKING_OVER": 6,
    "MISSING_CREDENTIAL": 20
  }
}
```

离线预估中 `executable = matched`、`skipped = 0`。预估是执行前的数据库快照；确认和执行之间状态可能变化，因此前端文案使用“预计”，最终以后端执行汇总为准。

### 4.4 执行汇总

ID 和查询接口统一返回兼容现有批量结果核心字段的汇总：

```json
{
  "requested": 1256,
  "submitted": 1200,
  "accepted": 1190,
  "skipped": 56,
  "failed": 10,
  "skipReasons": {
    "BANNED": 20,
    "UNBOUND": 10,
    "TAKING_OVER": 6,
    "MISSING_CREDENTIAL": 20
  },
  "batchErrors": []
}
```

`requested` 表示 ID 数量或执行时实际匹配数量；`submitted` 表示通过登录跳过规则并进入内部批次的数量；`accepted` 表示成功写入 outbox 的数量。批次错误只返回必要摘要，不返回凭据、代理密码等敏感信息，也不为大范围操作返回完整账号明细。

## 5. 后端组件与数据流

### 5.1 统一批量编排服务

新增账号批量生命周期编排服务，职责限定为：

1. 校验 ID 数量或查询条件；
2. 解析目标范围；
3. 计算或应用批量登录跳过规则；
4. 按操作类型分片；
5. 调用现有 `AccountOnlineCommandService` 的小批次能力；
6. 捕获单批异常并聚合结果。

现有上线服务继续负责凭据、代理分配、状态校验和 outbox 命令准备，不承担分页扫描和跨批次汇总。

### 5.2 共享查询口径

列表、预估、查询执行复用 `AccountMapper.xml` 的筛选 SQL 片段和相同 JOIN 口径。新增目标查询按账号 ID 游标扫描：

```text
WHERE <列表筛选条件> AND a.id > :afterId
ORDER BY a.id ASC
LIMIT :scanSize
```

游标扫描不使用页面当前页码，也不使用 OFFSET 遍历大结果集。租户条件继续由现有 MyBatis 租户拦截器注入。

登录候选查询同时读取账号状态和凭据是否存在，形成可执行 ID 与跳过原因。在线状态不属于跳过条件。

### 5.3 分片执行

1. ID 请求先在当前租户内加载最多 2,000 个目标并计算跳过结果。
2. 查询请求按稳定 ID 游标持续扫描全部匹配目标。
3. 登录可执行 ID 累积到 500 个即调用现有上线小批次；离线目标累积到 1,000 个即调用现有下线小批次。
4. 最后一批不足上限时正常提交。
5. 每批独立记录 requested、accepted 或 failed，完成后合并返回。

## 6. 前端状态与交互设计

### 6.1 两套筛选状态

账号页维护：

- `editingFilters`：筛选控件当前正在编辑的值；
- `appliedFilters`：最后一次成功加载当前列表时使用的规范化筛选快照，不包含分页字段。

行为规则：

1. 点击查询时，从 `editingFilters` 生成候选筛选快照并请求第 1 页。
2. 请求成功后，原子更新列表、总数和 `appliedFilters`。
3. 请求失败时保留原列表、原总数和原 `appliedFilters`，不能让未成功条件成为批量范围。
4. 翻页、修改页大小、工具栏刷新、批量操作后的刷新全部使用 `appliedFilters`。
5. 点击重置时先清空 `editingFilters` 并查询；查询成功后才把 `appliedFilters` 更新为空。
6. 并发查询使用请求序号，只允许最后一次发起且成功的查询更新页面和已生效条件，避免旧响应覆盖新列表。

### 6.2 批量操作路径

1. 点击“批量登录”或“批量离线”。
2. 如果存在勾选行，构造 `IDS` 预估请求；否则构造使用 `appliedFilters` 的 `QUERY` 预估请求。
3. 预估可执行数为 0 时不弹执行确认，提示没有可执行账号。
4. 展示范围和预计数量，用户确认后调用对应 ID 或查询执行接口。
5. 执行期间禁用重复提交。
6. 完成后展示后端汇总并使用 `appliedFilters` 刷新当前页。

批量登录不再由前端提前删除封禁、解绑等所选账号，也不因选中抢登中账号而禁用整个批量入口；后端预估和执行统一给出跳过结果。单行上线现有保护不在本次范围内。

### 6.3 确认文案

有勾选：

> 当前已勾选 10 个账号，预计执行批量登录 8 个，跳过 2 个不可登录账号，是否继续？

无勾选且有已生效筛选条件：

> 当前未勾选账号，符合已生效筛选条件共 1,256 个；预计执行批量登录 1,200 个，跳过 56 个不可登录账号，是否继续？

无勾选且无已生效筛选条件：

> 当前未勾选账号，将对全部 1,256 个账号执行批量离线，是否继续？

数量使用千分位格式。取消确认不调用执行接口。

## 7. 一致性与并发边界

- `appliedFilters` 保证前端提交的筛选条件与当前列表最后一次成功查询一致。
- 后端预估和执行都重新查询当前租户数据库，避免依赖前端当前页数据。
- 预估不是锁定目标的持久化快照；确认期间新增、删除或状态变化可能导致最终数字变化，最终响应必须展示实际汇总。
- 查询执行使用稳定 ID 游标。前面批次登录后产生的登录状态变化不会导致已扫描 ID 重复执行。
- 本次不提供全局全或无事务。outbox 已受理的前置批次不会因后续批次失败而撤销。

## 8. 测试设计

### 8.1 后端

- Controller：原 ID 路径保留；查询路径和预估路径正确绑定请求。
- ID 校验：空 ID、重复 ID、2,000 成功、2,001 拒绝。
- 登录跳过：封禁、解绑、抢登中、缺凭据分别计数；在线账号进入提交集合。
- 离线口径：不因账号状态或缺凭据跳过。
- 分片：登录 500/501/2,000；离线 1,000/1,001/2,000。
- 查询范围：单条件、组合条件、空条件全量、跨多个扫描批次。
- SQL 一致性：列表 count、预估 matched、目标扫描使用同一筛选口径。
- 租户隔离：ID 和查询请求都不能读取或操作其它租户账号。
- 局部失败：中间批次异常后后续批次继续，汇总数正确且无敏感错误信息。

### 8.2 前端

- 按钮文案为“批量登录”“批量离线”。
- 有选择调用 ID 预估和 ID 执行接口。
- 无选择调用查询预估和查询执行接口。
- 编辑条件未查询时，批量请求仍使用旧 `appliedFilters`。
- 查询成功才替换 `appliedFilters`；查询失败保留旧列表和旧条件。
- 重置成功后空条件代表全部；重置失败仍保留旧生效范围。
- 翻页、刷新和批量完成后的刷新使用 `appliedFilters`。
- 确认文案正确展示范围、匹配数、执行数和跳过数；取消不提交。
- 预估为零、执行局部失败和执行整体失败都有可见反馈。

### 8.3 联调验收

- 勾选账号仅操作所选 ID。
- 离线筛选列表中修改其它筛选框但不查询，批量登录仍按离线条件执行。
- 新筛选查询成功后，批量范围切换到新条件。
- 重置查询成功后，未勾选批量操作覆盖全部账号。
- 超过当前页和超过 2,000 个查询结果均由后端完整扫描、分片并汇总。
- 已在线账号的登录命令进入协议 outbox，协议层按现有在线判断不重复处理。

## 9. 实施顺序

1. 后端先补接口契约、容量、跳过、分片、查询扫描和局部失败测试。
2. 实现统一批量编排服务、Mapper 查询与 Controller 接入。
3. 前端补 API、筛选快照和批量交互测试。
4. 实现前端两套筛选状态、预估确认和双执行路径。
5. 分别运行后端测试、前端测试与构建，再做两仓联调验收。
