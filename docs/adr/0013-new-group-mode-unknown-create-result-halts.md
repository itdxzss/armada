# ADR-0013：建群结果不明时停止并等待人工对账，不按次数自动重建

日期：2026-08-18
状态：已接受

## 背景

业务流程图把建群失败画成「记录失败原因 → 是否达到重试次数 → 未达到则重试，达到则建群失败」，即以重试次数为唯一收敛条件。

这与仓库既有口径冲突。「新建普群」的设计（`docs/business/group-list-create-normal-group-development-design.md` 第 6.4 节）区分了两类失败：明确未创建的失败可重试；超时或连接中断导致无法判断是否已创建的，标记 `RESULT_UNKNOWN` 并禁止自动重建。平台层的 `IdempotentGroupCreatePort` 已经实现了这一行为：同一 `operationId` 只建一次群，只有 `BAD_REQUEST`、`ACCOUNT_NOT_ONLINE`、`UNSUPPORTED_BACKEND`、`ACCOUNT_REACHOUT_RESTRICTED` 这类确定未创建的错误会清除领取状态允许重来，其余异常保留 `PROCESSING` 挡住重复建群。

## 决定

新群模式采用既有口径，不采纳按次数重试。

1. **确定未创建**的失败（参数非法、账号不在线、后端不支持、账号被限制触达）：允许在既定上限内重试。
2. **结果不明**（超时、连接中断、幂等结果保存失败、锁所有权丢失）：执行行进入结果未知状态并停止，等待人工对账，**不自动重建群**。
3. 建群直接使用 `IdempotentGroupCreatePort`，不在拉群侧另写一套幂等或重试判定。同一执行行的同一次逻辑建群始终复用同一个 `operationId`。
4. **已返回群 JID 但个别初始成员未加入**：群已真实存在，登记该群、标记部分成功，不重建群。缺失的站台由后续拉人调用按既有站台选号逻辑正常补足；缺失的次管理员由 `MANAGER_JOIN` 既有踩链接分支处理。回执未明确成功的角色行不得写成 `IN_GROUP`（见 ADR-0011、ADR-0012）。

## 影响

- 建群阶段的重试判定完全由协议错误码性质决定，不由计数器决定。任务配置中不提供「建群重试次数」参数。
- 结果未知需要人工介入，这是本决定的成本。换来的是不会产生重复的 WhatsApp 群——超时重建的典型后果是第一次其实已经成功、只是回执丢失，重试后多出一个无人清理的空群，且两个群都绑在同一条执行行上无法自动归因。
- 群 JID 一旦取得必须先条件更新落库，再写逐成员回执。JID 落库失败应转为结果未知，不得标记为明确失败，否则会放行重建。
- 任务详情需要能把「结果未知」与「明确失败」分开展示，并给出可定位的执行行与命令标识，否则人工对账无从下手。

## 被否决方案

**按流程图实现固定重试次数**：在超时场景下会重复建群。WhatsApp 建群没有可靠的客户端去重，一旦重建，多出的群既不属于任何执行行的成功事实，也不会被自动清理，还会占用建群人账号的建群频率配额、增加风控暴露。
