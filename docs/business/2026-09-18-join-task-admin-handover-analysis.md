# 进群任务：清理其他管理员并退出群组（需求分析）

日期：2026-09-18。状态：用户已授权在主仓库实施，本地实现和定向验证完成，未提交或部署。下文保留确认后的需求，实施结果见 `.harness/changes/join-task-admin-cleanup/summary.md`。

## 已确认要求

1. 复用主仓库已经实现的进群后“设置管理员”流程。
2. 沿用现有提权成功判定；成功后直接进入清理，不增加提权后二次核实、逐项回读或退群前再核实。
3. 清理由新进群且已提升成功的账号执行，把其他管理员踢出群（REMOVE），不区分是否为平台受控账号，不是仅取消管理员权限。
4. 用户最新明确取消受控管理员保护。清理名单仅排除新管理员自身和最后主动退群的原执行账号，其他管理员无论是否受控都踢出。
5. 任一步失败停止该流程后续操作，记录失败阶段、目标和原因；不能把未知结果当成功。
6. 清理全部成功后，由原执行账号最后主动退群。用户已确认其余规则无问题；原号不在清理阶段被踢出，必须留到最后自行退出。

## 简化后的流程

进群成功 → 现有设置管理员成功 → 新管理员踢出其他管理员（不区分受控身份） → 全部成功后原执行账号主动退群。

不开启新开关时，现有流程不变。开启时，直接接在已有管理员成功分支；使用业务成功回执，不把命令入队或传输接收当成业务成功。名单读取用于确定清理对象，不额外建立新号提权后的核实阶段。

清理名单 = 本群管理员 − 新管理员自身 − 最后主动退群的原号。

逐个下发 REMOVE，当前目标明确成功才继续下一个；任一失败或回执不明就停止，原号不退群。已有成功操作保留记录，不回滚或重新跑整次进群。

## 清理范围（最新确认）

- 不查询受控账号名单，不按平台归属、在线状态或本次是否选中来保护其他管理员。
- 只排除执行清理的新管理员自身与最后主动退群的原号；使用现有身份解析准确匹配这两个账号。
- 普通群成员不属于清理对象。
- 其他已成为管理员的新号也不因“本次任务账号”或“受控账号”身份获得保留。
- 平台不允许移除的对象若导致清理失败，按统一失败停止规则处理，不跳过后仍让原号退群。

## 实施影响与剩余边界

- 前端：在已有“群管理设置”增加默认关闭的新开关，依赖现有设置管理员功能；创建、编辑、复制、详情同步。文案明确清理其他管理员包含平台受控账号，原号最后自行退群。
- 后端：接入管理员成功分支；清理执行者固定为新号，原号沿用 adminActorAccountId；清理/退群未结束不能提前整体完成。
- 状态与记录：复用已有任务、进群和管理员状态；只补清理/退群阶段及必要目标结果，不增加业务复核阶段。具体持久化结构待实施设计，不在分析阶段预设多套新表。
- 清理名单：从群管理员集合排除新号与原号，不增加受控身份识别或跨租户保护查询；原有执行账号的权限边界不变。
- 失败：依协议业务结果判断；逐目标处理，避免现有批量调用某项失败后仍继续。超时/未知即停止后续，不自动跳过。
- 恢复：重复回调、重启不得造成重复清理/退群；已发送但无明确结果的操作保留停止状态，不能盲目重发。
- 原号为空：现有“目标已经是管理员”可不派发提权，因此 adminActorAccountId 可能为空。若保留最后退群要求，需确定原号，不能随机挑受控账号退出。
- 既有管理员重试策略与“任何一步失败即停止”的边界，实施时应明确；清理、退群失败至少禁止继续后续动作。
- 多任务同群应避免重复清理和互相干扰，但不新增等待其他新号提权的产品步骤。
- 数据迁移只走 Flyway；新增开关缺省关闭，不影响历史任务。已有外部踢人或退群不能靠数据库回滚恢复。

## 后续验收

- 未开启清理时沿用现有行为；已有提权成功后直接进入清理，无额外权限回读。
- 清理由新号执行；向其他管理员发送 REMOVE，不区分是否受控，目标被移出群，而不是仅降权。
- 其他受控管理员无论在线或离线、是否本次选中均纳入清理；不调用受控保护名单筛选。
- 第二个清理对象失败时第三个不执行，原号不退；明确记录第一个已成功。
- 执行清理的新号自身和原号不被踢出；原号最后自行退群；普通群成员不受影响。
- 清理全部成功后只允许指定原号自行退群；退群失败或结果不明不报整体成功。
- 双协议、重复回调、租户与用户权限、原号为空和同群并发分别验证。
