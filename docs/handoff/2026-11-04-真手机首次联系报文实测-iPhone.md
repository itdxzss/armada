- iPhone：没封。但 B 和 A 有共同群，不能当"陌生人首次联系"的对照。
- **zhuan：发出 "hi" 后 5 秒被封**。08:43:36.07 发出 → 08:43:40.98 `stream:error 503` → 重连 08:43:45.66 登录 `403` 判封，和 11-02 两个号的信号链一样。链接没发出去。

### Web 两条在 A 主手机上一直显示"正在等待此消息"（用户 09:0x 发现）

- A 的**主手机没能解开第一份**，两条都回了重试回执（`<receipt type="retry">`，`from=2203…16@lid`，即 A 主设备的 LID 地址）。我们的探针分身（A:3）解开了，所以上面的结构对照仍然有效。
- 本机脚本**没有重发**：Baileys 日志 `recv retry request, but message not available`。消息发出时按手机号地址缓存（`244930362812@s.whatsapp.net/<id>`），重试请求按 LID 地址来查，对不上。线上 Web 协议提供了按"账号 + 消息 id"查 Redis 的 `getMessage`（`account-manager.ts` 第 1741 行、`sent-message-store.ts`），**应该能重发**，这是本机脚本的缺口，不代表线上。
- **线上同样按手机号地址发**：超链任务目标是 `手机号@s.whatsapp.net`（Armada `HyperlinkMessageCommandFactory.java` 第 124 行），Baileys 按 PN 身份加密（"Using PN identity for @s.whatsapp.net conversation"）。iPhone、zhuan 发给 A 都走 LID 地址（zhuan HTTP 返回 `To: 2203…16@lid`）。主手机第一份解不开是否和 PN 地址有关，**未验证**；但线上 Web 私聊很可能每条都要多一轮"解不开 → 重试 → 重发"，而重发的副本按 Baileys 逻辑不带举报令牌、不带 tctoken（`isRetryResend`）。
- 待验证：线上 Web 号发一条私聊，看对方主手机是否也先回 retry；以及改成先解析 LID 再发能否一次解开。

**根因（已核实）：A 号在服务器上的身份公钥是旧的，不是我们消息格式的问题。** 用户确认：A 主手机上 iPhone 发的 2 条正常，zhuan 的 "hi" 和 Web 的 2 条都显示"正在等待此消息"。
- Web 发送前 3 次向服务器取 A 主设备（`2203…16@lid` 设备 0）的公钥，服务器都返回 `19a40d53…650e`（`web-send-…/rx.jsonl`）。
- zhuan 库 `wa_identities` 里 A 当年作为 perf2 账号（id 2897，11-01 15:31 导入、16:41 被顶 LOGIN_REPLACED）自己的身份公钥正是 `0519a40d53…650e`。
- A 主手机现在的身份公钥是 `ebb3a3a6…d288`（探针配对时服务器下发的 ADV `accountSignatureKey`）。
- 结论：A 换到真手机后，服务器发给新联系人的仍是 zhuan 时期的旧公钥；第一次联系 A、只能向服务器取公钥的发送方（zhuan 新号、Web 新分身）都用旧公钥加密，A 主手机打不开；探针分身用自己的新密钥，所以能解开。B 的 iPhone 和 A 有 204 个共同群，推测手里早有 A 的新公钥，所以正常（推断，未验证）。
- 影响：**A 不能再当接收号**。以后实验的接收号必须从没在我们任何协议（zhuan / Web / WB）上登录过。B 从没当过账号，不受影响；11-02 第三轮发给 B 被封与此无关。
- 上面的报文结构对照不受影响（结构取自探针分身解开的副本）。是否"对方解不开"本身会增加封号风险，未知。

### 两个更正（推翻了早上的结论）

1. **"iPhone 先签发隐私令牌再发消息"不成立。** zhuan 代码从不签发（`BuildIqPrivacyToken` 无人调用），A 照样在消息前收到 1 条 `privacy_token` 通知 → 这条通知是服务器自己生成的。只有 Web 多出的第 2 条才对应发送方主动签发。
2. **`<reporting_tag>` 是服务器加的**，zhuan 不发 `<reporting>`，A 收到的消息里也有 `reporting_tag`。真正由发送方生成的是 `<reporting_token>`。

### Web 协议举报令牌为什么"看运气"（Baileys 缺陷，已本机复现）

- `messages-send.js` 第 814 行用 `encodeWAMessage(reportingMessage)` 取消息字节，这个函数会在末尾补 1–16 字节随机填充（每字节值 = 填充长度）。
- `reporting-utils.js` 的 `extractReportingTokenContent` 按 protobuf 解析这串字节，读到填充就解析失败 → 返回 null → **不带令牌，也不打日志**。
- 填充 5 或 16 字节时恰好能被跳过，令牌正确；8 或 9 字节时被当成字段 1 算进去，**令牌错误**；其余长度都不带。
- 本机对同一条 "hi" 算 2000 次：**不带 1505 次（75%），带且正确 237 次（12%），带但错误 258 次（13%）**。
- 去掉填充（`proto.Message.encode(m).finish()`）就能稳定算对。用 A 解密出的内容验算：本次 Web 链接带的令牌 `2bc5…2e31` 正确；"hi" 应为 `a82d…39ca` 但没带。
- 脚本：[`wa-probe/reporting-token-check/`](wa-probe/reporting-token-check/) 下的 `rt-test.mjs`、`rt-sim.mjs`、`verify-rt.mjs`。

## 局限

- iPhone、Web 的发送方 B 和 A 有共同群，不是陌生人；只有 zhuan 是真陌生人，所以"会不会封"不能横向比，只能比报文结构。
- zhuan 走的是 HTTP 旧路径，和线上 Kafka 路径在正在输入、组包函数上不同（线上私聊不发正在输入，组包用 `prepared_peer_send.go`）。
- 每方只有 1–2 条样本；接收端是分身，看不到发送方只发给服务器的内容（Web 有发送方记录，zhuan、iPhone 没有）。
- `rcat` 含义未知。
