# 拉群营销逐料随机间隔设计

## 背景

当前拉群营销在 `ADD_MATERIALS` 阶段会把本群全部待进群料子组成一个参与者列表，单次提交给协议层。协议层最终也会在同一条 WhatsApp 群成员 IQ 中携带全部参与者。失败或未确认的参与者最多立即重试两次，业务侧没有逐人间隔。

第一套测试环境的近期任务中，三个建群账号都已成功创建群聊，但在后续加料窗口进入重新认证状态。群聊本身仍正常，营销账号也已在群内。现有证据不能单独证明批量加料就是封号原因，但批量和立即重试会形成明显的操作突发，需要先将其收敛为可配置的逐料节奏。

## 目标

- 每个群每次只添加一个料子。
- 第一个料子也必须等待，不能在营销账号进群后立即添加。
- 相邻添加尝试使用用户配置的基准间隔，并在基准值上下 20% 范围内独立随机。
- 单次失败后的最多两次重试也必须经过完整随机等待。
- 等待状态持久化，不占用执行线程，并能跨服务重启恢复。
- 在现有“新增拉群营销任务”抽屉中完成配置，不新增页面。

## 非目标

- 不改变建群账号、营销账号和料子的分配规则。
- 不改变建群前的联系人同步/互存逻辑。
- 不改变设置管理员、群权限、群信息、营销发送和建群账号退群逻辑。
- 不开放随机浮动比例配置；本次固定为 20%。
- 不把多个群强制串行。每个单群执行独立生成下一次执行时间。

## 方案比较与决策

考虑过三种前端配置方式：

1. 配置一个基准分钟数，后端固定按上下 20% 随机。
2. 分别配置最小和最大分钟数。
3. 提供若干预设档位，再允许自定义。

采用方案 1。它只增加一个字段，能直接表达“五分钟左右拉一次”，同时避免上下限填反、范围过宽等额外校验。方案 2 更灵活但交互和契约更复杂；方案 3 对当前单一场景没有额外价值。

## 前端交互

在现有 `GroupPullMarketingCreateDrawer` 的单群料子数量附近新增：

- 标签：`拉料间隔`
- 控件：Element Plus `el-input-number`
- 表单单位：分钟
- 允许范围：1 至 60 的整数
- 步长：1
- 默认值：5
- 辅助提示：`每次只拉 1 个料子，实际间隔随机为 4～6 分钟（±20%）`

辅助提示随输入实时计算。例如输入 10 时显示 8～12 分钟。创建请求将分钟转换为秒并提交。任务创建后配置冻结；任务详情摘要只读展示 `拉料间隔：5 分钟（随机 ±20%）`。

前端表单字段使用 `materialEntryIntervalMinutes`，API 请求及响应字段使用 `materialEntryIntervalSeconds`，避免和已有营销消息发送间隔混淆。

## API 与数据模型

创建任务 DTO、任务详情 VO 和前端 API 类型新增：

```text
materialEntryIntervalSeconds: integer
```

后端校验范围为 60 至 3600 秒，且必须为 60 的整数倍。后端不能只依赖前端校验。字段缺失时使用 300 秒，兼容旧客户端。

`group_pull_marketing_task` 新增：

```text
material_entry_interval_seconds INT NOT NULL DEFAULT 300
```

Flyway 迁移为历史任务填充默认值 300。MyBatis 映射、扩展实体和任务详情查询同步增加该字段。

随机浮动比例是后端常量，不进入数据库。生产实现按秒从闭区间中均匀取整：

```text
lower = ceil(baseSeconds * 0.8)
upper = floor(baseSeconds * 1.2)
delaySeconds = uniformInteger(lower, upper)
```

基准值为 300 秒时，结果始终位于 240 至 360 秒。

## 执行状态机

### 首次等待

营销账号确认已在群内后，不再把执行记录以立即到期的方式推进到 `ADD_MATERIALS`。两个可能进入该阶段的路径——建群响应已确认营销账号入群，以及后补营销账号成功——都调用同一个推进方法：

1. 读取任务的拉料基准间隔。
2. 生成一次独立随机延迟。
3. 将阶段推进到 `ADD_MATERIALS`。
4. 将 `next_execute_at` 保存为当前时间加随机延迟。

### 单次添加

`ADD_MATERIALS` 每次调度只读取 `allocation_no` 最小且 `entry_status=1` 的一条料子，并只向 `GroupParticipantPort` 提交一个 JID。不得复用当前对整批参与者立即循环重试的调用方式。

成功时：

1. 将当前料子的 `entry_status` 更新为成功。
2. 清零 `stage_retry_count`。
3. 若仍有待执行料子，生成新的随机时间并保持在 `ADD_MATERIALS`。
4. 若已无待执行料子，立即推进到 `SET_MARKETER_ADMIN`，由现有调度器继续后续阶段。

### 失败重试

单个料子最多尝试三次，即首次加群加两次重试。每次协议调用失败后：

- 第一次或第二次失败：料子保持待执行，`stage_retry_count` 加一，并生成新的随机 `next_execute_at`。
- 第三次失败：将该料子标记为失败，清零 `stage_retry_count`；若还有料子则随机等待后处理下一条，否则进入后续阶段。

任意一次失败都不能在同一个 worker 调用内立即再次请求协议层。`stage_retry_count` 只表示当前顺序最前的待执行料子的已失败次数；当前料子成功或最终失败后必须清零。

### 群封禁与生命周期

- 协议层明确返回群封禁时，沿用现有群封禁识别和收口逻辑，立即停止该群执行，不再等待重试。
- 账号离线、接口超时或普通添加失败，计为当前料子的一次失败并进入随机等待。
- 任务暂停后，调度查询不得推进单群执行。
- 任务恢复时，所有仍处于 `ADD_MATERIALS` 且未完成的执行重新以当前时间为基准生成独立随机等待，避免积压执行同时到期。
- 任务结束、取消或进入资源释放后，即使原 `next_execute_at` 已到期也不得继续添加料子。
- 服务重启后直接使用数据库中的 `next_execute_at` 和 `stage_retry_count` 续跑，不重新立即执行，也不使用 `Thread.sleep`。

## 一致性与并发

- 沿用现有 `tryLeaseExecution` 租约，保证同一单群执行在一个到期时间只被一个 worker 处理。
- 单次料子结果、`stage_retry_count` 和下一次时间安排在同一数据库事务中完成，避免数据库只落下一半状态。
- 更新语句保留执行状态、当前阶段和待执行状态条件，租约丢失或任务生命周期变化时不得覆盖新状态。
- 不增加跨群全局锁。不同建群账号对应的群可以并行等待和执行，每个群独立随机。

协议请求和数据库之间不存在分布式事务。如果进程在协议层已成功、数据库尚未提交时退出，恢复后可能再次提交同一个号码。已有成员返回或成员查询确认已在群内时必须按成功处理，不能消耗重试次数；因此恢复语义是至少执行一次，但业务结果保持幂等。

## 可观测性

新增或调整的结构化日志包含：任务 ID、执行 ID、料子顺序号、当前尝试序号、结果、下次执行时间。日志不记录完整手机号。

任务详情继续展示每个群的成功料子数和失败原因，并在任务配置摘要中展示拉料间隔。随机得到的每次实际时间不作为用户可编辑配置，但可通过执行日志核查。

## 测试

### 后端

- 创建任务缺省值为 300 秒。
- 拒绝小于 60、大于 3600 或非整分钟的值。
- 任务详情返回配置值。
- 随机策略在边界值下始终落在 80% 至 120%，并可通过注入随机源进行确定性测试。
- 营销账号确认入群后，第一个料子不会立即执行。
- 每次协议调用只包含一个参与者。
- 成功后按顺序处理下一条，且每条之间都有新的随机等待。
- 前两次失败只增加尝试次数并延后，第三次失败才将当前料子标记失败。
- 群封禁立即终止，不安排下一次执行。
- 暂停不推进，恢复重新随机排期，结束或释放后不再调用协议层。
- 重启场景使用已保存的到期时间和尝试次数续跑。
- 已在群内的料子按成功处理，不消耗失败重试次数。
- 最后一条料子完成后才进入管理员、权限和退群阶段。

### 前端

- 创建表单默认显示 5 分钟。
- 仅接受 1 至 60 的整数。
- 辅助提示正确显示 80% 至 120% 的分钟范围。
- 创建请求正确把分钟转换为秒。
- 任务详情正确展示基准分钟和固定随机比例。

## 发布与验收

先部署数据库迁移和后端，再部署前端。使用第一套测试环境创建小规模任务，至少验证：

1. 营销账号进群后 4 至 6 分钟内没有立即批量加料。
2. 每个群一次只新增一个料子。
3. 三个料子的实际调用间隔均位于配置范围。
4. 人为制造一次可重试失败后，不会立即再次请求。
5. 暂停和恢复不会形成集中突发。
6. 群成员结果、任务阶段和资源释放最终一致。

本次节奏调整只能降低突发操作风险，不能承诺账号不会被 WhatsApp 风控。验收时仍需结合账号状态、群状态和安卓节点原始错误记录观察。
