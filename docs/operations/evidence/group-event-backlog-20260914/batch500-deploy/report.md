## 下一步分析（未实施）

1. 同一条完整群资料入口已调用 lockGroupWriteBoundary，但后续 fillGroupCreatedAt、replaceCompleteSnapshot、applyControlledParticipantObservations 又各自解析/锁定同群；有建群时间时最多4次进入resolveGroupIds，资料patch服务另查groupId。可以在同一事务复用已锁群上下文，保留必要的current-read与身份合并锁。
2. 完整快照已写15人成员事实，受控账号关系阶段又批写同批成员事实。上次120→8只优化第二阶段的逐账号SQL，没合并这两个阶段。下一轮可让完整快照负责成员状态、后续只补账号绑定；必须保留快照新旧判定、未接受快照的绑定行为、精确ADD的进群周期和PN/LID一致性。成员变更入口也存在先写事实、再对齐账号时重写事实的同类结构，应分场景验证。
3. 8秒/32次数据库当前语句采样共23次非空命中：创建者兼容表group_link_preview更新11次，资料wa_group_profile更新4次，成员wa_group_participant更新1次，其余为查询、最小资料行和commit。它只说明短时热点，不是耗时占比。创建者路径每条报告还查询国家配置。应进一步计时、收敛资料重复更新，保留观察时间、补全和纠错语义，不能仅以值相同跳过水位推进。
4. 当前topic只有3分区；单纯增加消费者线程不能直接突破分区上限。不同群并行可作为后续阶段，同群顺序、重复投递和提交位点需要一起处理，本轮分析不修改并发/分区/锁。
