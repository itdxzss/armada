# ADR-0010：新群模式的建群收进拉群执行行阶段循环

日期：2026-08-18
状态：已接受

## 背景

ADR-0001 把新群模式整体排除在上一期之外。现在要实现它。

仓库里已经有两套彼此独立的能力：

- 群组列表的「新建普群」（`com.armada.group.normalcreation`）：一次提交建 N 个群，Kafka 三阶段流水线（联系人准备 → 创建群 → 群后处理），完成一次性建群、五项权限设置与回读、自建群登记、可选提权与建群人退群。
- 拉群任务的普通群链接版：执行行阶段循环，`PullTaskExecutionStage` 八个阶段由 `PullTaskExecutionDispatchScheduler` 抢占执行行、`PullTaskExecutionStageRouter` 按持久化阶段执行一次有界动作，支持暂停、恢复、资源等待、检查点续跑、拉手与管理员人工补充。

新群模式需要「先建群、再按现有链路拉人」。问题是这段建群放在哪。

## 决定

在拉群任务自己的执行行阶段循环前面增加建群阶段，不调用「新建普群」的任务、表或 Kafka 流水线。

- 复用**协议能力层**，不新增端口，不复制协议实现：`IdempotentGroupCreatePort`（`platform/protocol/idempotency/`，装饰在 `GroupCreatePort` 外，同 `operationId` 只建一次群）、`ContactPort`、`GroupSettingsPort`、`GroupProfilePort`、`GroupInvitePort`、`GroupMetadataPort`。Web 与 Android 两套 Adapter 已覆盖这些能力。
- 新写的只有**编排**：新阶段调用上述端口、保存群 JID、生成群邀请链接、推进到下一阶段。
- **不新建任务表**，建群事实落在拉群现有执行行及其角色行上。
- `normal_group_creation_*` 三张表、三个 Kafka 主 Topic 和三个消费者不参与本模式，也不因本模式修改。

## 影响

- 「新建普群」功能零改动。它自己的口径、状态机和已上线行为不受本模式搅动。
- 一条执行行从建群到收口只有一套状态机、一条时间线；暂停、恢复、资源等待、重启续跑、任务详情展示全部沿用现有机制，不需要为「建群中」另找位置。
- 建群编排在仓库中会存在两份（`normalcreation` 一份、拉群一份）。这是本决定的真实代价。缓解方式是两边都通过 `IdempotentGroupCreatePort` 建群，重复的是编排而不是最容易出错的幂等与结果对账逻辑。
- 三个功能仍共用底盘，与本决定无关：`group_link` 与自建群登记、协议 Port/Adapter、协议命令 Outbox（按账号串行，新群模式上量会拉长同账号命令队列并影响另两个功能吞吐）、账号分组池。容量规划需要把这一层算进去。

## 被否决方案

**先调用「新建普群」建出群、拿到邀请链接，再把结果当成一条普通群链接执行行喂给拉群循环。**

复用最多、改动最小，但要为拉群的需求给 `normalcreation` 增加群名取自料子文件名、群头像、群描述、站台作为初始成员、群设置执行时机、建群后生成邀请链接等能力，并新增「建群人不得退群」分支——即直接修改一个已上线功能。其测试覆盖（约 23 个测试类）远薄于拉群（约 260 个测试类），回归风险更高。此外两套状态机拼接后，「建群中」在拉群的任务详情、暂停与结束语义里没有位置，失败归因需要跨表查询。
