## 1. 最终结论

采用“账号上的拉手专用状态”，不复用账号全局风控状态，也不把任务角色行当成跨任务的唯一事实源。

Armada 收到拉人受限结果后，给账号写入：

- `puller_restriction_status=2`：拉手受限；
- `puller_restriction_until=发生时间+24小时`：预计恢复时间。

Armada 每 10 分钟处理一次已到期记录，把拉手专用状态改回允许。普通拉群业务只判断拉手专用状态，不在选号、分配、执行等各处重复比较时间。预计恢复时间只供定时任务和页面倒计时使用。

这套状态只影响普通拉群的“拉手”资格：

- 不修改账号的正常、离线、解绑、封禁、被抢登等现有状态；
- 不写现有全局 `risk_status`；
- 不影响营销、建群营销或账号的其他业务能力；
- 不需要协议层查询真实解封时间；
- 到期后再次拉人如果仍受限，再从新的受限结果开始计算 24 小时。

## 2. 为什么使用拉手专用状态

### 2.1 现有账号状态不能混用

[`V005__account.sql`](../../../armada-api/src/main/resources/db/migration/V005__account.sql) 中已有账号生命周期、登录状态和全局风控状态。它们的职责不同：

| 状态 | 负责什么 | 本需求是否修改 |
| --- | --- | --- |
| `account_state` | 正常、解绑、封禁、被抢登等账号生命周期 | 否 |
| `login_state` | 在线、离线 | 否 |
| `risk_status/risk_end_time` | 多业务共享的账号风控 | 否 |
| 新增拉手专用状态 | 账号能否作为普通拉群拉手 | 是 |

营销和建群营销现有选号会过滤全局 `risk_status`。如果把本次拉人限制写入全局字段，这两个业务也会被连带停掉，与“只限制拉手”的目标不符。

### 2.2 不继续把任务角色状态当账号事实

现有 `pull_task_group_account.availability_status` 描述的是某个任务执行行里的角色状态，还会被离线、移除等事件覆盖。同一账号又可能出现在多个任务中，因此它不适合作为账号级、跨任务的受限事实。

本次把受限事实集中到账号维度后：

- 同一账号在所有普通拉群任务中的拉手资格一致；
- 离线、移除等任务内事件不会清掉账号的拉手限制；
- 到期只改一个地方，不需要扫描并修正该账号的多条历史任务角色行。

## 3. 数据设计

在 `account_state` 增加两个业务专用字段：

```sql
puller_restriction_status TINYINT NOT NULL DEFAULT 1
    COMMENT '普通拉群拉手限制状态:1允许 2受限',
puller_restriction_until BIGINT NULL
    COMMENT '普通拉群拉手预计恢复时间,epoch毫秒'
```

并增加到期扫描索引：

```sql
(tenant_id, puller_restriction_status, puller_restriction_until, id)
```

字段约束：

| 状态 | 截止时间 | 含义 |
| --- | --- | --- |
| 1 | `NULL` | 允许作为普通拉群拉手；仍需通过现有在线、生命周期等条件 |
| 2 | 非空 | 拉手受限，等待 Armada 到期处理 |

`puller_restriction_until` 是 Armada 的预计重试时间，不代表 WhatsApp 承诺在该时刻解除限制。

### 3.1 受限写入

继续复用现有标准结果 `RATE_LIMITED` 和 `ACCOUNT_REACHOUT_RESTRICTED`。Armada 接受并完成结果幂等校验后执行条件更新：

```text
status = 2
until = max(现有 until, occurredAt + 24h)
```

规则只有三条：

1. 重复结果不能反复延长同一次限制。
2. 迟到的旧结果不能缩短较新的截止时间。
3. 已经超过 24 小时才到达的旧结果不重新限制账号。

如果该结果仍属于执行行当前分配的拉手，则清除当前粘性拉手并让执行行进入既有的“等待拉手”流程；旧调用的迟到结果可以记录账号限制，但不能清除后续已分配的新拉手。

### 3.2 10 分钟到期任务

“Armada 每 10 分钟处理”是后端本地数据库定时任务，不是调用 WhatsApp，也不是发送试探性拉人命令。

每次只执行幂等条件更新：

```sql
UPDATE account_state
SET puller_restriction_status = 1,
    puller_restriction_until = NULL,
    updated_at = :now
WHERE puller_restriction_status = 2
  AND puller_restriction_until IS NOT NULL
  AND puller_restriction_until <= :now;
```

生产实现按租户、固定批次处理，调度间隔配置为 10 分钟。条件中的状态和截止时间用于避免并发覆盖：如果扫描期间账号又收到新的受限结果，新结果仍会把状态写回 2 并设置更晚截止。

到期任务只修改上述两个拉手专用字段，不修改：

- `account_state`、`login_state`；
- 全局 `risk_status/risk_end_time`；
- 静音、代理、凭据等账号信息；
- 拉群任务本身的暂停、结束、完成状态。

因此账号到期时即便仍离线、已解绑或已封禁，也只是“拉手限制到期”，仍会被现有账号条件挡住，不会错误参与任务。

### 3.3 存量数据

上线迁移需要把现有受限拉手汇总到新字段，确保现场这批账号不会继续永久卡住：

1. 按租户和账号识别现有普通拉群任务中的两个标准受限原因。
2. 优先使用现有拉人结果时间计算 `结果时间+24小时`；无法还原结果时间、但任务角色仍明确处于受限状态时，保守使用角色行 `updated_at+24小时`。
3. 截止仍在未来的账号写状态 2 和最大截止时间；已经到期的账号写状态 1、截止为空。
4. 不按父任务是否结束过滤。任务结束不等于账号的拉手限制立即失效。
5. 迁移输出命中数、已到期数和无法匹配数，便于核对现场 28 个账号。

现有 `pull_task_group_account.cooldown_until` 和 `availability_status=2` 不再作为新逻辑的跨任务事实。为兼容发布顺序，第一阶段保留列但停止新增冷却写入；新旧代码稳定切换后，再单独清理旧分支和冗余列，避免长期维护两份状态。

数据库实施仍需遵守项目数据规范：使用下一个未占用 Flyway 版本，同步提供 `.harness/changes/puller-risk-cooldown/db-migrations.sql`、`rollback.sql`，并重生成 `.harness/wiki/数据模型.md`。本设计阶段不创建迁移。

## 4. 普通拉群如何使用状态

### 4.1 唯一资格判断

普通拉群统一复用一个拉手资格查询，核心条件为：

```text
账号生命周期正常
AND 当前在线
AND puller_restriction_status = 1
AND 协议身份完整
AND 满足既有占用、群成员等条件
```

业务资格判断只看 `puller_restriction_status`，不看 `puller_restriction_until`。时间比较集中在 10 分钟到期任务中。

### 4.2 检查位置

保留两个必要边界，不在每个中间阶段堆叠时间逻辑：

1. 选号或补拉手时，通过统一资格查询过滤状态 2 的账号。
2. 正式生成拉人命令前，再读取一次同一个状态，防止账号在选号后才收到受限结果。

已成功生成并进入 Outbox 的命令视为在途，不做协议撤销。若最后一次状态检查发现受限，不生成拉人命令，执行行回到既有“等待拉手”流程。

### 4.3 到期后的任务行为

- 状态扫描恢复后，新任务可以重新选择该账号。
- 正在等待拉手且父任务仍为执行中的任务，会由现有资源恢复调度继续处理；当前默认复核周期约 30 秒。
- 人工暂停任务仍需人工恢复。
- 已结束、已完成或其他终态任务不会因为账号恢复而重新启动。
- 恢复后的第一次拉人仍返回受限时，账号再次进入状态 2。

因为到期扫描每 10 分钟一次，实际状态恢复时间是“预计截止时间之后 0 到 10 分钟”，等待中的任务再叠加现有约 30 秒资源复核延迟。

## 5. 其他业务边界

营销、建群营销和其他业务不读取 `puller_restriction_status`，所以拉手受限不会阻止该账号执行这些业务。它们仍按各自现有的账号生命周期、登录状态、全局风控和业务资格判断运行。

同一账号在普通拉群任务中担任经理、站台等非拉手角色时，也不因为这个拉手专用状态被直接阻断。只有代码明确以“拉手”身份选号或发起拉人命令时才检查该状态。

如果未来确认 WhatsApp 的这类限制实际覆盖营销、建群等所有动作，应另开需求提升为账号全局风控，不能直接扩大本字段的读取范围。

## 6. 接口与页面

任务详情拉手池汇总增加：

```json
{
  "serverNow": 1788134400000,
  "restrictedPullerCount": 28,
  "nextPullerRestrictionUntil": 1788220800000
}
```

拉手明细增加：

```json
{
  "pullerRestrictionStatus": 2,
  "pullerRestrictionUntil": 1788220800000
}
```

页面规则：

- 状态 2 且截止未到：显示“拉人受限，预计 xx:xx:xx 后可重试”。
- 页面用 `serverNow` 修正客户端时间差。
- 倒计时到 0 但状态仍为 2：显示“已到预计时间，等待系统解除”，并正常刷新详情。
- 只有后端返回状态 1 才显示可用；前端倒计时不能自行改状态。
- 文案使用“预计可重试”，不承诺“WhatsApp 已解封”。

## 7. 验收标准

### 7.1 后端与数据

- 两个标准受限结果都能把账号拉手专用状态写成 2，并写入 24 小时截止。
- 同一结果重复回调不重复延长，旧结果不能缩短或错误清除新限制。
- 初选、补拉手和正式命令生成前只按专用状态拦截，不在业务入口比较截止时间。
- 10 分钟任务只恢复已到期的专用状态；并发新限制不会被误清。
- 账号离线、解绑、封禁、被抢登等状态不会被到期任务改变。
- 营销和建群营销查询不读取新字段。
- 存量迁移能给出现场 28 个账号的匹配与恢复结果。

### 7.2 页面与任务

- 页面显示服务端校准的预计倒计时、受限数量和最近预计恢复时间。
- 倒计时结束后，在下一次 10 分钟扫描前不会自行显示可用。
- 执行中且等待拉手的任务能在状态恢复后继续；暂停和终态任务不会自动启动。
- 恢复后仍被 WhatsApp 限制时，可以再次进入新的 24 小时周期。

## 8. 发布与回滚

建议按兼容顺序发布：

1. 先加新字段、索引并完成存量回填。
2. 后端切换为写入和读取拉手专用状态，并启用 10 分钟任务。
3. 前端展示新状态和倒计时。
4. 观察稳定后再清理旧任务角色冷却逻辑。

回滚后端时保留新字段和数据，停止定时任务即可；不要在紧急回滚时删除字段或丢失现有受限记录。回滚脚本只用于明确的数据回退窗口，并需再次确认目标环境。
