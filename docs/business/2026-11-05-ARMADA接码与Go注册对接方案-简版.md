# ARMADA 接码与 Go 注册对接方案（简版）

日期：2026-11-05。状态：待 Claude 复核，本轮仅出方案。

**目标：沿用现有手动取号页面，取号后点击一次“开始注册”，后台自动申请验证码、等码、提交并显示注册结果，关闭页面也能继续。**

**当前前提：Go 三接口的本地工作流已实现，但真实网络 Transport 尚未接通。该能力和有效设备配置就绪前，注册按钮保持禁用；本方案不是“现在已经能够真实注册”的声明。**

## 1. 首版只做这些

- 复用现有 Grizzly 客户端、取号页面和短信订单；每次选一条已取得的号码开始，可同时办理三个不同号码。
- ARMADA 负责订单与注册事务对应、后台推进；Go 负责参数、加密、真实发码/验码和身份结果保存。
- 每条订单首版只发起一次发码、提交第一条有效新验证码。重复 HTTP 请求沿原幂等键恢复，不算另一次业务操作。重发、换码、补买号码先交人工处理，不自动循环。
- 成功边界是 Go 确认 REGISTERED 且结果已保存；账号导入、自动登录和上线验收另做。现有 Cobalt/手机注册流程保持原入口，不接管这里的订单。

## 2. 正常流程

| 步骤 | 执行方与动作 | 保存/显示什么 |
| --- | --- | --- |
| ① 取号 | 运营沿用现有取号功能 | 已有短信订单、完整号码 |
| ② 开始注册 | ARMADA 保存关联记录，调用 Go 发码接口 | Go transaction_id；不能仅凭 HTTP 200/202 判成功 |
| ③ 等码 | Go 确认 WAITING_CODE 后，后台按该 activation_id 查 Grizzly | 仅接受 RECEIVED 的新码，保留字符串前导零 |
| ④ 提交 | ARMADA 用对应 transaction_id、验证码和冻结的 expected_version 调 Go | 验证结果；三个号码乱序到码也各回各的事务 |
| ⑤ 收尾 | Go REGISTERED 且 result_available=true 后，先保存注册成功，再通知 Grizzly 完成 | 注册成功与接码订单完成分别显示；收尾失败不抹掉注册成功 |

页面只显示“申请中／等验证码／验证中／已注册／需处理”，复用现有号码、验证码展示，不增加新菜单。接码记录的完成状态仍按供应商确认更新。

## 3. 接口与数据：最少增加什么

**ARMADA 新增两个接口**，继续使用现有登录与 `tenant:account:edit` 权限：

| 接口 | 用途 |
| --- | --- |
| `POST /api/sms-activations/{id}/registration`，无业务正文 | 开始该订单的注册；重复点击返回同一关联记录，不另发码、不再买号 |
| `GET /api/sms-activations/{id}/registration` | 只读本地办理状态，不通过页面查询推进外部操作 |

开始只接受当前租户、未过期、处于 WAITING_CODE 且尚无验证码的订单。目标地址与设备 profile 从服务端取，不接受页面传入目标 URL、租户或密钥。

**Go 继续使用现有三个接口**：

| 动作 | 请求 |
| --- | --- |
| 首次发码 | `POST /ws/v1/registrations/code-requests`：`phone`、`profile_id`；method 省略即 sms |
| 提交验证码 | `POST /ws/v1/registrations/{id}/code-verifications`：`code` 字符串、`expected_version` |
| 查询结果 | `GET /ws/v1/registrations/{id}` |

适配器将供应商的国际数字号码补成显式 `+` 格式；解析 Go 的 `Code/Data/Msg` 与 snake_case 字段。号码、验证码、密钥和响应原文不写日志。

**新增一张小关联表 `sms_registration`，一条短信订单最多一条记录。** 归属 account 域，通过 Flyway 建表，tenant_id 隔离，`(tenant_id, sms_activation_id)` 唯一。只存本流程需要的字段：

| 字段组 | 用途 |
| --- | --- |
| id、tenant_id、sms_activation_id、created_by、created_at、updated_at | 定位订单、归属和审计 |
| state | 1申请中、2等码、3验证中、4已注册、5需处理；TINYINT + Java enum |
| go_transaction_id、go_profile_id | 固定 Go 事务与本次配置，启动后不换 |
| verify_version | 第一次提交验证码使用的 Go version；提交意图保存后冻结，重放不能改成 GET 的新版本 |
| lease_token、lease_until、next_run_at | 数据库抢占及下次推进时间，防两个实例同时执行同一记录 |
| finish_started_at、last_error_code | 接码订单完成请求的持久化意图，以及固定失败分类 |

号码、验证码和供应商订单号仍只存现有 sms_activation；验证码一旦进入本次验证阶段就不能覆盖。身份、私钥和完整注册结果只由 Go 保存。短信状态与注册状态是不同事实，因此用关联表；现有 account_registration_item 会被 Cobalt/手机 worker 扫描，不复用到本流程。

两个操作键由不可变记录生成：`sms-go-v1:{tenantId}:{id}:send` 和 `sms-go-v1:{tenantId}:{id}:verify`，无需再建操作表。先保存记录/阶段、profile 或 verify_version，再调用 Go；重放使用完全相同的号码、配置、验证码、版本和操作键。

## 4. 后台推进与三个必要边界

**一个简单 worker 足够。** 复用项目的定时执行方式，每约 4 秒扫描到期记录，用有期限的数据库 lease 抢占；每个 ARMADA 实例最多并行执行 3 条。不引入 Kafka、通用任务引擎或批量采购。lease 只防本地竞争，Go 幂等键继续防网络重复；过期 lease 不等于可以换键重发。所有阶段更新检查 lease_token，HTTP 调用不持数据库事务锁。

1. **订单占用互斥。** 开始注册与现有完成/取消操作都先在同一短信订单行上检查/占用，再发外部请求。开始与关联插入在同一短事务提交；现有取消须先用 CAS 标记“取消中”，成功占用后才请求供应商，避免取消已发出却又被注册接管。绑定后的订单不再允许旧人工完成/取消接口直接操作；由注册 worker 完成或转人工核对。绑定后的页面刷新只读本地，旧在途查码写回也必须检查是否已被注册占用，避免覆盖新流程。
2. **租户与运行目标固定。** 内部 HTTP 使用 `X-Tenant-Id` 传递服务端确定的租户，设备 `profile_id` 按租户配置；Go 对应同一 tenant_id，operator_id 固定为 `armada`，实际操作人在 ARMADA 审计。注册接口仅供受控 Armada 服务访问，不再维护逐租户令牌。worker 按已配置租户恢复 TenantContext；不同租户不能共用同一 Go 归属。首版直连一个受控 Go 注册服务；有未完成记录时不变更其地址、数据归属或存储保护密钥。现有 coordinator 未支持事务路由，本期不走它。
3. **成功后的订单完成只发一次。** 先保存 state=已注册，再 CAS 写 finish_started_at，最后调用 Grizzly COMPLETE。收到明确成功才将短信订单标为 COMPLETED；请求超时、崩溃或本地保存失败时，保留“已注册、接码完成待确认”，不自动重复 COMPLETE，由运营核对供应商订单。已有完成按钮不能绕过占用检查。

## 5. 失败与重启怎么处理

| 情况 | 首版处理 |
| --- | --- |
| 重复点击、同键重试 | 返回/恢复原记录；不得调用取号接口或生成新操作键 |
| 发码 HTTP 超时、尚未拿到事务 ID | 用原发码键和原正文取回原事务；不另建请求。Go 的幂等约束防止再次发送短信 |
| 已有事务 ID、请求仍在执行 | 查 Go 原事务；只有明确 WAITING_CODE 才继续收码，REGISTERED 且结果可用才记成功 |
| 验码请求超时或服务重启 | 先查原事务；需要恢复原 POST 时仍用原验证码、冻结的 verify_version 和原键。新查询版本不替换原请求版本 |
| Go OUTCOME_UNKNOWN、ACTION_REQUIRED、拒绝、版本冲突，或缺能力 503 | 转“需处理”，停止自动发码/验码/补买；保留原订单和事务。Go 已支持的显式重发能力不在本期自动启用 |
| Go 429 / RATE_LIMITED | 当前合同没有区分容量、冷却和次数限制，首版统一转“需处理”，不猜原因或自动重试 |
| Grizzly WAIT_RETRY / WAIT_RESEND | 旧码不提交，不自动要求再次发送；到期转“需处理” |
| 等码期间订单过期或已取消 | 停止提交新验证码，保留记录；不自动补买。已有 Go 在途操作仍查询归档，不能把到期当作撤回成功 |

重启从数据库继续，GET 永远只读。进入“需处理”后不自动重新开始；首版界面给出固定原因，后续人工续办需另定义操作，不能用重复点击偷偷重置。非终态推进到订单有效期为止；到期后最多做一次有界 Go 状态核对，仍不明就停，不无限轮询。

## 6. 改动范围与验收

| 位置 | 最小改动 |
| --- | --- |
| ARMADA account 域 | 两个 Controller 方法、一个注册 Service/worker、关联表 Mapper/实体；旧短信 Service 增加占用及取消意图检查 |
| ARMADA platform/protocol | 一个只含三方法的注册能力 port 及 Go HTTP adapter；业务不依赖 HTTP DTO，不改 Cobalt 合同 |
| ARMADA boot 与 Flyway | 服务端启用/地址/租户 profile 映射；一张关联表、短信状态增加取消中；迁移编号编码时核对 |
| 现有接码页面 | 一个开始按钮和注册状态展示；查询轮询不负责发码或提交验证码 |
| Go | 本方案复用三接口；真实网络 Transport 必须另行完成，旧凭据登录保持兼容 |

验收只抓六件事：单号正常完成；三个号码乱序到码不串号；重复点击/重启不重复发码；Go 超时和未知不会被当成功；跨租户拒绝及取消/启动竞争互斥；已注册但 COMPLETE 不明时不丢成功事实、不重复收尾。Java 存储用 H2 跑真实 Mapper/事务，跨端合同使用本地 HTTP 替身；这些结果不代替真实单号验收。

实施顺序：先关联表与 Go adapter，再 worker/页面，最后对接可用的 Go 网络实现做单号及三号验证。Go 未就绪时可离线开发，但不能以此开启真实注册入口或自动采购。回滚先关注册开关，停止新启动与自动推进，保留订单/关联/Go 事务；占用检查继续有效，已绑定订单转人工核对，不删除数据或退回能绕过占用的旧代码。
