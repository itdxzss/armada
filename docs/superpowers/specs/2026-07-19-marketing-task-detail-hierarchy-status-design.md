# 营销任务明细层级与群组状态统一设计

## 1. 背景

普通群组营销任务详情已经具备按“账号 → 实际发送群组”聚合的基础能力，但当前展示字段和状态语义尚未完全对齐业务要求：

- 一级当前展示的是任务目标执行状态，不是发送账号实时在线状态。
- 二级仍混有群组链接、最近原因等非目标字段。
- 协议状态 `BANNED` 同时承载多种群异常，`NO_PERMISSION` 同时承载无发言权限和账号不在群内，页面无法准确区分。
- 协议发送失败统一使用 `SEND_FAILED`，账号封禁缺少稳定、可判定的失败原因码。
- 当前分支已提交最新发送结果 `executionResult` 的第一阶段实现，但结果与失败原因使用不同排序口径，存在跨轮次错配风险。

本设计合并需求第 4、5 条，统一详情层级、统计口径、群组状态和最后一轮执行结果。

## 2. 已确认业务口径

### 2.1 展示层级

一级一行一个发送账号，字段严格为：

1. 在线状态
2. 发送账号
3. 账号发送总条数
4. 明细

二级为该账号在当前任务中实际产生发送记录的群组，字段严格为：

1. 群组状态
2. 群名称
3. 单群发送条数
4. 最后发送时间
5. 执行情况

群组链接和独立“最近原因”不再作为二级展示列；失败原因合并在“执行情况”内展示。

### 2.2 发送次数

- 账号发送总条数：该账号在当前任务中收到成功发送回执的累计次数。
- 单群发送条数：该账号向该群在当前任务中收到成功发送回执的累计次数。
- 同账号、同群跨轮次成功发送会逐次累计。
- 失败、跳过和已提交但尚未回执的尝试不计入发送条数。
- 固定选群和账号动态选群统一以 `marketing_task_send_attempt` 中的实际发送事实为准，不使用创建任务时的预计目标数代替。

### 2.3 最后一轮与最后发送时间

- “最后有效发送结果”只在发送尝试状态为成功或失败时产生。
- 按 `round_no DESC, attempt_no DESC, id DESC` 选择同账号、同群的最后有效发送记录。
- 已提交和已跳过记录不覆盖上一条已确认的成功或失败结果。
- 最后发送时间只取该账号向该群最近一次成功发送的结果时间；从未成功时展示 `-`。

### 2.4 成功覆盖状态

用户已确认：最后有效发送结果为成功时，群组状态无条件显示“正常”，覆盖该轮发送前可能存在的过期封禁、成员或权限检测结果。实际成功回执是发送可用性的最高优先级事实。

## 3. 方案选择

### 3.1 推荐方案：协议稳定原因码，后端统一归一化

协议层保留现有群可发送性快照字段，同时把通用 `SEND_FAILED` 细分为稳定失败原因码。Armada 后端基于“最后有效发送记录”的发送结果、失败原因码和群状态原因，统一生成页面使用的群组状态与执行原因。

优点：

- 账号封禁不依赖前端或后端解析英文错误文本。
- 不扩大 Kafka `groupStatus` 原始枚举的兼容风险。
- 页面只消费稳定业务枚举，不理解 Baileys 或 WhatsApp 原始异常。
- 现有 `reason_code`、`group_status`、`group_status_reason` 列足够承载，不需要数据库迁移。

本设计采用该方案。

### 3.2 被否决方案：直接扩展协议 `groupStatus` 为页面五态

该方案会把账号封禁混入纯群状态快照，并要求协议、Kafka 消费者和历史群相关消费者同时升级。契约影响面更大，且原始协议事实与页面展示状态耦合，不采用。

### 3.3 被否决方案：前端解析失败文案

英文异常文本、Baileys 错误结构和版本差异均不稳定，无法可靠区分账号封禁、群组封禁和权限问题，不采用。

## 4. 统一群组状态

详情接口对前端返回以下业务枚举：

| API 值 | 页面文案 | 判定依据 |
|---|---|---|
| `NORMAL` | 正常 | 最后有效发送结果为成功 |
| `ACCOUNT_BANNED` | 账号封禁 | 最后有效发送失败，且协议给出 `ACCOUNT_BANNED` 稳定原因码 |
| `GROUP_BANNED` | 群组封禁 | `CHAT_SUSPENDED`、`CHAT_TERMINATED` 或等价群封禁信号 |
| `NO_PERMISSION` | 没有权限 | `ANNOUNCE_ONLY_NON_ADMIN` 或等价无发言权限信号 |
| `KICKED_OUT` | 被踢出群聊 | `ACCOUNT_NOT_PARTICIPANT` 或等价成员缺失信号 |
| `UNCONFIRMED` | 未确认 | 元数据查询失败、身份无法识别、未知异常或无可判定结果 |

`UNCONFIRMED` 是必要兜底。需求要求“至少包含”前五类，不代表可以把未知异常错误归入其中任意一类。

### 4.1 判定优先级

对同一条最后有效发送记录按以下顺序归一化：

1. 发送成功 → `NORMAL`。
2. `reasonCode = ACCOUNT_BANNED` → `ACCOUNT_BANNED`。
3. `ACCOUNT_NOT_PARTICIPANT` → `KICKED_OUT`。
4. `CHAT_SUSPENDED` / `CHAT_TERMINATED` → `GROUP_BANNED`。
5. `ANNOUNCE_ONLY_NON_ADMIN` → `NO_PERMISSION`。
6. 仅有兼容期宽泛状态时，`BANNED` → `GROUP_BANNED`，`NO_PERMISSION` → `NO_PERMISSION`。
7. 其余情况 → `UNCONFIRMED`。

账号封禁优先于发送前缓存的群状态，避免账号已被封禁时仍展示过期的群组封禁或权限状态。

## 5. 执行情况

接口返回：

```text
executionResult: SUCCESS | FAILED | null
executionReason: string | null
```

展示规则：

- `SUCCESS`：绿色标签“发送成功”，不展示失败原因。
- `FAILED`：红色标签“发送失败”，并在同一单元格展示该次失败的标准中文原因。
- `null`：展示 `-`。

标准原因至少包括：

| 群组状态 | 执行原因文案 |
|---|---|
| `ACCOUNT_BANNED` | 账号封禁 |
| `GROUP_BANNED` | 群组已封禁 |
| `NO_PERMISSION` | 当前账号没有发言权限 |
| `KICKED_OUT` | 账号已被踢出群聊 |

无法归类的失败仍展示“发送失败”，原因优先使用经过脱敏的协议失败描述；描述也为空时使用“未知原因”。

`executionResult`、`executionReason` 和 `groupStatus` 必须从同一条最后有效发送记录派生，禁止分别按结果、时间或最近失败记录独立取值。

## 6. 数据流与跨仓职责

### 6.1 协议层 `armada-protocol`

- 保留 `groupStatus`、`groupStatusReason`、`groupStatusCheckedAt` 原始快照字段。
- 对消息发送异常增加稳定分类；明确的 401/403、`NEED_REAUTH` 等账号封禁信号输出 `reasonCode = ACCOUNT_BANNED`。群组封禁、无权限和被踢出继续通过现有 `groupStatusReason` 精确表达。
- 原始错误只用于日志和诊断，事件中的 `reasonMessage` 必须脱敏。
- 无法确认时继续发送通用失败码，不猜测业务状态。

协议层只报告事实，不生成中文页面文案。

### 6.2 后端 `armada`

#### 账号一级明细

- `MarketingTaskAccountTargetVO` 新增可空 `loginState`。
- 在线状态取打开详情时 `account_state.login_state` 的当前值：1=在线、2=离线、3=待上线、空=未知。
- Marketing 域通过 Account 域 Service 批量读取账号登录态，禁止跨域直接依赖 Account Mapper 或 Entity，且不得产生逐账号 N+1 查询。
- 发送账号继续使用任务创建时保存的账号号码快照，保证账号后续修改或软删后任务历史仍可识别。

#### 群组二级明细

- 在现有发送记录聚合基础上返回 `groupStatus`、`executionResult`、`executionReason`。
- 累计发送次数与最后有效发送记录分开计算，但最后有效记录的三个派生字段必须来自同一行。
- 群名称优先使用发送记录快照，再回退群预览或群链接记录；仍为空时允许前端回退 JID 或“未命名群组”。
- 保留旧兼容字段不影响本次展示，但前端不再展示群链接和独立最近原因列。

建议接口片段：

```json
{
  "accountId": 501,
  "accountPhone": "8613800000000",
  "loginState": 1,
  "sentMessageCount": 12,
  "groups": [
    {
      "groupJid": "120363001@g.us",
      "groupName": "营销群 A",
      "groupStatus": "NO_PERMISSION",
      "sentMessageCount": 3,
      "lastSentAt": 1784455200000,
      "executionResult": "FAILED",
      "executionReason": "当前账号没有发言权限"
    }
  ]
}
```

#### 租户隔离

- 详情主任务先按当前租户校验存在性。
- 发送记录、账号状态和群组辅助表查询继续由 MyBatis 租户拦截器约束。
- 不新增 `@IgnoreTenant`，不引入跨租户读取。

### 6.3 前端 `wheel-saas-pure-web`

- 一级使用 Element Plus 表格，一行一个账号。
- “在线状态”复用账号列表已有登录态标签映射。
- “明细”使用展开行；未产生实际群组发送记录时展示“暂无发送记录”。
- 展开内容严格按“群组状态、群名称、单群发送条数、最后发送时间、执行情况”排列。
- “执行情况”单元格同时承载结果标签和失败原因，不再保留独立“最近原因”列。
- 未知后端枚举统一回退“未确认”或 `-`，避免新增状态导致页面报错。

详情自动刷新不属于本次第 4、5 条的业务口径。本设计保留当前已提交的轮询行为，不调整其间隔、启停和错误提示策略；新字段必须能随现有详情刷新正常更新。

## 7. 边界与异常处理

- 账号已软删：保留账号快照和历史统计，在线状态展示未知。
- 账号没有任何成功发送：账号发送总条数为 0。
- 群组只有失败记录：单群发送条数为 0，最后发送时间为 `-`，执行情况展示失败及原因。
- 最新已确认结果成功、历史失败：群组状态为正常，执行情况为发送成功，不穿透历史失败原因。
- 最新已确认结果失败、历史成功：累计成功条数和最后成功时间保留，执行情况展示最新失败及其原因。
- 最新记录为跳过或待回执：不覆盖上一条成功或失败结果；没有历史有效结果时执行情况为 `-`。
- 未知协议错误：群组状态为未确认，执行情况仍展示发送失败及脱敏原因。

## 8. 数据模型、部署与回滚

### 8.1 数据模型

不新增表、列或索引。现有发送尝试表已经保存：

- `status`
- `reason_code`
- `reason_message`
- `group_status`
- `group_status_reason`
- `group_status_checked_at`
- `round_no`
- `attempt_no`

本次只扩展协议原因码、查询聚合和 API 字段。

### 8.2 发布顺序

推荐顺序：

1. 协议层：先发布稳定失败原因码，旧后端可继续按字符串存储。
2. 后端：发布统一状态与执行原因字段，旧前端会忽略新增字段。
3. 前端：最后切换到新字段和新层级。

该顺序保证滚动发布期间向后兼容。

### 8.3 回滚

- 前端先回退字段展示和状态映射。
- 后端再回退新增 VO 字段和聚合逻辑。
- 协议层最后回退失败原因分类。
- 无数据库变更，无数据回滚。

## 9. 验证方案

### 9.1 协议层测试

- 群正常且发送成功 → 成功回执。
- 401/403 或 `NEED_REAUTH` 明确信号 → 账号封禁稳定原因码。
- `CHAT_SUSPENDED`、`CHAT_TERMINATED` → 群组封禁原因。
- 公告群非管理员 → 没有权限。
- 当前账号不在参与者列表 → 被踢出群聊。
- 未知异常 → 通用失败，不误判五类状态。

### 9.2 后端测试

- 真库 DbTest 覆盖一个账号多个群、同群多个轮次和重试。
- 断言账号发送总条数、单群发送条数只累计成功回执。
- 断言最后成功后状态为正常，并清除历史失败执行原因。
- 断言最后失败时结果、原因、群组状态来自同一发送记录。
- 覆盖账号封禁、群组封禁、没有权限、被踢出、未确认五类失败归一化。
- 覆盖实时在线、离线、待上线、账号软删后的未知在线状态。
- 覆盖租户 A 不能读取租户 B 的任务、账号状态和发送记录。

### 9.3 前端测试

- 断言一级和二级字段名称、顺序及移除字段。
- 断言在线状态标签映射。
- 断言六种群组状态的中文文案和未知值回退。
- 断言发送成功不显示原因。
- 断言发送失败同时展示“发送失败”和对应失败原因。
- 断言零条数、空时间、空群组明细的展示。

### 9.4 联调验收

至少构造五种明确异常各一条发送记录，并验证协议事件、数据库 attempt、详情 API 和页面文案四层一致；账号封禁场景不得仅通过手工改库或前端 mock 验收。

## 10. 非目标

- 不调整营销任务创建、轮次调度、自动重试和账号占用规则。
- 不改变任务级状态机和任务列表统计。
- 不新增群组实时状态轮询或群状态历史表。
- 不修改建群营销和历史群营销页面；协议原因码应保持兼容，但本次验收只覆盖普通群组营销任务详情。
- 不以当前账号状态反写历史发送记录。

## 11. 当前已提交基础改动的后续处理

当前分支已有后端提交 `7dcf4ca` 和前端提交 `35ae2b6d`，完成了 `executionResult`、详情执行结果展示和轮询的第一阶段实现。后续实施必须在这些提交之上按本方案调整：

- 新增与最后有效发送记录同源的 `executionReason`。
- 将群状态扩展为本设计统一枚举。
- 失败原因合并进入“执行情况”，移除独立最近原因列。
- 二级字段按最终要求重排并移除群链接展示。
- 保留当前已提交的轮询能力，本需求不调整其交互策略。

## 12. 自检结论

- 需求范围可由一个跨仓实施计划完成，无需拆成独立子项目。
- 统计口径、最后有效发送记录、状态优先级和失败原因来源均已明确。
- 不需要数据库迁移。
- 没有待定字段或占位项；进入实施计划前只需用户评审本设计。
