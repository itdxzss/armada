# ADR-0011：新群模式的建群人落 `role_type=4`，建群与提权后退居二线

日期：2026-08-18
状态：已接受

## 背景

普通群链接版的角色模型（`pull_task_group_account.role_type`）已经是：

```
1=管理   2=拉手   3=站台   4=提权管理员
```

其中 `4=提权管理员`（V102 引入）的语义是「群内现有的我方群主或管理员，负责为任务管理员提权」。在群链接模式下，这是老群里我们本来就持有的账号。`PullTaskExecutionStage.MANAGER_ADMIN` 的实现（`PullTaskManagerAdminCandidateSelector`）正是从群域实时可用的管理员候选里挑这个角色。

角色 `1=管理` 指的是**次管理员**：踩链接进入目标群（`MANAGER_JOIN`），再由角色 4 提权（`MANAGER_ADMIN`），随后与拉手互加好友并轮询邀请拉手。

新群模式引入了一个群链接模式没有的账号——建群人。需要确定它落在哪个角色、承担哪些职责。

## 决定

1. **建群人落 `role_type=4` 提权管理员**，不新增角色取值。新群模式下这个槽位比群链接模式更可靠：群是本任务刚创建的，群主身份确定，无需在群内实时挑选候选。
2. **建群人只承担两项职责：创建群组、为次管理员提权。** 两项完成后不再参与后续阶段。
3. 建群人**不参与邀请拉手**，不执行拉人调用，不与拉手互加好友。
4. 建群人**不参与拉手跨任务互斥**：ADR-0008 的 `occupancy_key` 生成列保持只在 `role_type = 2` 时取值，本模式不修改该生成列与唯一索引。
5. 建群人**不自动退群**。「新建普群」的建群人自动退群策略不适用于本模式。
6. 次管理员（`role_type=1`）沿用群链接模式的既有链路：踩本任务生成的邀请链接进群 → 被建群人提权 → 与拉手互加好友 → 轮询邀请拉手。`MANAGER_JOIN` 阶段不需要为建群人增加跳过分支，因为建群人不在管理清单内。

## 影响

- `MANAGER_JOIN`、`MANAGER_ADMIN`、`MANAGER_PULLER_CONTACT`、`PULLER_INVITE` 四个阶段零改动。
- 拉手与建群人之间没有直接协议动作。建群人对拉手的影响只是间接前置：未完成次管理员提权，次管理员就没有邀请拉手的权限，链路在 `PULLER_INVITE` 断开。
- 建群阶段必须生成群邀请链接并持久化。新群没有用户输入的链接，而次管理员进群、ADR-0006 第 45 条的补充拉手、以及补充管理员的踩链接分支都依赖它；链接生成失败即阻断后续全部入群动作，必须作为建群阶段的完成条件之一，不能延后。
- `LINK_VALIDATION` 阶段对本模式无意义（链接由本任务生成）。建群阶段完成后直接把执行行阶段置为 `MANAGER_JOIN`，跳过该阶段，不修改 `LINK_VALIDATION` 的实现。

## 被否决方案

- **为建群人新增一个 `role_type` 取值**：角色 4 的既有语义「群内现有的我方群主或管理员」已经完全覆盖建群人在本模式中的职责，新增取值会让 `MANAGER_ADMIN` 的候选选择出现两条等价分支。
- **建群人继续参与邀请拉手**：需要修改 `PULLER_INVITE` 的轮询来源（当前只从角色 1 取），并额外定义建群人与拉手是否互加好友，收益仅是次管理员全部不可用时的兜底，不值得改动一个已稳定的阶段。
- **把建群人纳入拉手跨任务互斥**：建群人在同一任务内本就唯一，且完成提权后即退出执行，占用其他任务的资源没有收益。
