# 普通拉群成员查询异步化

## 问题

普通拉群的批次派发和“未知结果收敛”当前由同一个单线程调度器串行执行。收敛逐条同步 HTTP 查询群成员时，网络等待会占住该线程，导致已经到期的下一批拉人命令不能及时写入 Outbox。任务 50346754 中，14 条未知记录的收敛使第二批在配置的 6 秒之外额外等待约 21 秒。

## 目标与边界

- 批次派发与未知结果收敛使用不同执行器，互不阻塞。
- 普通拉群涉及的群成员事实读取改为 Outbox + Kafka 命令/结果事件。
- Web 与 Android 两种协议后端都支持该命令。
- 普通流程仍是：管理员与拉手双向加联系人，然后管理员邀请拉手进群；本次不改变业务阶段。
- 不迁移营销建群、营销拉群，也不顺带异步化群设置、进群等尚未证明存在调度阻塞的调用。

## 最小架构

### 调度隔离

`PullTaskExecutionDispatchScheduler` 只负责拉群执行行派发。新增 `PullTaskUnknownResultReconciliationScheduler`，独立单线程执行未知结果收敛，并提供带信号合并的 `trigger()`。两者继续依赖数据库租约、条件更新和现有任务顺序约束，不通过增加派发线程数规避串行问题。

### 一张查询表

新增一张短生命周期 `pull_task_member_query` 表，一行代表一次成员查询尝试，保存：租户、任务/群执行行、业务键、用途、协议账号/后端、群 JID、目标 JSON、结果 JSON、状态、尝试次数、`commandId`、请求/完成时间和错误信息。

不新增查询明细表、attempt 子表或 Redis 幂等状态。查询是只读操作，协议消费者只有在结果事件成功写入 Kafka 后才确认消息；重放一次成员读取是安全的。后端以 `commandId` 和查询行状态处理重复、迟到事件。

### 复用现有 Kafka 通道

- Web 命令复用现有 master command topic。
- Android 命令复用现有 group-action topic。
- 结果复用现有 group-events topic。
- Kafka key 使用协议账号 ID，保留账号内顺序。

仅新增逻辑类型：

- 命令：`group.members.query.requested`
- 事件：`group.members.result_reported`

Outbox 持久化查询引用，发布时由 hydrator 从查询表加载目标列表，避免大 JSON 在多处重复保存。创建查询行、创建 Outbox、绑定 `commandId` 必须处于同一事务，Kafka 仍只在事务提交后发送。

### 协议执行

协议消费者在现有账号/group operation gate 内读取群元数据，只返回所请求目标的成员事实，不回传无关完整名单。Web master 找不到账号 owner、Android 找不到账号或读取失败时，也发布明确的 FAILED 结果事件。

只读查询不建立新的协议层 Redis action state：结果发布失败时消息不确认，重读群成员并重发即可。

### 后端回写与唤醒

结果消费者严格校验账号、`queryId`、`commandId`、任务和执行行关联，只允许当前未完成查询落终态。重复结果幂等忽略，旧尝试的迟到结果不得覆盖新尝试。

结果提交后：

- 阶段查询将对应执行行的 `next_run_at` 提前到当前时间（仅在任务、阶段和租约条件仍匹配时），再触发派发调度器。
- 未知结果收敛查询触发独立收敛调度器。

不新增专用超时扫描器。调用方再次 `requestOrRead` 时识别已超时查询并创建下一次尝试，沿用现有阶段重试/收敛节奏。

### 不重复副作用

查询等待期间沿用现有动作状态 `SUBMITTED/UNKNOWN` 和 `verificationOnly`：

- 管理员邀请、设管理员、补位等动作提交后，等待查询只释放执行租约，不把动作退回待提交。
- 下次被结果唤醒时只验证成员事实，不重复发送邀请、进群或设管理员命令。
- 手工补拉手的 `JOIN_BY_LINK` 分支同样保持动作已提交状态；普通主流程的“互加联系人→管理员邀请拉手”不变。

## 验证与发布

- 用阻塞式测试证明收敛线程卡住时，派发仍能写入下一批 Outbox。
- 覆盖查询创建/超时/取消、结果重复/迟到、阶段精准唤醒、等待时不重复副作用。
- Web、Android 分别覆盖命令解析、账号 gate、结果过滤、无 owner/无账号和发布失败重放。
- 先部署 Web/Android 消费者，再按协议后端开启后端生产；全程复用现有物理 topic。
