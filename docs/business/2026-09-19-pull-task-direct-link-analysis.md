# 群链接模式（新）需求与执行依赖分析

日期：2026-09-19。用户已在后续消息授权在前后端主仓实施；当前不包含提交、推送、远程数据库操作或部署。实施进度与验证见 `.harness/changes/pull-task-direct-link/summary.md`。

源码基线：后端 `armada` / `1.0.3-snapshot` / `0bb0a688`；前端 `wheel-saas-pure-web` / `1.0.3-snapshot` / `b96bdd90`。仓库存在其他会话工作，本分析不处理这些改动。以下源码事实不代表第二套环境当前运行版本或业务验收结果。

## 已确认需求

- 在现有“群链接模式”旁新增“群链接模式（新）”tab，旧模式保持原行为。
- 新模式移除整个“执行策略”和“群信息设置”模块，移除“账号分组”中的管理分组。
- 管理员准备、原管理员清理、账号互加好友作为独立前置工作；新模式直接使用拉手踩链接进群并拉人。
- 用户补充确认：新模式取消 TXT 料子中 A/a 标记触发的管理员提权，只负责进群和拉人。
- 用户再次明确：拉手按普通成员使用，不需要提权为管理员；新模式不要草稿，只保留创建、执行、详情。
- 用户已授权在主仓编写代码；无需再次确认实施。提交、推送和部署不在本次授权范围。

## 页面与行为边界

| 内容 | 新模式建议 |
| --- | --- |
| 相邻 tab | 新增“群链接模式（新）”，创建、列表、详情均识别 |
| 草稿保存、恢复、清空与草稿任务 | 新模式全部取消；填写期间仅保留当前页面输入，点击创建后才生成正式任务 |
| 群组分组、手工链接、TXT、数据包 | 保留现有来源与匹配方式 |
| 任务名称、自动启动、备注 | 保留 |
| 拉人数范围、间隔、拉手数、前期拉人数/次数、并发群数 | 保留本次未要求移除的拉人参数 |
| 拉手分组、拉手完成归档 | 保留 |
| 站台数量/分组 | 按现有范围保留可选，0 表示不用站台 |
| 管理分组、管理完成归档 | 一并移除；不分配管理角色，不等待管理号 |
| 执行策略 | 不展示；链接入群成为新流程固定行为 |
| 群信息设置 | 不展示，不执行名称、头像、公告、权限等设置 |
| 清成员、群主退群、料子提权 | 不执行 |
| 任务内互加好友 | 同时跳过管理↔拉手、拉手↔站台两处 |
| 入群/拉人结果、补拉手、暂停恢复、结束、资源释放 | 保留并适配新流程 |

“保留”项是基于用户只要求删指定模块的范围判断，不增加其他业务功能。对 A/a 料子建议继续识别号码，仅让标记失去提权含义，并在导入提示明确说明；不修改源文件，也不让该标记生成待提权事项。具体解析兼容需在实施时用旧料子样例验证。

## 当前链路与建议链路

旧流程的主要路径：

`管理进群 → 管理提权 → 开放普通成员加人等设置 → 管理/拉手互加 → 拉手入群 → 拉手/站台互加与拉人 → 料子提权等收尾 → 完成`

其中拉手入群已有“自己踩链接”的可选分支，但分配拉手、群身份、失败恢复等仍依赖前面的管理流程。

新流程建议：

`填写参数并选择群与料子 → 点击创建，一次生成正式任务 → 分配拉手 → 拉手以普通成员身份踩链接进群 → 确认入群并绑定真实群 ID → 按现有参数拉人 → 回执结算、释放资源、归档 → 详情查看结果`

若使用站台，站台仍按现有批次加入，但新模式不再执行联系人保存。无加人权限、等待审批、链接失效、拉手不足、结果未知需要有可区分的明细。等待审批或结果未知不能当成已入群，不应盲目重复提交。

## 普通成员权限与已有准备能力

拉手无需成为管理员，不将管理员身份或提权成功作为新模式的准入条件。此前关于管理员交接的分析仅用于厘清现有能力，不构成新增拉手提权需求。普通成员是否可加人是另一项群权限；新模式不改群权限，执行中遇到限制时明确记录实际结果。

1. 进群任务给该条进群明细的账号设置管理员，不会自动给以后拉群任务选中的另一批拉手提权。证据：`JoinTaskAdminFacts.java:45-87`。
2. 清理原管理员执行的是成员移除和原号退群，不包含开放普通成员加人。证据：`JoinTaskCleanupProtocol.java:30-73`。
3. 进群任务仅在遇到 `PENDING_APPROVAL` 的恢复路径关闭审核，不能从某条普通进群成功推出后续拉手无需审核。证据：`JoinTaskResultServiceImpl.java:195-223`、`JoinTaskApprovalProtocol.java:35-43`。
4. 旧拉群的 `OPEN_MEMBER_ADD` 是独立后台动作，即使页面不显示群信息模块，也不能假定该权限已准备好。证据：`PullTaskManagerPullerContactTransactionService.java:120-162`、`PullTaskGroupSettingsPayloadHydrator.java:120-124`。
5. 账号互加任务按创建时两个分组的合格在线账号建立双向配对；不自动包含后来补入的账号。双向回执成功才是互加完成。证据：`AccountMutualContactServiceImpl.java:87-97,138-178`、`AccountMutualContactMapper.xml:33`。

新模式按拉手普通成员进群、直接拉人设计；遇到群权限不允许或进群待审批，记录明确结果，不自动补管理、提权或修改群设置。本需求不扩展进群任务的权限设置功能。

## 无草稿创建

现有创建链依赖草稿：前端初始化读取 `/standard/draft`，上传匹配调用 `/draft/plan`，数据包调用 `/draft/data-packages`；后台在匹配时调用 `ensureDraft` 和 `append` 写入草稿任务与料子，正式提交必须携带 `draftTaskId`。证据：前端 `useStandardPullTaskCreate.ts:235-271,405-468,540,580`；后端 `PullTaskStandardDraftServiceImpl.java:144-174`、`PullTaskStandardDraftWriter.java:62-101`、`PullTaskStandardCreateTransactionService.java:100-103`。

新模式采用独立的直接创建合同：

1. 当前页面暂存参数、文件、群链接/群分组选择和数据包选择，不自动保存或恢复任务草稿，不读取或删除旧模式草稿。
2. 点击“创建任务”一次提交全部创建输入，入参不含 `draftTaskId`；服务端复用解析、匹配算法，重新校验真实群与数据包来源，不能直接信任前端预览的计数和成员结果。
3. 校验通过后，在事务内写正式任务、配置、执行行、料子与需要的资源占用；失败回滚，不遗留半成品任务。重复提交需有幂等保障。
4. 自动启动开启时，提交成功后启动；关闭时直接形成正式“待启动”任务，待启动不属于草稿。
5. 如创建页需要提前显示匹配预览，可使用不写任务、不占资源的校验能力；预览仅辅助输入，不引入保存、恢复或提交草稿步骤。

旧模式的草稿服务和行为保留；新模式不复用会创建草稿的编排，仅复用解析、校验、匹配等可独立调用的能力。

## 建议的技术隔离

- 保留当前 `mode=NORMAL_LINK` 的公共调度族语义，不贸然改值；它被多处准入条件使用。
- 实施采用 `creationMode=DIRECT_LINK`，复用现有任务聚合中的创建模式作为唯一身份，不另增重复的 executionFlow 列。统一适配群来源判断、分组使用保护和换群；旧草稿/提交接口拒绝该新值，新模式仅通过直接创建入口进入。
- 该模式从一次创建正式任务开始持久化，覆盖读回、列表、调度及恢复；不根据管理分组是否为空推断新旧。新增执行阶段 `DIRECT_PULLER_JOIN(10)`，已有阶段值不变。
- 旧客户端不传新标识时默认旧流程；存量任务继续旧流程。新模式的禁用操作由服务端约束，不能仅靠前端关闭控件。
- 新建拉手准备/入群分支，复用料子解析、账号占用、批次拉人、回执、计数、暂停恢复和收口。避免复制整套旧流程。
- 新模式使用独立直接创建入口和页面输入状态，不加载旧草稿、不调用写草稿的上传匹配接口；切换 tab 不将旧模式隐藏设置或草稿带入新模式。
- 详情/列表显示“群链接模式（新）”，隐藏管理资源和补管理入口；不显示虚假的管理缺口、待提权、群设置完成状态。
- 保留现有租户和创建人校验；账号、群来源、回调、占用仍按 tenant/task/execution/account 定位。
- 数据变更只通过 Flyway；本轮未添加迁移、未选择迁移版本。实施时重新确认模型和所有新模式必填项，不能填假 ID 或假名称绕过旧 NOT NULL。
- 不新增 Redis 队列、锁或独立调度系统；若实施需要变更现有恢复机制，应由具体证据支持。

## 后续验证与发布边界

实施后重点验证：旧模式行为；新模式填写/预览不生成任务、创建失败无残留、一次创建生成正式任务、重复提交不重复建单；无管理分组创建和启动；切 tab 不带旧设置、不读取或破坏旧草稿；普通成员拉手无需提权即可进入拉人流程；首拉手成功入群绑定群身份后真实拉人；审批/权限错误准确展示；补拉手和换群始终走新入口；含 A/a 料子不会进入提权；有/无站台均不发送互加联系人动作；暂停恢复与完成归档正确。

分析阶段未运行测试；实施阶段使用隔离构建副本中的单测和 H2/真实 Mapper 测试覆盖上述逻辑，实际结果记录于实施 summary。部署和真实账号业务验收需另行确定环境。发布需后端/迁移支持后再开放前端新 tab。回滚时先停止创建新模式任务，对在途新流程任务做明确处置，不能将其交给不认识新流程的旧后端继续执行。

## 结论

新模式的产品范围是“创建、执行、详情”，拉手以普通成员身份踩链接进群并拉人，无草稿、无管理分组、无提权。后端需要一次创建正式任务、独立拉手入群入口，并补齐群身份及恢复路径；继续复用现有拉人和结果能力。
