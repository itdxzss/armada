# ADR-0009：本期不做人工操作审计表，幂等改由状态前置校验与乐观锁承担

日期：2026-08-02
状态：已接受

## 背景

需求确认：任何人工操作都需要幂等 requestId、状态复核、租户校验和审计。第一版数据模型为此建了 `pull_task_operation_log`，靠 `UNIQUE (tenant_id, action_type, request_id)` 同时承担两个职责——人工操作幂等键，以及操作前后状态的审计留痕。

用户明确要求本期不做审计日志。删表就必须为幂等另找落点，否则重复提交会产生重复副作用。

仓库现状核对：没有通用审计表可以借用，只有 `account_online_attempt_log` 这类单业务表。

## 决定

- 本期不建 `pull_task_operation_log`。
- 人工操作幂等改由状态前置校验 + 乐观锁承担，不引入任何幂等记录表：

  | 操作 | 机制 | 重复提交的结果 |
  |---|---|---|
  | 暂停 / 恢复 / 结束（任务级） | `UPDATE pull_task SET status=?, version=version+1 WHERE id=? AND status IN (合法前置态) AND version=?` | 第二次发现已是目标态，返回当前状态视为成功 |
  | 暂停 / 恢复 / 放弃（单群） | 同上，作用于 `pull_task_group_execution.version` | 同上 |
  | 补充管理员 / 拉手 / 站台 | 服务端校验 `当前数 + 补充数 <= 计划数`；手动选号时由 `UNIQUE (tenant_id, group_execution_id, role_type, account_id)` 吞掉重复 | 手动选号无副作用；自动选号超出计划数时被拒 |

- 生命周期操作天然是状态收敛型操作，"再暂停一次已暂停的任务"没有第二次副作用，因此不需要请求级幂等键。
- 补充资源的语义固定为"补足到计划数"，其上界由 `pull_task_standard_setting.required_manager_count` 和 `puller_count_per_group`、`station_count_per_call` 给出，重复提交无法突破上界。
- 复制任务不在本期范围（见需求拆分第 58 条），因此不存在"重复提交生成两个任务"的敞口。

## 影响

- **明确损失**：谁在什么时候暂停、恢复、结束或补充了资源，不留任何痕迹。排查线上问题时只能看到状态和时间戳，看不到操作者。
- 该表是纯追加的：将来要补，只是一个新增表的迁移，不改动本期 6 张表的任何字段，也不改动上述幂等机制——审计表加回来时它记录事实，幂等仍由状态机承担。
- 自动选号的补充操作在缺口窗口内被重复提交时，两次可能选中不同账号；由于总数受计划数上界约束，效果有界且不产生超额资源。这是接受的残留风险。
- 所有写操作仍必须做租户校验；租户隔离不依赖审计表。

## 被否决方案

- **保留审计表**：用户明确要求本期不做。
- **删表但保留一张纯幂等键表**：只为幂等建表，收益低于直接用状态机；且生命周期操作本身就是幂等的，幂等键属于重复防护。
- **给 `pull_task` 加 `create_request_id` 列**：该列原本是为复制任务的重复提交准备的，复制任务取消后不再需要。
