# 普通拉群任务群封禁终止设计

## 目标

当 WhatsApp 明确返回群已暂停或终止时，将群组标记为封禁，并立即把该群对应的普通拉群执行行推进为失败终态，停止该群后续调度与结果重试；同一父任务下的其他群继续执行。

## 触发条件

仅接受同时满足以下条件的 WhatsApp 明确群封禁事实：

- 群健康事件 `health=BANNED`；
- 原始原因是 `CHAT_SUSPENDED` 或 `CHAT_TERMINATED`。

普通 `403`、`TEMPORARY_FAILURE`、账号离线或代理失败均不能推断为群封禁。

## 处理流程

1. 现有 `group.health_reported` 消费链路接收并校验群健康事件。
2. 群域按现有逻辑将 `group_link_health` 写成封禁状态。
3. 对明确的 `BANNED` 事件，调用任务域的群封禁终止服务。
4. 任务域在事件租户上下文内，按解析后的群入口或群 JID 定位普通群链接任务的非终态执行行。
5. 命中的执行行写成：
   - `execution_status=FAILED`；
   - `reason_code=GROUP_BANNED`；
   - `reason_message=群已被封禁`；
   - `finished_at` 为事件处理时间；
   - 清空资源等待、调度租约，并把 `next_run_at` 置零。
6. 取消该执行行尚未发布的协议命令和计划事实，释放该执行行占用的拉手。
7. 将 `GROUP_BANNED` 执行行排除出未知结果收敛候选，避免后台继续查询群成员或重新收敛该群。
8. 调用现有父任务终态聚合：其他执行行未结束时父任务保持 `EXECUTING`；全部执行行终态时父任务进入 `COMPLETED`。

## 状态与幂等性

- 仅允许 `WAIT_START`、`EXECUTING`、`WAIT_RESOURCE` 推进为 `FAILED`。
- 已经处于 `COMPLETED`、`FAILED` 或 `ABANDONED` 的执行行不再修改。
- 重复的封禁事件不会重复终止、重复释放资源或改变父任务结果。
- 后续群健康恢复不会自动恢复已经失败的执行行；需要新建执行计划才能再次处理该群。
- 已经发送到协议层、无法撤回的命令允许返回迟到结果，但迟到结果不得重新激活失败执行行。

## 领域边界

群域仍负责持久化群健康事实，任务域负责执行行终止、命令取消和资源释放。现有群健康事件适配层在完成封禁落库后调用任务域服务，不新增 Kafka topic、数据库表或定时扫描任务。

## 错误处理

- 群健康落库失败时抛出异常，由现有 Kafka 机制重投。
- 群健康已落库但任务终止失败时同样抛出异常；重复投递会幂等重放封禁落库并再次尝试任务终止。
- 找不到关联的非终态普通拉群执行行时只记录业务日志，不创建任务数据，也不影响群封禁事实。
- 所有查找和写入均受事件 `tenantId` 限制，不允许跨租户匹配。

## 测试范围

- `BANNED/CHAT_SUSPENDED` 与 `BANNED/CHAT_TERMINATED` 会触发任务终止。
- 普通不可用、临时失败和非封禁健康事件不触发任务终止。
- 仅命中的群执行行进入 `FAILED/GROUP_BANNED`，同任务其他群保持原状态。
- 终止时取消该群未发布命令、释放该群拉手，不影响其他群事实。
- 被封禁执行行不会进入未知结果收敛候选。
- 重复封禁事件幂等；终态行和跨租户行不被修改。
- 最后一条执行行终止时父任务完成；仍有其他非终态执行行时父任务继续执行。

## 不在本次范围

- 不根据普通 HTTP 403 或临时操作失败推断群封禁。
- 不停止整个父任务。
- 不自动恢复已失败的执行行。
- 不修改群封禁解除策略。
- 不部署或修改测试环境数据。
