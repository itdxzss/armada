## 当前链路的具体缺口

1. `PullTaskPullCallReconciliationService.reconcile` 只对已提交 attempt 收口，掉线或到达结果窗口时固定传 `UNCONFIRMED`，不读取群域入群事实，不查询名单。两个核心文件与当日 perf2 发布源快照一致；相关日志也证实运行行为。`PullTaskPullCallReconciliationServiceTest.fifteenSecondWindowReleasesExplicitUnknownAndMissingCallbackWithoutRosterQuery` 锁定了这一旧行为。
2. `PullTaskUnknownResultReconciliationService` 的 `legacySnapshotRequired` 将有 attempt 台账的新批次排除在该批次成员查询需求之外；`reconcileCalls` 又跳过已 WRITTEN_BACK 的调用。执行行 215 当前 `pull_task_member_query` 查询结果为零行。扫描器可以因为 material UNKNOWN 继续选中执行行，但不能靠重复扫描消除这些 CLOSED/UNKNOWN。
3. `ProtocolGroupParticipantChangedSinkAdapter -> ProtocolGroupJoinSinkImpl -> WhatsappGroupMemberJoinFactServiceImpl` 已把 ADD 事件写入当前群模型。`saveLatest` 实际调用 `AccountGroupCurrentSnapshotPersistenceImpl.applyParticipantJoins`，读取服务也从 `wa_group_participant.last_joined_at` 获取事实。该路径没有向普通拉群 attempt 结果应用服务传播成功事实。
4. `PullTaskPullCallParticipantResultService` 支持 CLOSED/UNKNOWN 的迟到成功提升聚合，但名单 settlement 仅接收 SUBMITTED，不能直接套在本次已关闭记录上。迟到 FAILED 只更新旧 attempt，不更新料子聚合；后续仍可能展示未知，需要在没有更新尝试或成功事实时补齐结果一致性。`alreadyApplied` 只比较生命周期、outcome、executionState，新的 TIMEOUT 原因可能被视为重复，从而保留通用文案。
5. Web `group-participants-executor.ts` 超时后存储 UNKNOWN 并发布，原 promise 仅用于持有操作锁，后续返回值没有继续解析/补报成功。重复原 commandId 读取的是已缓存结果，不能作为主动核实方式。补报若继续复用原 eventId，必须检查消费幂等，避免新事实被去重丢弃。
6. 群成员查询可以复用，但不能直接把其当前 `inGroup=false` 当重试依据：Web `group-members-query-executor.ts/memberFacts` 将 participants 缺失当空数组，按 id/lid/phoneNumber 精确匹配不到就返回 false。只有 LID、号码映射不全或成员集合不可靠时，应属于“无法确认”，不能视为不存在。当前完整快照时间为 2026-09-18 01:02:09.364，早于本批，不能拿它作缺席证明。

## 建议方案：先收敛已有事实，再处理剩余不确定结果

### 第一阶段：让有证据的未知自动变成确定结果

- 复用现有核实调度器、attempt 台账和群域事实服务，增加针对 CLOSED/UNKNOWN 的只读事实核实及事务内结果应用入口。优先按当前执行行、原批次、目标名单批量查询，避免扫描整个群或整个历史任务。
- 严格匹配 tenant、group JID、冻结目标 PN/LID 映射及入群事件时间；事件必须在相关执行时间窗内。既有老成员只能标注“确认已在群”，不能倒推本次原命令成功；历史多轮任务不得任意归因。
- 成功应用在执行行锁和 CAS 下执行：更新 attempt 的已核实结论、料子聚合、计数和数据包结果。保留原始超时原因和核实事件来源；不能直接用手工 SQL 把状态改成成功。若现有字段无法分别保存原始回执和核实依据，再对最小字段扩展作模型评估，不先创建新事实平台或新表。
- 复用迟到成功的保护逻辑：已成功不回退；新计划尚未提交时移除相应目标；新命令已提交时保留审计并收敛聚合，不能声称已撤销外部请求。
- 对已完成/已结束任务允许“有证据的结果纠正”，不自动重启任务、提权、发消息或补拉。需要后续业务动作的恢复必须走明确的恢复入口。
- 对本次执行行 215，五个目标均可按已落库 ADD 事实确认历史入群成功。首次修复后对这 5 行做定向修复预览及验收，不顺带批量恢复其他 CLOSED 任务。

### 第二阶段：没有入群事实时主动查询和有界恢复

| 核实结果 | 处理 |
|---|---|
| 有本次时间窗内可靠 ADD 事件或明确成功回执 | 确认入群成功；后续退群独立展示 |
| 查询确认已在群 | 核实成功，标明来自名单，不伪造原命令成功回执 |
| 完整、新鲜且身份匹配可靠的名单确认不在群 | 先排除成功后退出，再根据原调用是否已结束决定是否进入补拉 |
| 查询失败、无在线观察者或号码/LID 映射不全 | 显示具体“待核实/等待查询账号/身份未匹配”原因，按有界轮次切换观察者 |
| 群封禁、无权限且无法取得事实 | 结束自动核实并给出明确人工处理原因；不伪造成拉人失败 |

- 按群/异常批次合并查询，优先使用已经在群且在线的其他受控账号，复用异步 `PullTaskMemberQueryService` 与 Outbox。查询成功缓存必须带本轮/时间窗语义，不能永久读取旧名单。核实次数、下次时间和截止时间要可持久恢复；现有 `pull_task_member_query` 与 call 的 roster 字段优先评估复用，避免新增全局队列。
- 一个未确认批次不能拖住无关后续号码；但是不能在还有自动核实工作时仅展示“全部完成”。区分“拉人执行结束、结果核实中”和核实已完成；截止后仍无证据必须明确说明阻塞原因和处理动作。
- 仅仅“等待了 30 秒”或“快照里没看到”都不等于原调用不再生效。原 promise 仍可能执行时，自动补拉不能宣称无重复风险。可靠缺席且原调用结束/明确未开始时复用现有补拉波次、换拉手、次数上限和退避；无法排除迟到副作用的补拉须有明确风险策略，不能把 TIMEOUT 全部加入无条件重试白名单。
- Web 查询契约应能表达 PRESENT/ABSENT/UNCONFIRMED 以及快照时间/完整性，缺失 participants 必须失败而不是全体缺席；有可信映射才把 LID 对齐号码。Android 共用此契约时也需要同等验证，不能仅改 Java 后假定两端成立。

### 第三阶段：减少原始回执漏收敛

- 保留 Web 超时后原调用的最终结果；若后续明确成功/失败，使用可演进的结果版本/事件身份补报，并同步缓存状态。副作用幂等仍绑定原 commandId，不能为了补结果再执行原命令。
- 改善结果解释：例如“拉手掉线，调用超时；已从另一账号的群事件确认入群”，以及“已拉入，后续主动退群”。真实执行失败与核实失败分开呈现。
- 代理掉线及 403 重认证属于账号可用性治理，能够减少异常，但即使代理稳定也需要上述事实收敛，不能用延长 12 秒超时替代。

## 影响范围和边界

- 后端：逐成员结果事务、核实调度、候选 Mapper、群域事实查询服务、波次/完成状态、数据包投影。跨域通过 Service，不让 task 直接依赖 group Mapper。
- 前端/API：现有逐号码接口有 pullStatus/pullReasonCode/pullReasonMessage，但无核实轮次、核实依据与后续离群表达。需要在创建/执行策略、明细、任务完成展示之间保持同一语义。新增状态字段优先采用增量兼容方式，不重编号原枚举。
- 协议：成员查询三态及完整性是可信缺席补拉的前置条件；迟到结果补报是独立增强。第一阶段读取已有 ADD 事实不依赖发起新的 WhatsApp 请求。
- 数据库：本次无变更；已有表可覆盖主要事实。若实现需要保存结果来源/核实调度状态，应先明确字段归属和现有字段不能覆盖的理由，再走 Flyway。
- 回滚：普通代码回滚不能撤销已发生拉人。第一阶段只纠正有证据的结果，不启动外部动作；补拉阶段应独立开关，关闭停止新补拉并继续接收原结果。历史修复记录保留，不能回滚成无事实的未知。

3. 迟到明确失败只纠正当前归属未知，不覆盖成功或新尝试；同 outcome 不同原因不会丢失诊断。

5. LID-only、缺失/不完整名单、旧快照不能触发补拉；先成功后退群不能当原失败补拉。
6. 补拉计划与迟到成功并发时幂等收敛；旧调用尚未结束不得假设安全重试；重复计数和释放错误必须覆盖。

## 用户确认后的本地实施

用户后续明确选择：未知先读取本地已有入群事实；无事实则接受一次换拉手补拉，不增加远端成员查询，也不再追加结果等待。此选择替代上文第二阶段的主动名单查询方案。原命令仍可能迟到生效，补拉不被描述为“已确定原调用失败”。

- `PullTaskUnknownParticipantRecovery` 通过群域 Service 定点读取同租户、同群、同号码、执行时间窗内的 `wa_group_participant.last_joined_at`。保留入群后离群的成功事实；执行结束后的新入群不归因给旧任务。
- 回执处理、既有未知核实调度、补拉提交前均能收敛本地成功事实。复用执行行锁、条件更新、迟到成功保护及数据包结果投影，已计划但未提交的同号码补拉会被取消。
- 当前 SUBMITTED 未知可释放一次补拉。授权码 `UNKNOWN_RESULT_RETRY_ONCE` 保存在原 attempt 的原因字段；迟到非成功不能擦除该标记。后继无论未知、超时或账号受限都不能继续补拉，且保留总尝试预算上限。
- 后继批次排除该批次所有目标原来使用的账号；没有其他可用拉手时等待资源，不复用原拉手，也不把仍在线原账号标为离线。
- 免除新增结果等待及原有 60/120/240 秒补拉退避。沿用现有波次顺序，在当前波次收口后规划后继，未改成抢占正在执行的普通批次；等待资源仍需有合格拉手后才能执行。
- 已关闭历史未知只纠正可靠成功事实，不自动重启已完成、停止或暂停任务。不触发远端群成员列表查询，无数据库结构变更。
