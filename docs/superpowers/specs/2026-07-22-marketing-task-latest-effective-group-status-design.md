# 营销任务明细最近有效群状态设计

## 1. 背景

普通群组营销任务详情当前从同账号、同群的最新成功或失败发送记录派生群组状态。当安卓账号离线时，协议无法查询群元数据，会为本轮全部群返回：

- `reasonCode = ACCOUNT_OFFLINE`
- `groupStatus = UNCONFIRMED`
- `groupStatusReason = STATUS_RESOLUTION_UNAVAILABLE`

因此一次账号离线会把此前已经确认的正常、群组封禁或无权限状态全部覆盖为“未识别”。测试环境任务 62 的相邻轮次已经验证：账号在线时各群状态分布稳定，离线轮次全部变为未识别，恢复在线后又恢复原分布。这是详情聚合口径问题，不代表所有群真实状态同时变化。

## 2. 已确认业务口径

- 群组状态展示该账号、该群最近一次有效识别结果。
- 账号离线造成的无法识别不是有效群状态，不覆盖历史有效结果。
- 最新一轮执行结果独立展示；例如群组状态仍为“正常”，执行情况可以是“发送失败 / 安卓账号当前不在线”。
- 如果该账号、该群从未产生有效群状态，继续展示“未识别”。
- 暂不增加账号在线检测，也不改变营销任务调度、暂停恢复或重试逻辑。

## 3. 方案选择

### 3.1 采用：查询层选择最近有效群状态

在现有 `attempt_facts` 基础上标记发送记录是否包含有效群状态证据。`latest_protocol` 优先选择有效证据，再按 `roundNo DESC, attemptNo DESC, attemptId DESC` 选择最近记录；如果完全没有有效证据，则回退到最近一条成功或失败记录，以保留“未识别”兜底。

`latest_ended` 继续独立选择最新已结束记录，负责执行结果和执行原因。两个维度分别取值，但每个维度内部的状态、原因及原始字段必须来自同一条记录。

优点：

- 不修改数据库结构。
- 不依赖协议进程内缓存，服务重启后语义不变。
- 聚合继续在数据库完成，不增加全量历史记录传输或 Java 内存归并。
- API 枚举和前端展示结构不变。

### 3.2 不采用：Service 层读取历史后归并

该方案需要增加查询或加载更多记录，并在 Java 中重复数据库窗口排序逻辑，性能和一致性都更难控制。

### 3.3 不采用：新增最近群状态持久化表

该方案需要数据迁移、历史回填和写入链路改造。对于本次只修复详情读取口径的需求，影响面过大。

## 4. 有效群状态判定

一条成功或失败发送记录满足以下任一条件时，视为包含有效群状态证据：

1. 发送成功。实际成功是群组可发送的最高优先级事实，状态归一为 `NORMAL`。
2. 原始群状态为 `NORMAL`、`BANNED` 或 `NO_PERMISSION`。
3. 稳定原因码或群状态原因为以下可归一化信号之一：
   - 账号封禁：`ACCOUNT_BANNED`
   - 被踢或不在群：`KICKED_OUT`、`ACCOUNT_NOT_PARTICIPANT`
   - 群组封禁：`GROUP_BANNED`、`BANNED`、`CHAT_SUSPENDED`、`CHAT_TERMINATED`
   - 没有权限：`NO_PERMISSION`、`ANNOUNCE_ONLY_NON_ADMIN`

以下记录不构成有效群状态证据：

- `ACCOUNT_OFFLINE + UNCONFIRMED + STATUS_RESOLUTION_UNAVAILABLE`
- 元数据查询失败、身份无法识别或其他只能归一为 `UNCONFIRMED` 的未知结果
- 已提交但尚未结束的记录
- 业务跳过记录

账号封禁虽然不是群本身状态，但它是现有详情群状态枚举中的明确业务状态，因此仍作为有效识别结果保留。

## 5. 查询与对象边界

### 5.1 最近有效群状态

`latest_protocol` 的排序口径调整为：

1. 有效群状态证据优先；
2. 同一证据类别内按轮次、尝试序号和记录 ID 倒序。

这样存在历史有效状态时，最新离线未识别记录不会覆盖它；完全没有有效状态时，仍返回最近未识别记录。

### 5.2 最新执行情况

`latest_ended` 保持按最新轮次选择成功、失败或跳过记录，并额外映射该记录自己的原始群状态和群状态原因。`MarketingTaskAccountGroupStatRow` 因此分别承载：

- 最近有效群状态记录的状态、原因及原始群状态字段；
- 最新已结束记录的执行状态、原因及原始群状态字段。

Service 生成执行原因时只使用最新已结束记录自己的字段，禁止使用较早的有效群状态字段。例如：

```text
群组状态证据：第 86 轮 NORMAL / GROUP_SEND_ALLOWED
最新执行记录：第 87 轮 FAILED / ACCOUNT_OFFLINE

页面结果：群组状态=正常；执行情况=发送失败；原因=安卓账号当前不在线
```

### 5.3 归一化补充

失败发送也可能携带 `NORMAL / GROUP_SEND_ALLOWED`，表示群状态检测正常、但消息因为其他原因发送失败。此时群组状态应归一为 `NORMAL`，执行结果仍为 `FAILED`，失败原因取该次发送失败记录。

## 6. 兼容性和非目标

- 不新增或修改表、列、索引。
- 不修改 HTTP 接口字段或前端枚举。
- 不修改协议回执契约。
- 不修改发送计数、最后成功时间、任务状态或账号状态口径。
- 不实施在线检测。
- 不部署、不操作远程数据库、不修改测试环境数据。

## 7. 验证方案

采用测试先行，覆盖以下场景：

1. 历史成功 `NORMAL`，最新失败为账号离线且 `UNCONFIRMED`：群组状态保持 `NORMAL`，执行结果为 `FAILED`，执行原因为账号离线。
2. 历史为 `BANNED / CHAT_SUSPENDED`，最新失败为账号离线：群组状态保持 `GROUP_BANNED`，执行原因仍为账号离线，不被历史群封禁原因污染。
3. 只有账号离线未识别记录：群组状态为 `UNCONFIRMED`。
4. 最新发送失败但检测为 `NORMAL / GROUP_SEND_ALLOWED`：群组状态为 `NORMAL`，执行结果为 `FAILED`。
5. 后续恢复在线并发送成功：新的成功记录正常覆盖此前有效状态和离线执行结果。

验证层级包括：

- `MarketingGroupExecutionNormalizerTest`：纯归一化规则。
- `MarketingTaskMapperSqlShapeTest`：窗口排序和执行字段来源。
- `MarketingTaskCreateReadDbTest`：真实 MySQL 聚合结果与接口语义。
- 后端相关单元测试及模块测试。

真库 DbTest 仅在确认 `armada-api/.env` 指向获准测试库后运行。
