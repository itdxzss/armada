## 方案与边界

1. 服务端许可新增可选 `providerId`，严格校验为单个正整数字符串；请求体不能覆盖。许可固定商家时直接按用户明确选择传唯一 providerIds，不按报价换商家、不自动回退；仍传 maxPrice 并精确核对成交价。
2. `account_registration_task.provider_id` 属于采购任务的不可变约束，与 country_id/price 同聚合。现有列没有商家筛选事实；新增一个 nullable 列，不新增表，任务创建写入、worker 和许可一致性检查读取。旧自动报价任务保留 NULL。V197 迁移，禁止手改远程 schema。
3. 更换本设备的服务端 requestId，保留设备认证配置，手机无需输入配置。部署前核对旧任务仍为确定失败且未分配号码；旧任务不删除、不重置。新许可配置本身不会创建任务或采购。
4. r6 手动开始时先读取许可。仅当服务端明确返回新的未开始许可、旧本地任务无号码且未提交号码/验证码/成功回报时允许领取；旧本地状态可为 FAILED/CANCELLED，或因断线落后的 START_INTENT/PENDING/PURCHASING，服务端始终要求旧任务已确定失败且无订单。用户确认商家、价格后才替换本地任务。旧记录待确认期间保持不变；后台轮询不会自动换许可。
5. 本次新许可还携带 `replacesRequestId`，手机校验它必须等于旧请求，避免把任意失配当作重试。服务端只对确定失败且无号码/订单的旧请求认可这一引用。
6. 未完成采购状态、UNKNOWN、已拿到号码、成功、待回报均不自动重置。接码、原生注册之后仍不执行任何导入或上线工作。
7. `/start` 必须带仅一个 `requestId` 字段且与当前许可相等；旧包的 `{}` 或过时请求 ID 被拒绝，不能因服务端换许可而采购新订单。
