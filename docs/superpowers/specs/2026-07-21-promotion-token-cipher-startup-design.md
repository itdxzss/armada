# 推广 Token 加密组件启动修复设计

## 问题

`PromotionTokenCipher` 同时保留生产构造器和便于单测注入 `SecureRandom` 的构造器，但没有明确告诉 Spring 应使用哪个构造器。Spring 在创建组件时无法完成构造器选择，最终按无参构造器实例化并报出 `No default constructor found`，导致整个应用上下文启动失败。

此外，应用配置已经引用 `PROMOTION_TRACKING_ENCRYPTION_KEY` 和 `PROMOTION_TRACKING_ENCRYPTION_KEY_ID`，测试与生产 Compose 模板却没有将这两个变量传入容器。即使 Bean 能创建，新增或编辑带平台 Access Token 的渠道时仍可能因为密钥为空而失败。

## 设计

1. 在公开的两参数生产构造器上明确标记 `@Autowired`，让 Spring 注入配置值。
2. 保留三参数构造器，继续作为包内测试入口，不增加无参构造器，也不在代码中提供固定密钥。
3. 在测试环境和生产环境 Compose 模板中显式透传密钥及密钥版本号；任一值为空时 Compose 直接拒绝启动。
4. `.env.example` 只保留不可用的占位值和生成说明；真实 AES-256 密钥只存放在部署机的 `.env` 中。
5. 部署预检严格校验密钥是合法 Base64 且解码后恰好 32 字节，并将 `.env` 权限收紧为 `0600`。
6. 使用 Spring 上下文回归测试验证 Bean 能通过生产构造器创建；使用部署脚本测试约束 Compose、示例配置和预检逻辑不可再次遗漏。

## 安全与运维边界

- 密钥必须是 Base64 编码的 32 字节随机值，并在同一环境中稳定保存，不能每次部署重新生成。
- 密钥版本号必须显式配置；每次更换密钥必须同步更换版本号，不能让同一版本号指向不同密钥。
- 本次不实现密钥轮换和历史密文解密迁移；`key-id` 仅用于标识当前密钥版本并为后续轮换预留边界。
- 本次不修改接口、数据库表结构或公共组件，也不自动连接远程机器和部署。
