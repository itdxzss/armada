## 1. 要做什么

一句话流程：**选一批号 → 建批次 → 后台限速查每个号的 WhatsApp 信任档位 → 在批次详情看分布 → 隔一段时间点"复查此批" → 看和上次比有没有变化**。

### 用户已拍板

- **协议**：Web 先做，Android 后补。
- **查询发起方做成可选**：「每个号查自己」或「探针号代查」。第一期探针只能选 Web 协议号，但被查的号不限协议（档位是服务器按号码返回的），所以第一期探针模式已经能查 Android 账号。
- **复查是手动按钮**：对同一批号再建一个批次，不做定时。
- **菜单**：账号管理 → 档位检测，`menu_key` 用 `AccountTierCheck`，路由 `/account/tier-check`，组件 `account/tier-check/index`，**排序号 25**（现有 列表 10、分组 20、导入 30、新号注册 40、手动接码 45），夹在"账号分组"和"账号导入"之间。菜单权限 `tenant:account:view`；创建、复查、停止、重试要 `tenant:account:edit`。
- **前端格式已定稿**：用现有组件按同类页面写好了草稿，截图为准，不要重新设计布局。

### 不做

- 不做任何"提升档位"的动作（包括自家号互聊），不对账号做自动封禁、下线。
- 不做定时自动复查、账号列表"最新档位"列、导出、档位下降告警（见第 9 节）。
- 不保存协议原始返回，只存归一化字段。
- 不改探针脚本，不把它 import 进服务。

## 4. 各仓库任务

### 4.1 Web 协议层（`armada-protocol/protocol-layer`，分支 `1.0.3-snapshot`）

新增 `POST /v1/accounts/:accountId/integrity-query`，请求 `{ "phone": "<纯数字>" }`，响应结构见设计文档 5.2。

- 查询：`<iq xmlns="w:mex" type="get" to="s.whatsapp.net">` 里放 `query_id="24966207873007786"`（`IntegrityQuery`），变量 `{"input":{"query_input":[{"jid":"<jid>"}],"telemetry":{"context":"INTERACTIVE"}}}`，超时 15 秒。
- 先用 `<号码>@s.whatsapp.net`；返回里没有 integrity 字段，再用 usync 取该号 LID 重试；响应里用 `jidType` 回报用了哪种。
- `status` 取值：`OK`（有字段）、`EMPTY`（返回成功但字段为空，被限流的迹象）、`NOT_ALLOWED`（GraphQL 错误码，已封或不可查）、`ERROR`（其余，带原因码）。
- **不得发任何 `message` 帧。** 测试里断言所有出站帧只有 `iq`。
- 账号必须在线，不在线按现有错误类返回，不要新造错误形状。
- 路由层自己再加账号级串行和最小间隔（配置项，默认 3～4 秒），防止上游误用打爆限流。
- 日志不得输出完整号码和返回体，号码只出前 4 后 2。
- jest 测试：`OK`、`EMPTY`、`NOT_ALLOWED`、GraphQL 其它错误、iq 错误、超时、手机号 JID 无数据时回退 LID、同账号并发时串行。
- 接口文档：补进 `armada-protocol/openapi` 或 `docs/` 里现有的契约文档（先找现有位置，别新建一套）。

### 4.2 Armada 后端（分支 `1.0.3-snapshot`）

**迁移**：取开工时最新版本号。注意 `V223__sms_registration.sql`、`V224__ip_proxy_registration_reservation.sql` 目前是**另一个会话在途、未提交**的文件（`git status` 里是 `??`），所以要用 `ls` 加 `git status` 一起看，必要时先问用户 V225 起是否已被占用，别撞号。两张表 `account_tier_check_task`、`account_tier_check_item` 按设计文档第三节；菜单种子单独一个迁移。表、列、索引都要写 `COMMENT`，遵守《数据模型规范》，写完刷新数据模型文档（见第 7 节关于 `gen_datamodel.py` 的提醒）。

**协议侧**（`com.armada.platform.protocol`）：`port/AccountIntegrityPort`、`routing/AccountIntegrityBackend`、`routing/RoutingAccountIntegrityPort`、`backend/web/WebAccountIntegrityAdapter`、`model/result/ProtocolAccountIntegrity`。第一期没有 Android 适配器，路由会抛 `UNSUPPORTED_BACKEND`：**预览时把它归为排除原因"协议暂不支持"，不要让整批失败**。

**业务侧**（`com.armada.account`，平铺，仿 `AccountMutualContact*`）：Controller、Service + Impl、Scheduler、Transactions、Mapper + XML、DTO/VO/实体。

**调度与限流（实现注意）**：

- tick 不能串行阻塞在同步 HTTP 上（单次查询在协议层最长等 15 秒，HTTP 读超时另算）。建议：tick 只**认领**到期明细（条件更新 `待查→查询中`，同时推进 `next_execute_at`），把查询交给有界线程池（大小走配置，默认小），结果在独立短事务里落库。
- **每个发起账号同一时刻最多一条在途**，相邻两次间隔、每轮条数、轮间冷却全部走配置 `armada.tier-check.*`。默认值取设计文档第四节（间隔 4 秒、每轮 20 个），轮间冷却时长先给占位值，试跑后再定。
- `armada.tier-check.enabled` **默认 false**，真机试跑获得授权后由环境配置打开。这是有意和互存联系人（默认开）不同：这个功能会让真实账号发查询。
- 重启恢复：`查询中` 超时的明细回到 `待查`。
- 租户上下文写法照 `AccountMutualContactScheduler`（`TenantContext.set` / 还原）。
- 结果判定：`OK` → 成功并写字段；`EMPTY` → 失败 `EMPTY_RESPONSE`，**同时让该发起账号进入冷却**，绝不写成"档位消失"；`NOT_ALLOWED` → 状态 5（不可查）；其它异常 → 失败，原因码用 `TIMEOUT` 等，不存原始返回。
- 写结果前校验账号仍存在、协议句柄没变（参照 `AccountTypeVerificationServiceImpl`）。
- 变化判定：只在 `SUSPICIOUS < TIER_0 < TIER_1 < TIER_2 < TIER_3` 这条**推断**链内部判上升、下降；涉及 `UNTIERED` 的变化一律判 4（方向不明）；上次可查、本次没查到判 5。判定集中在一个方法里，方便以后改。
- 上一次快照 = 该账号最近一次**成功**快照，不要求来自 `source_task_id`。
- 探针模式：创建和预览时校验探针属于本租户、在线、第一期是 Web 协议；调度时按当前排队最少分配；探针掉线其未完成明细回到待查；没有在线探针则明细失败 `NO_PROBE_ONLINE`。
- 自查模式：发起账号必须在线，否则失败 `EXECUTOR_OFFLINE`，可用"重试失败"。

### 4.3 接口契约

前端 [`src/api/account-tier-check.ts`](../../../wheel-saas-pure-web/src/api/account-tier-check.ts) 是契约的另一半，**字段名和类型以它为准**，后端照着实现。基路径 `/api/accounts/tier-check-tasks`，统一 `ApiResponse` 信封，列表是 `PageResult`（`list`、`total`、`page`、`pageSize`）。

| 接口 | 权限 | 说明 |
|---|---|---|
| `POST /preview` | edit | 请求 `TierCheckRequest`；响应 `eligible`、`excluded`、`excludedReasons[{reason,count}]`、`previewToken` |
| `POST /` | edit | 请求同上，带 `requestId`、`previewToken`，语义同互存联系人；响应 `TierCheckTask` |
| `GET /` | view | 参数 `page`、`pageSize`、`keyword`、`mode`、`status`；响应 `TierCheckTask` 分页 |
| `GET /{id}` | view | `TierCheckTask`，含 `tierCounts`（键是服务器返回的档位字符串）和 `stats` |
| `GET /{id}/items` | view | 参数 `page`、`pageSize`、`filter`（`changed` 或 `lost`，可空）；响应 `TierCheckItem` 分页 |
| `POST /{id}/stop` | edit | 无响应体 |
| `POST /{id}/retry-failed` | edit | 返回重新排队的条数 |
| `POST /{id}/recheck` | edit | 以同一批账号建复查批次，`sourceTaskId` 指向本批；返回新批次 |
| `GET /api/accounts/{id}/tier-history` | view | 返回 `TierCheckAccountHistory`，`entries` 按时间倒序 |

账号列表入口（4.4 最后一步）需要 `TierCheckRequest` 增加可选 `accountIds`，与 `accountGroupIds` 二选一；到时前后端一起加。
