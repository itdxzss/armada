# Flyway 迁移链对齐

## 目标

在不回退第一套测试环境 V152 数据库的前提下，将最新 `1.0.3-snapshot` 部署回该环境，并继续交付超链一期。

## 决策

- 原样保留用户隔离版本已经执行的 V141～V152，保证 Flyway 版本、描述和校验和与数据库历史一致。
- 超链数据包、模板、菜单迁移从 V141～V143 调整为 V153～V155。
- 不关闭 Flyway 校验，不执行 `flyway repair`，不手工回退或修改共享数据库。
- 当前主线不启用用户隔离业务逻辑；保留的 `owner_user_id` 可空列和兼容索引允许旧逻辑继续写入。

## 影响

- 第一套测试环境启动时校验 V141～V152，并继续执行 V153～V155。
- 新版本运行期间产生的数据仍可能以 `owner_user_id = NULL` 写入，后续恢复用户隔离时需要统一归属。
- 协议层无代码和部署变更。

## 验证

- 对比主线 V141～V152 与隔离 worktree 文件 SHA-256，必须逐个一致。
- 执行超链迁移合同测试、后端回归、前端构建和部署脚本测试。
- 部署后检查 Flyway 日志、进程稳定性和核心业务冒烟。

## 部署结果

- 环境：第一套测试环境；范围：后端和前端；协议层与 Zhuan 未部署、未重启。
- 后端：`origin/1.0.3-snapshot` commit `76a72de3`；前端：commit `6cfd13c7`。
- Flyway 成功校验 156 条迁移，数据库从 V152 顺序执行 V153～V155，最终版本为 V155。
- 后端与 nginx 均为 running，重启次数为 0，部署后五分钟内无 ERROR 或 Flyway 校验错误。
- 测试机本地 HTTP 冒烟：前端返回 200；数据包和超链模板接口未登录返回 401，证明路由已进入鉴权链。
- 部署后只读深度检查通过。

## 回滚

应用异常时恢复部署前后端制品；数据库保留已经成功执行的前向迁移，不手工删除 Flyway 历史。
