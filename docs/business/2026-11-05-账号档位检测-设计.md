# 账号档位检测 设计（2026-11-05，已确认，交 CodeX 实施）

实施任务书：[账号档位检测开发任务书](../handoff/2026-11-05-账号档位检测-Codex任务书.md)。前端原型截图（真实外壳渲染）：[account-tier-check-prototype](../handoff/account-tier-check-prototype/)。

目标：在控端对**一批号**查询 WhatsApp 服务器给的信任档位（trust_tier），隔一段时间对**同一批号**再查一次，看档位有没有变化。对应知识库待办 [`2026-11-04-商业号质量提升-知识库.md`](2026-11-04-商业号质量提升-知识库.md) 第六节第二条："隔几天再查同一批号，看档位会不会变"。

本功能**只读**：不发消息、不改资料，也不负责"提升档位"。它回答的是"这批号现在在哪一档、和上次比有没有变"。

## 一、已确认的事实（出处）

- 查询：`IntegrityQuery`，编号 `24966207873007786`，走 `<iq xmlns="w:mex" type="get" to="s.whatsapp.net">`，变量 `{"input":{"query_input":[{"jid":"<jid>"}],"telemetry":{"context":"INTERACTIVE"}}}`。从网页版协议发能用，**能查别人**（知识库 2.1；脚本 `docs/handoff/wa-probe/integrity-probe.mjs`）。
- 返回字段：`trust_tier`、`is_suspicious`、`is_banned`、`join_date_ms`、`phone_country_code`、`is_mv_subscribed`，以及服务器认定的类型 `XWA2User`（个人号，档位恒为 UNTIERED）/ `XWA2BusinessUser`（商业号）。
- 档位取值：`SUSPICIOUS`、`TIER_0`、`TIER_1`、`TIER_2`、`TIER_3`、`UNTIERED`。**高低顺序是推断**（知识库 2.3），官方没有说明。
- 限流：一次查 20～30 个号后，返回字段会变空或超时断连；每次 5～20 个号、间隔 4 秒比较稳。已封的号返回 `NOT_ALLOWED`。同一个号隔几小时再查结果一样。
- 现状代码：Web 协议层已在发 `w:mex`（`protocol-layer/src/worker/group-member-link-mode.ts`）；Android 协议层有 `SendIqMex`（`internal/service/app/safemex.go`），但返回体没有解析（`internal/service/node/nodes/iq.go` 里解析代码被注释掉）。
- Armada 账号表没有档位字段，只有 `account_type`、`wa_creation_at` 等。

| 期 | 内容 | 说明 |

| 第 0 步 | 小规模真机试跑 | 需要用户授权，并先确认目标环境。见第七节 |

## 三、数据模型（Flyway，版本号落地时取当时最新，现为 V225）

沿用互存联系人（V202）的"任务 + 明细"形状。**每次检测新增一行明细，不覆盖**，否则没法对比。

`account_tier_check_task`（一次检测批次）

| 字段 | 说明 |
|---|---|
| id, tenant_id, created_by, request_id | 租户、发起人（数据归属）、创建幂等键；唯一键 (tenant_id, created_by, request_id) |
| name | 批次名，可空 |
| mode | 1 每个号查自己；2 探针号代查 |
| source_task_id | 复查时指向上一个批次，可空 |
| total_count | 号数 |
| status | 1 执行中；2 已停止；3 已完成；4 部分失败 |
| created_at, updated_at, finished_at | 毫秒时间戳 |

探针号集合记在任务上，具体存法（JSON 列或子表）按《数据模型规范》定。

`account_tier_check_item`（一个号在一个批次里的一次检测 = 一份快照）

| 字段 | 说明 |
|---|---|
| id, tenant_id, task_id, account_id, phone | 目标账号及号码快照；唯一键 (tenant_id, task_id, account_id) |
| executor_account_id | 实际发起查询的账号；自查模式等于 account_id，探针模式由调度时分配 |
| status | 1 待查；2 查询中；3 成功；4 失败（可重试）；5 不可查（`NOT_ALLOWED` 等）；6 已取消 |
| reason_code | 失败或不可查原因码，如 `EXECUTOR_OFFLINE`、`EMPTY_RESPONSE`、`NOT_ALLOWED`、`TIMEOUT`；不存协议原始返回 |
| server_user_type | `PERSONAL` / `BUSINESS`，**以服务器返回为准**，不用我们库里的标签（知识库 2.2 说标签不可靠） |
| trust_tier | 档位字符串；没拿到数据时为空，**不写成 UNKNOWN 档** |
| is_suspicious, is_banned, is_mv_subscribed | 可空 |
| join_date_ms, phone_country_code | 注册时间、号码国家，可空 |
| prev_item_id, prev_trust_tier, prev_checked_at | 同一账号上一次**成功**快照，写结果时回填，列表不用再联查 |
| tier_change | 0 首次；1 不变；2 上升；3 下降；4 变化但方向不明；5 本次未查到（上次可查） |
| checked_at, attempt_no, next_execute_at, created_at, updated_at | 查询时间、尝试次数、调度水位 |

索引：(tenant_id, account_id, checked_at) 用来找上一次快照和画单号时间线；(tenant_id, task_id, status, id) 用来翻页和调度。

**变化判定**：只在 SUSPICIOUS < TIER_0 < TIER_1 < TIER_2 < TIER_3 这条推断链内部判"上升/下降"；涉及 UNTIERED 的变化一律判 4（方向不明），界面上如实显示"有变化"，不标箭头。顺序坐实后只改这一处判定。

## 四、执行与限流

- 调度器照 `AccountMutualContactScheduler` 的写法，按固定间隔扫到期明细。**每个发起账号同一时刻只有一条查询在途**。
- 默认参数（配置项，试跑后调整）：同一发起账号相邻两次查询间隔 4 秒；每轮最多 20 个；轮与轮之间冷却，时长试跑后定。
- **自查模式**：发起账号必须在线。不在线的明细置失败（`EXECUTOR_OFFLINE`），可用"重试失败"再跑。
- **探针模式**：创建时选 1～N 个在线探针号，调度时按"当前排队最少"分配；探针中途掉线，其未完成明细回到待查，由别的探针接手；没有在线探针则明细失败（`NO_PROBE_ONLINE`）。
- **空返回不当结果**：协议返回 200 但没有 integrity 字段，记失败（`EMPTY_RESPONSE`），同时让该发起账号进入冷却（这是被限流的迹象）。绝不能写成"档位消失"。
- 查询中状态超时未回，回到待查，防止进程重启后卡死。
- 档位查询是**同步 HTTP**，响应里就带结果，不像互存联系人那样"只投递命令、事件回写"。调度 tick 只认领到期明细，查询交给有界线程池，不在 tick 里串行阻塞调用。
- 配置开关 `armada.tier-check.enabled` 默认关闭，真机试跑获得授权后由环境配置打开（会让真实账号发查询，所以和互存联系人默认开不同）。
- 复查 = 用同一批账号再建一个批次，`source_task_id` 指向上一个批次。上一次快照取"该账号最近一次成功快照"，不要求一定来自 `source_task_id`。

## 五、协议层契约

### 5.1 Armada 内部（沿用 `AccountRuntimeStatusPort` 三件套）

- `platform/protocol/port/AccountIntegrityPort`：`query(ProtocolAccountRef executor, String targetPhone)` → `ProtocolAccountIntegrity`（归一化：状态、用户类型、档位、是否可疑、是否封号、注册时间、国家、是否认证）。
- `routing/AccountIntegrityBackend` + `RoutingAccountIntegrityPort`：按发起账号的协议后端分发，未注册的后端抛 `UNSUPPORTED_BACKEND`。
- `backend/web/WebAccountIntegrityAdapter`（第一期）、`backend/android/AndroidNativeAccountIntegrityAdapter`（第二期）。

### 5.2 Web 协议层（第一期）

新增 `POST /v1/accounts/:accountId/integrity-query`，请求 `{ "phone": "<纯数字>" }`，响应：

```json
{ "phone": "...", "status": "OK|EMPTY|NOT_ALLOWED|ERROR", "userType": "PERSONAL|BUSINESS",
  "trustTier": "TIER_1", "isSuspicious": false, "isBanned": false, "isMvSubscribed": false,
  "joinDateMs": 0, "phoneCountryCode": "...", "jidType": "pn|lid" }
```

- 用该账号自己的连接发 `w:mex` 的 `IntegrityQuery`；先用手机号 JID，没有 integrity 字段再用 usync 取 LID 重试。解析逻辑直接复用探针里的 `pickFields`。
- 不发任何 `message` 帧。路由层自己再加一道账号级串行 + 最小间隔，防止上游 bug 打爆限流（纵深防御）。

### 5.3 Android 协议层（第二期）

- 先确认 `SendCheckAccount` 返回的 promise 能不能拿到响应体；拿不到就在 `handleResultNode` 按请求编号关联。
- 补解析 `data.xwa2_fetch_wa_users[0].integrity_signals_info`，新增查询接口，返回同 5.2 的结构。
- Android 现有编号 `24897449816559062` 和 iOS 编号 `24966207873007786` 哪个能用，要试跑确认。

## 六、Armada API 与前端

后端 `/api/accounts/tier-check-tasks`（权限沿用 `module_key` / `perm_key`，数据按 tenant_id + created_by 隔离）：

| 接口 | 作用 |
|---|---|
| `POST /preview` | 预览：可查数、排除数及原因（自查模式的离线号、探针号不在线等） |
| `POST` | 创建批次，参数含账号范围（勾选 / 分组 / 筛选）、模式、探针号、`sourceTaskId`、`requestId` |
| `GET` / `GET /{id}` / `GET /{id}/items` | 批次列表、详情（含各档位计数）、明细分页（可只看有变化的） |
| `POST /{id}/stop`、`POST /{id}/retry-failed` | 停止、重试失败 |
| `POST /{id}/recheck` | 以同一批账号建复查批次 |
| `GET /api/accounts/{id}/tier-history` | 单个账号的档位时间线 |

前端（`wheel-saas-pure-web`，沿用 pure-admin + Element Plus，页面只调 `src/api/account-tier-check.ts`）：菜单"账号管理 → 档位检测"（`menu_key` 为 `AccountTierCheck`，路由 `/account/tier-check`，排序号 25，夹在"账号分组"和"账号导入"之间；靠 Flyway 种子，参照 `V222__sms_activation_menu.sql`）。菜单权限 `tenant:account:view`，创建、复查、停止、重试要 `tenant:account:edit`。新建、详情、账号时间线都是抽屉，与"互相添加好友"抽屉一致。账号列表"批量操作"另加"检测档位"入口，带着勾选账号打开新建抽屉。

- 批次列表：批次名、模式、号数、各档位占比、状态、时间、"复查"按钮。
- 新建：选账号（默认只勾商业号，可选包含个人号）、选模式、选探针号、预览。
- 批次详情：各档位计数；"上次 → 本次"变化统计；明细表（号码、服务器类型、档位、上次档位、变化、注册时间、国家、状态）；筛选"只看有变化"。
- 账号详情里看该号的档位时间线。

## 七、验证与放量

1. 后端：Mapper / Service 用 H2 测，调度、限流、空返回、探针掉线接手、变化判定各有用例；Web 协议层用 jest 模拟 `sock.query`（参照 `group-member-link-mode.test.ts`）；前端跑 typecheck / lint / build。
2. **真机试跑（第 0 步，需要用户授权并先确认目标环境）**，不超过 10 个号，回答四个问题：
   - 自查和探针代查，同一个号的结果是否一致；
   - 手机号 JID 和 LID 哪个能用；
   - 隔几小时重复查，结果是否稳定（知识库说稳定）；
   - 每轮 20 个号的限流边界。
3. 试跑通过再放量；放量后第一次复查，就是对知识库"档位会不会变"这个待办的第一份实测。

## 八、风险与待验证

- **自查结果是否等于"查别人"的结果，没有验证过**，试跑才知道。如果不一致，自查模式要降级成"仅供参考"或去掉。
- **从生产号发这个查询是否有风险，没有证据**。知识库的探针特意没连生产环境。探针模式把风险集中在少数号上，建议用可丢弃的号做探针。
- 档位高低顺序是推断，"上升/下降"只在推断链内部成立。
- 限流参数是知识库里的经验值，来自 20 来个号的观察。
- 档位变化和发送量、封号的关系，没有证据。本功能只提供数据，不下结论。

## 九、不做

- 不做任何"提升档位"的动作（包括自家号互聊）。知识库第一节已写明原因。
- 不自动对账号做封禁、下线等处理。
- 不保存协议原始返回，只存归一化字段。
