# 拉手邀请间隔与 423 locked 重试设计

## 背景

普通链接拉群当前通过共享 `PullTaskOperationDelayPolicy` 在相邻 WhatsApp 副作用之间随机等待 3～5 秒。现场任务中，第一个拉手入群成功后约 4.6 秒发起第二次邀请，WhatsApp 对第二次邀请返回顶层 IQ 错误 `423 locked`，目标拉手未进入群聊；Android 随后把所有顶层 IQ 错误泛化成 `PROTOCOL_RESULT_UNCONFIRMED`。

## 目标

1. 相邻拉手邀请之间随机等待 6～8 秒。
2. Android 收到拉手邀请的明确顶层 IQ `423 locked` 后，不查询群成员，随机等待 6～8 秒并重试一次。
3. 第二次仍返回 `423 locked` 时，上报明确且可重试的失败，不再上报结果未知。
4. 不改变管理员进群、管理员提权、保存联系人和批量拉人等其他副作用的既有间隔与错误语义。

## 后端设计

新增拉手邀请专用的延迟策略，随机范围为闭区间 6000～8000 毫秒。`PullTaskPullerInviteResultServiceImpl` 在处理一次拉手邀请回调后，使用该策略设置下一次执行时间。

现有 `PullTaskOperationDelayPolicy` 继续维持 3～5 秒，供管理员动作、保存联系人和其他普通链接副作用使用，避免扩大本次变更范围。`pull_interval_seconds` 的批次拉人语义保持不变。

## Android 设计

Android 原生拉人客户端保留顶层 IQ 错误的 `code` 与 `text`，不再把 `423 locked` 丢失为无类型普通错误。

仅对来源为 `pull_task_puller_invite` 的成员添加动作执行以下流程：

1. 第一次原生邀请返回 `423 locked`。
2. 记录包含 `commandId`、`actionId`、群 JID、目标 JID、错误码和重试延迟的结构化 Warn 日志。
3. 使用可响应 `context.Context` 取消的计时器随机等待 6～8 秒。
4. 使用同一账号、群和目标重试一次，不查询群成员。
5. 重试成功则按原成员回执上报成功。
6. 重试再次返回 `423 locked`，上报 `FAILED / GROUP_ACTION_LOCKED / retryable=true`。

非 `423` 顶层错误沿用现有处理；批量拉人和管理员提权不进入本次单次重试流程。任何路径都不允许无限重试。

## 一致性与终态

`423 locked` 是服务端明确拒绝，不属于网络超时或连接中断，因此本设计不执行成员快照确认。重试耗尽后记录明确的可重试失败事实，供诊断和后续策略使用；当前拉手邀请业务不会据此再次自动重试。UI 不再展示“Android 成员变更结果未确认”。

若等待期间上下文取消，则停止重试并沿用现有执行超时/不确定结果处理，避免后台 goroutine 无界存活。

## 测试

后端测试覆盖：

- 拉手邀请专用策略接受 6000 和 8000 毫秒边界。
- 超出边界时拒绝。
- 拉手邀请回调使用专用策略计算下一执行时间。
- 其他副作用仍使用原 3～5 秒策略。

Android 测试覆盖：

- 第一次 `423 locked`、第二次成功时只重试一次并返回成功。
- 连续两次 `423 locked` 时返回 `GROUP_ACTION_LOCKED` 可重试失败。
- 非 `423` 错误不进入 locked 重试。
- 等待期间上下文取消时不发起第二次原生调用。
- 重试路径不调用任何群成员查询能力。

## 非目标

- 不修改 `pull_interval_seconds`。
- 不加入群成员查询或结果对账。
- 不增加无限重试、指数退避或跨进程重试状态。
- 本次不部署测试环境或修改线上数据。
