# 150 账号上线内存/稳定性问题 — 诊断与修复设计

日期：2026-07-08
状态：待用户审阅
范围：`protocol-layer`（Baileys 7.x WhatsApp 协议层）

## 1. 问题陈述

单节点上线约 150 个账号后，机器负载被打满、worker 进程内存持续增大并最终被 PM2 重启，重启后账号不再恢复上线。初始怀疑是内存泄露。

## 2. 诊断结论（数据来源：2026-07-07 19:00–22:00 运行时快照，共 1471 个采样）

快照文件：`protocol-runtime-20260707-{19,20,21}.ndjson`（由 `scripts/collect-runtime-snapshot.sh` 采集）。

**结论：不是经典慢泄露，而是"掉线-重连风暴 → 瞬时分配风暴 → GC 高压 → 内存尖峰撞限 → worker 猝死 → 账号不恢复"的复合缺陷链。**

### 2.1 证据链

| # | 现象 | 数据 |
|---|------|------|
| 1 | 428 掉线风暴 | worker-1（66 账号）3 小时内 `disconnect_total{code=428}` 从 1155 → 1899（+744，≈3.8 次/账号/小时）；worker-3 从 2443 → 2614 |
| 2 | PROXY_FAILED 重上线空转 | `online_total{source=proxy_failed_reonline}`：worker-1 +307/3h，worker-3 +190/3h（worker-3 仅 4~29 个账号，人均每小时被重上线 60+ 次） |
| 3 | 分配风暴 + GC 高压 | worker-1/2 heap 每 ~7 秒在 200MB↔550MB 之间锯齿震荡；CPU 60–120% 常态 |
| 4 | 内存尖峰撞限 | worker-2 于 19:37:40 heap 瞬时冲到 1058/1494MB（1.5GB 上限）、RSS 1309MB，同时刻 `kafka_producer_inflight` 飙到 188；20:04 heap 986MB/RSS 1411MB 时被 PM2 重启 |
| 5 | 账号不恢复（最严重业务影响） | worker-2 重启后，其名下 78 个账号直到快照结束（约 2 小时）ONLINE=0，master 注册表 load=0；150 账号最终仅剩 77 在线 |
| 6 | worker-3 病态热点 | 仅 4~29 个账号，CPU 恒 100%+，事件循环延迟恒定 ~1.75 秒持续 3 小时（正常 <10ms） |
| 7 | 负载不均 | worker-4 全程 0 账号闲置，worker-1/2 各扛 66/78 |

### 2.2 根因链（代码层面）

1. **重连退避形同虚设**：`src/worker/reconnect.ts` 的 `ReconnectController.schedule()` 中 `s.attempt = 0` 恒置零，延迟恒为 0–500ms 随机抖动，A 类重连实际上是无退避立即重连。
2. **428 救援闭环空转**：428 掉线 → `rescueClosedSocketAfterProbe`（同代理快速救援）→ 救援再失败 → `markProxyFailed` → `releaseRuntimeSlot`（`slotReleased=true`）→ 上游以 `source=proxy_failed_reonline` 重新上线 → 代理依旧不稳 → 再次 428。每轮循环 = 新建 Baileys socket + noise 握手 + libsignal 加密 + 拉取离线数据，产生大量瞬时分配。
3. **故障释放的槽位无人认领**：`src/worker/assignment-reconciler.ts` 的 adopt 循环对 `runtime.slotReleased === true` 的账号一律跳过，且不区分"业务主动下线"与"故障释放"。worker 猝死重启后，名下账号全部处于释放态，reconciler 永远跳过 → 账号丢失。
4. **事件积压放大内存尖峰**：Kafka producer inflight 无上限背压，事件 envelope 在风暴期堆积在 heap 中，与重连分配叠加冲破 1.5GB。

## 3. 修复设计（止血，按优先级）

### 修复 ①：worker 重启后账号自动恢复（P0）

- 释放槽位时记录语义：`releasedReason` 与 `releasedAt` 时间戳，写入 account runtime store。两类语义：
  - `terminal_offline`（不可自动恢复）：业务主动下线、LOGIN_REPLACED（抢登）、NEED_REAUTH（需重新认证）——终态，必须业务侧介入，reconciler 永远跳过；
  - `fault_released`（可自动恢复）：PROXY_FAILED、重连耗尽等故障路径——临时故障，允许自动回归。
- `AssignmentReconciler.tick()` 跳过规则改为：仅跳过 `terminal_offline`；`fault_released` 的账号在冷却期（默认 5 分钟，可配）过后允许重新 adopt。
- 效果：worker 猝死/重启后，名下账号最迟"一个 reconciler 周期（30s）+ 冷却期"内自动回归，不依赖上游手工重上线。

### 修复 ②：重连真退避（P0 — 2026-07-08 二次确认实施，退避封顶调整为 30s）

- `ReconnectController` 真正使用 `attempt` 字段：延迟 = `min(1s × 2^attempt, 30s)`，附 ±30% 抖动；每次调度 `attempt++`。
- 重置条件：连接成功且稳定在线超过 5 分钟（而非一连上就清零），防止"连上 10 秒又掉"绕过退避。
- 428 快速救援路径（`rescueClosedSocketAfterProbe`）纳入同一 per-account 退避计数，救援与重连共享 attempt。

### 修复 ③：PROXY_FAILED 重上线冷却 + 熔断（暂缓 — 2026-07-08 用户决定本次不实施，设计保留备后续）

- 协议层 online 入口强制执行（不信任上游节流）：
  - 账号进入 PROXY_FAILED 后开启冷却窗口（首次 60s，指数增长，封顶 15 分钟）；窗口内拒绝 `source=proxy_failed_reonline` 的上线请求，返回结构化错误：错误码 `PROXY_COOLDOWN` + `retryAfterSec`。
  - 连续 5 次 PROXY_FAILED（中间无"稳定在线"，即无一次 ≥5 分钟的持续 ONLINE，与修复②的重置条件一致）触发熔断：静默 30 分钟，并通过现有 publisher 发布 `account.proxy_quarantine` 事件，提示业务侧更换代理。
- 冷却/熔断状态存 worker 内存 + runtime store（进程重启不丢熔断状态）。

### 修复 ④：内存尖峰护栏（P1）

- `src/events/publisher.ts` 增加 inflight 上限（默认 100，可配）与背压策略：超限时低优先级事件（如状态抖动类）丢弃并计数（新增 metric `unsea_event_dropped_total{reason=backpressure}`），高优先级事件（NEED_REAUTH、quarantine 等）阻塞入队。
- 校准 PM2 `max_memory_restart` 与 `--max-old-space-size`：保证 heap 上限先于 RSS 重启线生效，给 GC 留出回收窗口而不是直接进程死亡。

### 暂不做（YAGNI / 用户决策）

- 修复③（冷却+熔断）：用户决定本次不实施；`proxy_failed_reonline` 的外部空转仍会存在。
- **预期管理**：③不做意味着"救援→释放→上游重上线"环路仍在（每次释放清空退避状态，②对该环路抑制有限）；②主要抑制进程内短周期反复掉线的账号。稳态 CPU 与掉线率的大幅改善依赖 ③ 排期 + §4 profile 根治。
- worker 间负载均衡（w4 闲置）：修复①落地后单 worker 压力下降，暂不动分配策略。
- worker-3 事件循环热点：不盲改，见 §4 用 profile 定位后另立后续项。

## 4. 根治定位（止血合入后，复现环境进行）

1. **稳态分配风暴溯源**：单节点测试环境（参照 `protocol-layer/docs/SINGLE-NODE-TESTING.md`）上线 100~150 账号，间隔 30 分钟抓 3 份 heap snapshot 对比 retained size；嫌疑对象：重连历史同步缓冲、keys L1 缓存（200k 条目）、事件 envelope、drop 入站消息的日志量。
2. **worker-3 病态热点**：`--cpu-prof` 抓火焰图，定位 10 账号却恒定 1.75s 事件循环延迟的空转代码。修复方式取决于定位结果，独立后续项，不阻塞止血上线。

## 6. 测试

- 单元：退避序列计算（含抖动边界、封顶、稳定重置）；熔断状态机（冷却→熔断→恢复）；reconciler 对 `fault_released` 账号的 adopt 条件与冷却判断；publisher 背压丢弃/阻塞分支。
- 集成：模拟 428 连环掉线，断言退避序列与 PROXY_FAILED 转移；模拟 worker 重启（清内存态、保留 runtime store），断言 reconciler 恢复。
- 遵循仓库现有 jest 测试模式（`account-manager.heartbeat.test.ts` 等文件旁新增）。

## 7. 错误处理

- 冷却中的上线请求：返回结构化错误（`PROXY_COOLDOWN` + `retryAfterSec`），不静默吞掉；上游可编程处理。
- 熔断触发：发布 Kafka 事件，不静默。
- 背压丢弃：计数进 metric，日志按采样率记录。
