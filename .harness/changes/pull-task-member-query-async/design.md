# 普通拉群成员查询异步化

## 背景

普通拉群调度器当前在同一条单线程内依次执行批次派发和未知结果收敛。收敛中及管理员、补位流程中直接通过 `GroupMemberListPort` 调用协议层 HTTP 接口。网络慢请求会占住调度线程，导致已经到期的下一拉人批次不能按配置间隔写入 Outbox。

## 目标与范围

- 将普通拉群的批次派发和未知结果收敛拆为两个独立执行器。
- 将普通拉群所有群成员事实读取改为 Outbox + Kafka 命令/结果事件；调度线程不再直接 HTTP 查询协议层。
- 覆盖管理员进群/设置、补拉手/补管理员、未知结果收敛和逐号码批次名单核验。
- 不改营销建群、营销拉群的成员查询；它们不属于本次普通拉群任务范围。

## 协议

新增 `group.members.query.requested` 命令与 `group.members.result_reported` 事件。命令以 `commandId` 作为幂等键，携带租户、普通拉群执行行、查询用途、群 JID、协议账号和所需目标成员集合。Worker 在该账号的 group operation gate 内调用 `groupMetadata`，发布结果后才确认 inbox。结果只包含被请求成员的在群和管理员事实；查询失败回传明确错误，不能把缺少回调推断为拉人失败。

## 后端状态机

后端持久化成员查询请求、用途、目标、状态及 `commandId`。阶段处理器在短事务中创建查询记录与 Outbox，随后退出；结果消费者在行锁内校验关联关系和幂等性，保存事实并唤醒对应执行行。未收到结果的查询在超时后可重新入队，但同一业务用途同一时刻只能有一个未完成请求。

## 调度隔离

`PullTaskExecutionDispatchScheduler` 仅运行到期执行行派发和显式触发。`PullTaskUnknownResultReconciliationScheduler` 独立运行收敛扫描。两个执行器均保持单线程和租约/版本检查，因此不改变单任务批次顺序；一个慢成员查询只会占用协议 Worker 的账号 gate，不会阻塞派发执行器。

## 失败与可观测性

- Outbox 投递失败沿用既有重试和死信语义。
- Worker 查询失败、结果超时和重复事件分别记录 query 状态、原因码和时间戳。
- 增加按 `commandId`、执行行和用途输出的结构化日志与测试断言。

## 验证

- 后端：调度器隔离、查询入队、重复/迟到结果、失败/超时及各用途状态推进的单元和 MyBatis 集成测试。
- 协议层：命令解析、账号 gate、成员结果过滤、发布失败重放与未知命令拒绝测试。
- 端到端：收敛慢查询不会推迟下一拉人批次 Outbox 写入。
