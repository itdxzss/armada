# 普通群组营销任务账号锁定与五态生命周期设计

## 背景

2026-07-10 上午实现的普通群组营销账号占用以“进入发送中”为锁定起点，并允许停止后释放、已结束后重新启动。最新确认的业务规则改为：任务创建保存成功即锁定所选账号，未到开始时间和暂停期间都不释放；只有已完成或已关闭两个终态释放账号，两个终态都不可再次启动。

本设计替代同日早先的“执行期动态占用”和“已结束重新启动”口径。

## 范围

- 仅处理普通群组营销任务 `marketing_task`。
- 覆盖后端任务状态、账号占用、调度、API、删除联动和前端列表/创建抽屉。
- 不处理建群营销、速拉群。
- 手动关闭只阻止后端生成新轮次，不撤回已经写入 Outbox、Kafka 或协议层队列的消息。
- 不新增协议层取消命令。

## 方案比较与选择

### 方案一：复用现有占用表和主要状态码（采用）

保留 `marketing_account_occupancy` 的 `(tenant_id, account_id)` 唯一约束，复用任务状态码 1、2、5、7，新增状态码 8。创建事务在保存任务和目标后一次性锁定全部所选账号；暂停不删除占用行；终态事务统一释放。

优点是迁移面最小，现有任务、目标、轮次和账号占用结构都能继续使用。缺点是需要将历史状态 3、4、6 归并为已完成，并删除上午新增的重新启动链路。

### 方案二：重建连续的五状态码

把五种状态重新编号为 1 到 5，并迁移全部 SQL、前端常量和历史数据。状态表面更整齐，但会扩大迁移风险，并容易与现有目标状态、发送尝试状态混淆，因此不采用。

### 方案三：任务状态与账号租约分别建独立状态机

为账号租约增加单独的 ACTIVE/RELEASED 状态和历史表。审计能力更强，但当前需求只需要当前占用关系，现有 current-only 表已经能由唯一键提供并发闸门，因此不采用。

## 五态模型

任务主表只保留以下五种业务状态：

| 代码 | 后端枚举 | 前端文案 | 账号占用 | 允许操作 |
|---|---|---|---|---|
| 1 | `PENDING` | 未启动 | 保留 | 启动、手动关闭 |
| 2 | `SENDING` | 执行中 | 保留 | 暂停、手动关闭 |
| 5 | `PAUSED` | 已暂停 | 保留 | 恢复、手动关闭 |
| 7 | `COMPLETED` | 已完成 | 释放 | 无 |
| 8 | `CLOSED` | 已关闭 | 释放 | 无 |

任务主状态 3=发送成功、4=发送失败、6=部分失败不再使用。已有数据在迁移时归并为 7=已完成。任务目标 `marketing_task_target` 和发送尝试 `marketing_task_send_attempt` 的成功、失败、部分失败、跳过状态保持不变，用于表达实际发送结果。

状态流转固定为：

```text
PENDING --到达开始时间或窗口内点击启动--> SENDING
SENDING --暂停--> PAUSED
PAUSED --恢复且仍在时间窗口内--> SENDING

PENDING/SENDING/PAUSED --到达结束时间或确定异常终止--> COMPLETED
PENDING/SENDING/PAUSED --手动关闭--> CLOSED
```

`COMPLETED` 和 `CLOSED` 没有任何流出状态。删除 `/restart` 接口、DTO、Mapper 更新、前端弹窗和相关测试。

## 计划时间与启动语义

- 创建任务时根据表单保存 `task_start_at` 和 `task_end_at`，账号在创建事务提交时已经锁定。
- `now < task_start_at` 时任务为 `PENDING`。运营可以点击“启动”，接口幂等成功，但不生成轮次、不提前发送，状态仍为 `PENDING`，前端提示“任务已进入等待，将在计划开始时间自动执行”。
- 即使运营从未点击“启动”，调度器也会在 `task_start_at <= now < task_end_at` 时自动将 `PENDING` 推进为 `SENDING`。
- 在计划窗口内，点击“启动”和调度器自动启动使用同一个带预期状态的并发更新；并发发生时最终只有一个状态推进，不重复生成轮次。
- `now >= task_end_at` 时不允许启动或恢复。API/调度器先把任务推进为 `COMPLETED`，再释放账号。
- `PAUSED` 到达结束时间时同样自动进入 `COMPLETED` 并释放账号。

## 账号锁定与并发

### 创建时原子锁定

`POST /api/marketing-tasks` 在同一个数据库事务内按以下顺序执行：

1. 校验任务表单、模板和账号目标。
2. 插入 `marketing_task`。
3. 插入 `marketing_task_target`。
4. 按目标中的去重账号 ID 插入 `marketing_account_occupancy`。
5. 查询全部目标账号的当前 owner，确认每个账号都由新任务持有。
6. 若任一账号属于其它任务，抛冲突异常，整个任务、目标和本次新插入占用全部回滚。

数据库唯一键 `(tenant_id, account_id)` 是并发事实源。账号树禁选和创建前检查仅用于改善提示，不能代替创建事务的最终校验。

冲突提示固定为：

```text
该账号正在被任务【任务名称】占用，请先关闭原任务后再使用。
```

如果并发冲突涉及多个账号，返回按账号 ID 排序后的第一条冲突；任务整体保存失败，不允许部分账号锁定、部分账号跳过。

### 有效占用

占用 owner 任务只要处于 `PENDING`、`SENDING`、`PAUSED` 任一状态就有效。占用清理不再依据 `task_end_at` 直接删除；必须先完成任务终态状态更新，再按任务 ID 释放，避免任务仍是非终态时账号已经可被其它任务选中。

`deleteStale` 只清理 owner 任务不存在、已软删或处于 `COMPLETED/CLOSED` 的残留占用。

### 暂停与恢复

- 暂停只执行 `SENDING -> PAUSED`，清空 `next_round_at`，不释放账号。
- 恢复只执行 `PAUSED -> SENDING`，将 `next_round_at` 设为当前时间，不重新竞争已由本任务持有的账号。
- 每轮发送仍可检查 owner 作为防御；若发现其它任务 owner，应停止该账号本轮发送并记录一致性错误，但正常创建流程不会产生这种冲突。

## API

保留：

- `POST /api/marketing-tasks/{id}/start`
  - 仅接受 `PENDING`。
  - 开始时间前幂等返回 `PENDING`。
  - 计划窗口内推进为 `SENDING`。
  - 结束时间后推进为 `COMPLETED` 并释放。
- `POST /api/marketing-tasks/{id}/pause`
  - 仅接受 `SENDING`，推进为 `PAUSED`，不释放。
- `POST /api/marketing-tasks/{id}/resume`
  - 仅接受 `PAUSED`。
  - 时间窗口内推进为 `SENDING`；已到结束时间则推进为 `COMPLETED` 并释放。
- `POST /api/marketing-tasks/{id}/close`
  - 接受 `PENDING`、`SENDING`、`PAUSED`。
  - 原子更新为 `CLOSED`、清空 `next_round_at`、写 `finished_at`、释放全部账号。
  - 已完成或已关闭任务调用时明确拒绝。

删除：

- `POST /api/marketing-tasks/{id}/restart`
- `RestartMarketingTaskDTO`
- 所有已完成任务重新设置时间的逻辑。

## 正常完成、异常终止和联动

- 到达 `task_end_at` 是当前普通群组营销的正常完成条件。
- 如果业务代码明确判定任务不可恢复并结束任务，必须使用与正常完成相同的 `COMPLETED + releaseByTaskId` 事务路径。
- 调度器中的单次可重试异常只记录并等待下轮，不等同于“异常结束”，因此不释放账号。
- 删除被非终态任务引用的营销模板时，关联任务统一进入 `COMPLETED`、写 `finished_at` 并释放账号，避免产生无法恢复但长期占用账号的暂停任务。
- 批量删除营销任务只允许 `COMPLETED`、`CLOSED`；请求包含任一非终态任务时整批拒绝。删除时再按任务 ID 防御性清理残留占用。

## 账号配置树

账号树不再因为分组中存在一个占用账号而拒绝整个分组。查询返回每个账号自身的可用性，并增加结构化字段：

```text
locked
occupiedTaskId
occupiedTaskName
selectable
disabledReason
```

被占用账号必须返回：

```text
locked=true
selectable=false
disabledReason=该账号正在被任务【任务名称】占用，请先关闭原任务后再使用。
```

前端账号树继续展示空闲账号，并把占用账号置灰。通过自定义节点内容或 Tooltip 直接展示 `disabledReason`；默认全选和构造提交 selections 时都必须排除 `selectable=false` 或 `locked=true` 的账号。

懒加载单账号群列表时再次检查占用状态，防止账号树加载后、用户展开或提交前 owner 已发生变化。

## 前端任务按钮

任务列表生命周期主按钮使用单一状态映射：

| 状态 | 主按钮 |
|---|---|
| 未启动 | 启动 |
| 执行中 | 暂停 |
| 已暂停 | 恢复 |
| 已完成 | 不可操作，可显示“已完成” |
| 已关闭 | 不可操作，可显示“已关闭” |

“手动关闭”是独立操作按钮，仅在未启动、执行中、已暂停显示。点击后必须二次确认；成功后行状态更新为“已关闭”，所有生命周期按钮消失。

移除 `GroupMarketingRestartDialog.vue`、`useMarketingTaskRestart.ts` 和对应 API、页面接线、测试。

## Outbox 边界

暂停或关闭后，任务状态和 `next_round_at` 阻止生成新轮次。已经在关闭事务之前写入 Outbox、Kafka 或协议层 Redis Stream 的命令继续执行并正常回写结果；本次不增加撤回或取消机制。

轮次 Worker 在写 attempt/outbox 前继续以 `status=SENDING` 作为并发守卫。关闭或暂停与轮次抢占并发时，只有先成功持有状态守卫的一方能生成该轮；关闭成功后不会再生成后续轮次。

- 保留 1=未启动、2=执行中、5=已暂停。
- 更新 `marketing_task.status` COMMENT，增加 8=已关闭。

## 测试范围

后端必须覆盖：

- 未来任务创建后立即锁定全部所选账号。
- 并发创建共享账号时只有一个事务成功，失败方完整回滚并返回占用任务名称。
- 账号树逐账号禁选，不再整组拒绝。

- 正常完成、明确异常终止、模板删除联动和终态删除清理都释放账号。

- 五态文案及启动/暂停/恢复单一按钮映射。

- 手动关闭确认、成功刷新和失败提示。
- 不再存在重新启动 API、弹窗和页面接线。
- 占用账号置灰、提示精确文案、默认全选及提交排除锁定账号。

## 非目标

- 不取消已排队消息。
- 不新增协议层任务状态或账号锁。
- 不修改建群营销、速拉群。
- 不支持已完成或已关闭任务恢复；继续使用时重新创建或复制任务。
